# MySQL

## 1. 事务四大特性 ACID

- **原子性 (Atomicity)**：事务是最小执行单元，要么全部执行成功，要么全部回滚，不会部分执行。
- **一致性 (Consistency)**：事务执行前后，数据库数据完整性、约束规则保持一致。
- **隔离性 (Isolation)**：多个并发事务之间相互隔离，互不干扰，由隔离级别控制。
- **持久性 (Durability)**：事务提交后，数据永久落地，宕机也不会丢失。

**补充**：InnoDB 通过 `redo log` 保证持久性，`undo log` 保证原子性。

## 2. 事务四大隔离级别（默认可重复读）

1. **读未提交 (Read Uncommitted)**：可读到其他事务未提交数据，存在**脏读、不可重复读、幻读**。

   **读已提交 (Read Committed)**：只能读到已提交数据，**解决脏读**，仍存在不可重复读、幻读。

   **可重复读 (Repeatable Read)**：同一事务多次读取结果一致，**解决脏读、不可重复读**；MySQL InnoDB **默认级别**，通过间隙锁 / 临键锁大部分解决幻读。

   **串行化 (Serializable)**：最高级别，完全串行执行，**解决所有并发问题**，并发性能极差。

## 3. 脏读、不可重复读、幻读

- **脏读**：读到别人未提交脏数据
- **不可重复读**：同一事务两次查同一条数据不一样
- **幻读**：同一事务两次查询，条数不一样（新增 / 删除）

## 4. MySQL 如何解决幻读

- 快照读：**MVCC 多版本并发控制**
- 当前读：**间隙锁 + 临键锁** 锁住区间防止插入

## 5. InnoDB 三大日志

- **redo log**：崩溃恢复，保证事务持久性
- **undo log**：事务回滚、MVCC 版本链
- **binlog**：归档日志，主从同步、数据恢复

## 6. MVCC 原理，快照读和当前读的区别

- **MVCC（多版本并发控制）**：InnoDB 无锁并发读写的机制，依靠 `undo log` 保存数据历史版本。
- 作用：实现**读写不阻塞**，大幅提升数据库并发能力。
- 两种读取方式：
  - **快照读**：普通 `SELECT` 查询，无锁，读取历史数据快照；
  - **当前读**：`INSERT/UPDATE/DELETE/SELECT ... FOR UPDATE`，主动加行锁，读取最新数据。

## 7. 索引分类

- 主键索引、唯一索引、普通索引、联合索引、全文索引
- 聚簇索引、二级（辅助）索引

## 8. 聚簇索引与非聚簇索引区别

- **聚簇**：叶子存**整行数据**，一张表只有一个
- **非聚簇**：叶子存**主键值**，回表查询

## 9. 联合索引最左匹配原则

查询必须**从最左列开始**，跳过中间列失效

例：索引 (a,b,c) 查 b、c 不走索引

## 10. 索引失效常见场景

- 左右模糊查询 `%xx`、`%xx%`
- 字段隐式类型转换
- or 无全索引、not in、not exists
- order by 字段无索引
- 联合索引不满足最左

## 11. 为什么用 B + 树不用 B 树、哈希

- B + 树**非叶子不存数据**，层高更低，磁盘 IO 少
- 叶子有序链表，**范围查询极强**
- 哈希不支持排序、范围、模糊查询

## 12. InnoDB 索引层高一般几层

千万级数据**3 层**足够，查询极快

## 13. 回表查询是什么

二级索引查到**主键**，再去聚簇索引拿整行数据

## 14. 悲观锁和乐观锁的区别、实现方式以及适用场景

**悲观锁**

- 思想：认为并发冲突一定会发生，操作前先加锁独占数据；
- 实现：基于数据库行排他锁 `SELECT ... FOR UPDATE`；
- 场景：**写多读少、并发冲突高**，如库存扣减、订单、金融交易。

**乐观锁**

- 思想：认为冲突很少发生，全程不加锁，更新时校验冲突；
- 实现：业务层增加 `version` 版本号 / 时间戳做校验；
- 场景：**读多写少、冲突低**，如商品查询、普通信息修改。

## 15. 主键设计原则

- 自增主键最优，**有序插入**减少页分裂
- 禁用 UUID、无序字符串当主键

## 16. MySQL 有哪些锁？行锁和表锁的区别？为什么行锁会降级为表锁？

锁按粒度分为：**全局锁、表级锁、行级锁**；还有意向锁、间隙锁、临键锁等 InnoDB 专属锁。

表锁：粒度大、加锁快、并发低，MyISAM 默认使用；

行锁：InnoDB 专属，粒度小、并发高，只锁定单行数据。

**行锁降级为表锁原因**：

行锁**依赖索引**，当 `where` 条件无索引、索引失效、全表扫描时，InnoDB 无法定位行，行锁退化为整张表的表锁，严重影响并发。

## 17. MyISAM 和 InnoDB 区别

- InnoDB：支持事务、行锁、外键、MVCC，**默认引擎**
- MyISAM：无事务、表锁、快，不支持崩溃安全

## 21：什么是死锁？产生死锁的四个必要条件？如何避免和解决死锁？

**参考答案**

1. **死锁**：两个或多个事务互相持有对方需要的锁，又互相等待对方释放锁，无限阻塞。
2. 四大必要条件：**互斥、请求并保持、不可剥夺、循环等待**。
3. 解决 / 优化方案：
   - 统一事务**加锁顺序**，破坏循环等待；
   - 缩短事务执行时间，尽快提交；
   - 降低事务隔离级别，减少间隙锁；
   - 避免范围查询，减少锁范围扩大；
   - MySQL 会自动检测死锁，回滚代价小的事务。

## 22：线上出现锁等待 / 阻塞，你如何一步步排查？

执行 `SHOW FULL PROCESSLIST`，查看处于 `Locked`、`Updating` 状态的阻塞会话；

查询 `information_schema.innodb_lock_waits`，定位**等待线程、阻塞线程**；

查看 `innodb_trx`，找到长时间未提交的**长事务**与对应 SQL；

执行 `SHOW ENGINE INNODB STATUS`，查看详细锁信息与**死锁日志**；

紧急处理：`KILL 线程ID` 杀掉阻塞会话恢复服务；

根源优化：优化索引、缩短事务、修改 SQL、调整隔离级别。

## 23：MySQL 表设计有哪些规范和原则？

**参考答案**

1. 遵循**三大范式**，业务高并发场景可适度反范式冗余字段；
2. 命名规范：小写 + 下划线，禁用中文、拼音，字段见名知意；
3. 字段类型选型精准：金额用 `DECIMAL`、时间统一 `DATETIME`、状态用 `TINYINT`；
4. 每张表标配：主键、创建时间、更新时间、逻辑删除字段；
5. 主键优先使用自增 `INT/BIGINT`，不用业务字段做主键；
6. 合理建立索引，避免过度索引；大文本、大字段独立分表。

## 24：SQL 窗口函数是什么？和普通 GROUP BY 聚合有什么区别？列举常用窗口函数

**参考答案**

1. **窗口函数**：分组计算但**不合并行数**，每条原始数据都会保留，同时展示统计 / 排名结果。
2. 区别：
   - `GROUP BY`：分组后多行合并为一行，行数减少；
   - 窗口函数：分组后**行数不变**，适合排名、累计统计、行对比。
3. 常用窗口函数：
   - 排名：`ROW_NUMBER()`、`RANK()`、`DENSE_RANK()`
   - 聚合：`SUM/AVG/MAX/MIN`
   - 行取值：`LAG()`、`LEAD()`

## 25: 线上出现慢SQL你如何解决

- 先通过**慢查询日志**和数据库监控，定位出具体的慢 SQL；
- 使用 `EXPLAIN` 分析执行计划，重点查看是否全表扫描、有没有走索引、是否产生临时表和文件排序；
- 分析根因，常见问题是**索引缺失 / 失效、SQL 写法低效、单表数据量过大、长事务锁阻塞**；
- 针对性优化：补充合理索引、改写低效 SQL、大表做分表归档、优化事务与锁；热点查询配合 Redis 缓存减负；
- 优化后复测执行计划与线上指标，同时完善 SQL 规范和监控，避免问题重复出现。

## 26: MySQL支持事务吗

MySQL **支持事务**，但是否支持取决于使用的**存储引擎**。

1. **InnoDB**（MySQL 默认引擎）：完全支持事务，同时具备事务四大特性 ACID、行级锁、崩溃恢复、MVCC，是线上业务主流选择。
2. **MyISAM**：**不支持事务**，也不支持行锁、崩溃安全恢复，仅使用表锁，现在基本不再用于线上业务。

## 27：SQL 注入漏洞成因 & 解决方案

（一）SQL 注入产生原因
根本原因
后台代码将前端用户输入直接字符串拼接进原生 SQL 语句，用户输入被当作 SQL 代码执行，而非普通数据。
本质问题
代码混淆了数据和SQL 指令的边界，攻击者利用单引号、or、and、注释符等特殊符号，破坏原有 SQL 结构，篡改执行逻辑。
```

```
1. 首选：使用 预编译 + 参数化查询（最有效、根本防御）
使用数据库预编译机制，SQL 结构提前固定，用户输入仅作为参数值，不会被解析为 SQL 指令。
主流技术实现：
Java：PreparedStatement、MyBatis #{} （推荐），禁止 ${} 直接拼接；
PHP：PDO、mysqli 预编译；
Python：pymysql 预编译语句。
重点区分：MyBatis 中 #{} 会做参数预编译与转义，防注入；${} 纯字符串拼接，极易引发注入。
2. 输入过滤与正则校验
对前端入参做合法性校验：
账号、手机号、ID 等固定格式字段，用正则严格匹配；
拦截 '、" 、or、and、union、delete、drop、--、# 等关键字与特殊符号；
对特殊字符做转义处理。
3. 数据库账号最小权限原则
业务连接数据库的账号，只分配必要权限：查询业务库仅给 SELECT，下单仅给 INSERT/UPDATE；
禁止使用 root 等高权限账号连接业务程序；
禁止账号拥有 DROP、ALTER、FILE 等高风险权限。
4. 关闭数据库危险配置
关闭 show databases、load_file、into outfile 等文件读写、库查看功能；
关闭 MySQL 远程不必要访问，限制访问 IP。
5. 应用层防护
统一封装 SQL 工具类，禁止手写拼接 SQL；
自定义错误页面，不对外暴露数据库报错信息（报错会泄露表名、字段名）；
部署 Web 应用防火墙（WAF），拦截恶意注入请求；
接口限流、防爬虫，减少攻击探测机会。
6. 其他辅助手段
禁止在 URL、GET 请求中传递 SQL 相关参数，重要参数改用 POST；
定期代码审计，排查代码中直接拼接 SQL 的风险点。

## 28：如何进行数据库优化

数据库优化是一个**全方位、多层次**的体系，我会按照以下**五个维度**逐步优化：

### 1. **SQL 语句优化（最基础、最优先）**

- 定位慢 SQL，使用 `EXPLAIN` 分析执行计划。
- 避免 `select *`，只查需要的字段。
- 避免 `where 1=1`、`or`、`!=`、`not in`、`like '%xx'` 导致索引失效。
- 优化 `join`、`group by`、`order by`，减少文件排序和临时表。
- 分页优化，避免深分页。

### 2. **索引优化（优化效果最明显）**

- 为 `where`、`join`、`order by`、`group by` 字段建立合适索引。
- 联合索引遵循**最左匹配原则**。
- 避免冗余索引、重复索引。
- 禁止在索引列上做函数、运算、类型转换。
- 大表在线建索引，避免锁表。

### 3. **表结构设计优化**

- 选择合适的数据类型：越小越简单越好。
  - 数字用 `int/bigint`，不用字符串存数字。
  - 定长用 `char`，变长用 `varchar`。
  - 金额用 `decimal`，禁止浮点型。
- 大字段（文本、详情）拆分为附表。
- 合理遵循三大范式，高并发场景适度反范式。
- 每张表必须有主键、创建时间、更新时间、逻辑删除。

### 4. **MySQL 配置优化**

- 调整 `innodb_buffer_pool_size`（缓冲池），通常设为物理内存的 50%~70%。
- 调整最大连接数、日志大小、事务隔离级别。
- 关闭不必要的日志、禁用 `query_cache`（MySQL 8.0 已废弃）。
- 调整 `join_buffer`、`sort_buffer` 提升排序与关联效率。

### 5. **架构层面优化（高并发、大数据量必备）**

- **读写分离**：主库写，从库读。
- **分库分表**：水平拆分、垂直拆分，解决单表过大问题。
- **引入缓存**：Redis 缓存热点数据，减轻 DB 压力。
- **冷热数据分离**：历史数据归档，不影响主表性能。
- 使用消息队列削峰，防止数据库被打满。

# Redis

1. **Redis 是什么？**

   是完全开源免费的，高性能**内存键值数据库**，支持多数据类型，支持持久化、集群，常做缓存、计数器、分布式锁。

2. **Reids和memcache的区别**

   1、存储方式 Memecache 把数据全部存在内存之中，断电后会挂掉，数据不能 超过内存大小。 Redis有部份存在硬盘上，这样能保证数据的持久性。

    2、数据支持类型 Memcache 对数据类型支持相对简单。 Redis有复杂的数据类 型。

    3、使用底层模型不同 它们之间底层实现方式 以及与客户端之间通信的应用协议 不一样。 Redis 直接自己构建了 VM 机制 ，因为一般的系统调用系统函数的话， 会浪费一定的时间去移动和请求。

3. **Redis 默认端口、默认数据库数量？**

   默认端口**6379**，默认**16**个数据库，0-15 编号。

4. **Redis 是单线程吗？**

   核心读写命令**单线程**，持久化、后台清理、网络 IO 采用多线程，

   Redis 是单进程单线程的，redis 利用队列技术将并发访问变为串行访问，消 除了传统数据库串行控制的开销。

5. **单线程 Redis 为什么速度快？**

   纯内存操作、IO 多路复用、数据结构高效、无线程锁竞争。

6. **Redis 五大常用数据类型+四种增强？**

   String、List、Hash、Set、ZSet。 Geospatial，HyperLogLog ， Bitmap，Stream

7. **String底层结构和用途**                                                                                                                                                           

   简单动态字符串（SDS）场景：缓存、计数器、分布式 ID、手机号验证码

8. **List 底层结构与用途？**

   底层**双向链表**，有序可重复；做消息队列、浏览记录、时间线。

9. **Hash 适合存储什么数据？**

   **ziplist（压缩列表） + hashtable（字典)**适合存储**对象数据**，如用户信息、商品信息，节省内存。

10. **Set 集合特点与场景？**

    intset 整数集合,hashtable 字典,无序、自动去重；用于好友关系、共同好友、点赞、去重统计。

11. **ZSet 有序集合特点？**

   压缩列表 ziplist + 跳表 skiplist,有序、去重、带分数排序；用于排行榜、积分排名、延时任务。

11. **Redis 两种持久化方式？各自特点**

    **RDB 快照**、**AOF 日志**。

    1、RDBRedis DataBase 持久化方式： 是指用数据集快照的方式半持久化模式) 记录redis 数据库的所有键值对,在某个时间点将数据写入一个临时文件，持久化 结束后，用这个临时文件替换上次持久化的文件，达到数据恢复。

     优点

     1、只有一个文件dump.rdb，方便持久化。

     2、容灾性好，一个文件可以保存到安全的磁盘。

     3、性能最大化，fork 子进程来完成写操作，让主进程继续处理命令，所以是IO 最大化。使用单独子进程来进行持久化，主进程不会进行任何IO操作，保证了redis 的高性能) 

    4.相对于数据集大时，比 AOF的启动效率更高。

     缺点

     1、数据安全性低。RDB是间隔一段时间进行持久化，如果持久化之间redis发生 故障，会发生数据丢失。所以这种方式更适合数据要求不严谨的时候)

     AOFAppend-only file 持久化方式： 是指所有的命令行记录以 redis 命令请 求协议的格式完全持久化存储)保存为aof文件。

     优点

     1、数据安全，aof 持久化可以配置appendfsync 属性，有 always，每进行一次 命令操作就记录到aof文件中一次。

     2、通过 append 模式写文件，即使中途服务器宕机，可以通过redis-check-aof 工具解决数据一致性问题。 

    3、AOF 机制的 rewrite 模式。AOF 文件没被 rewrite 之前（文件过大时会对命令 进行合并重写），可以删除其中的某些命令（比如误操作的flushall）)

     缺点

    1、AOF 文件比 RDB文件大，且恢复速度慢。 

    2、数据集大的时候，比rdb启动效率低。

12. **Reids常见的性能问题和解决方案**                                                                                                                   1、Master 最好不要写内存快照，如果Master写内存快照，save命令调度rdbSave 函数，会阻塞主线程的工作，当快照比较大时对性能影响是非常大的，会间断性 暂停服务 2、如果数据比较重要，某个Slave开启 AOF备份数据，策略设置为每秒同步一 3、为了主从复制的速度和连接的稳定性，Master和 Slave最好在同一个局域网 4、尽量避免在压力很大的主库上增加从 5、主从复制不要用图状结构，用单向链表结构更为稳定，即：Master<-Slave1 <- Slave2 <- Slave3…这样的结构方便解决单点故障问题，实现 Slave 对 Master 的替换。如果Master 挂了，可以立刻启用Slave1 做 Master，其他不变。

13. **Redis 过期键删除策略？**

    **惰性删除 + 定期删除**组合策略。

    1、定时删除:在设置键的过期时间的同时，创建一个定时器timer). 让定时器在键 的过期时间来临时，立即执行对键的删除操作。 

    2、惰性删除:放任键过期不管，但是每次从键空间中获取键时，都检查取得的键是 否过期，如果过期的话，就删除该键;如果没有过期，就返回该键。 

    3、定期删除:每隔一段时间程序就对数据库进行一次检查，删除里面的过期键。至 于要删除多少过期键，以及要检查多少个数据库，则由算法决定。

14. **Redis 内存淘汰常用策略？**

    生产常用 **allkeys-lru**，淘汰最近最少使用的 key。

15. **什么是缓存穿透？怎么解决？**

    查询不存在数据直达数据库；解决：空值缓存、布隆过滤器、接口校验。

16. **什么是缓存击穿？怎么解决？**

    热点 key 过期，大量请求打数据库；解决：永不过期、分布式锁。

17. **什么是缓存雪崩？怎么解决？**

    大量 key 同时过期或 Redis 宕机；解决：过期加随机值、集群高可用、熔断降级。

18. **Redis 事务支持回滚吗？**

    **不支持**，语法错误整体失败，运行出错不会回滚。

19. **Redis 如何实现分布式锁？**

    `set key value nx ex 过期时间`，保证原子性，设置过期防死锁。

20. **主从复制、哨兵、集群作用？**

    主从：数据备份、读写分离；哨兵：自动故障转移；Cluster 集群：分片扩容存海量数据。

21. **生产环境为什么禁用 keys \*？**                                                                                                                            遍历所有 key 阻塞主线程，大数据量会卡死 Redis，线上用 scan 迭代遍历。

22. **scan如何遍历的**

    AN 采用**游标分批迭代**方式，首次游标为 0，每次执行返回新游标与部分 key，开发者持续使用新游标遍历，直到再次返回游标 0 代表遍历完成。它非阻塞遍历，不会阻塞 Redis 主线程，解决 keys * 卡顿问题，适合线上生产环境使用。

Redis同步机制                                                                                                                                                 答：Redis 可以使用主从同步，从从同步。第一次同步时，主节点做一次bgsave， 并同时将后续修改操作记录到内存buffer，待完成后将 rdb文件全量同步到复制 节点，复制节点接受完成后将rdb镜像加载到内存。加载完成后，再通知主节点 将期间修改的操作记录同步到复制节点进行重放就完成了同步过程。

25. Jedis和redission的区别                                                                                                                                   Jedis 是 Redis 的 Java 实现的客户端，其 API 提供了比较全面的 Redis 命令 的支持；Redisson 实现了分布式和可扩展的 Java数据结构，和 Jedis 相比，功能 较为简单，不支持字符串操作，不支持排序、事务、管道、分区等Redis特性。 Redisson 的宗旨是促进使用者对 Redis 的关注分离，从而让使用者能够将精力更 集中地放在处理业务逻辑上。

26. Redis 事务                                                                                                                                                          Redis 事务核心：**批量命令打包执行、一次性顺序执行、不保证原子性（不回滚）**，只有 5 个核心命令，直接记：5 个事务核心命令

    1. **MULTI**

       开启一个事务，之后的命令**不会立即执行**，而是加入事务队列。

    2. **EXEC**

       执行事务队列里的**所有命令**，一旦执行，事务结束。

    3. **DISCARD**

       放弃事务，**清空事务队列**，取消本次事务。

    4. **WATCH key [key ...]**

       **监视一个 / 多个 key**，如果事务执行前 key 被修改，**事务会被打断、不执行**（实现乐观锁）。

    5. **UNWATCH**

       取消对所有 key 的监视，释放 WATCH 锁定。

27. Redis如何进行内存优化                                                                                                                                      尽可能使用散列表（hashes），散列表（是说散列表里面存储的数少）使用 的内存非常小，所以你应该尽可能的将你的数据模型抽象到一个散列表里面。比 如你的web系统中有一个用户对象，不要为这个用户的名称，姓氏，邮箱，密码 设置单独的key,而是应该把这个用户的所有信息存储到一张散列表里面

28. Redis适合场景                                                                                                                                                     **热点数据缓存**

    缓存接口、首页、商品、用户信息、字典数据，减轻数据库压力，提升访问速度。

    **会话 / 令牌存储**

    存储登录 Session、Token、验证码，过期特性天然适配有效期控制。

    **计数器 & 限流**

    文章阅读量、点赞数、接口 QPS 限流、防刷，利用原子命令实现。

    **排行榜**

    借助**有序集合 (ZSet)** 做销量、积分、热度实时排行。

29. Redis 如何实现分布式锁                                                                                                                                用 `SET key value NX EX` 原子命令加锁。

    必须带**过期时间**，防止死锁。

    value 使用**唯一 ID**，避免误删别人锁。

    解锁必须用 **Lua 脚本**保证原子性。

    生产直接用 **Redisson**，自带看门狗续期 + 红锁
