# JDK 生产环境检测 & 分析工具

> 生产环境核心约束：**低开销，尽量不重启、不侵入业务，优先使用 JDK 自带工具，尽量少装第三方软件**。 分为四大类：JDK 内置命令行工具、JFR 飞行记录（生产首选）、外部诊断工具、线上问题分析思路。

## 一、JDK 自带工具

（JDK bin 目录，无需额外安装）

> 生产服务器只需要 JDK，不需要装 JMC 图形界面。

### 1. jps —— Java 进程状态工具

快速拿到 Java 进程 PID，一切诊断的起点

```
jps -l       # 显示pid + 主类全限定名/jar包名
jps -v       # 查看JVM启动参数(Xmx,Xms等)
```

### 2. jcmd（生产最强全能命令，优先用 jcmd，替代 jstack/jmap/jinfo）

> 集合 jstack、jmap、jinfo，开销可控，**推荐优先使用 jcmd，而不是旧版 jmap -dump:live**

```
# 查看JVM启动参数
jcmd <pid> VM.CommandLine

# 打印线程栈（等价jstack），排查死锁、线程阻塞、线程泄露
jcmd <pid> Thread.print

# 打印堆配置（新生代老年代大小、GC策略）
jcmd <pid> GC.heap_info

# 堆dump，生成hprof文件（发生OOM时导出堆快照）
jcmd <pid> GC.heap_dump -all  /data/dump/heap.hprof

# 触发一次Full GC（谨慎！生产不要随便执行）
jcmd <pid> GC.run
```

### 3. jstack（线程快照）

```
jstack <pid> > thread.txt
```

用途：死锁、线程阻塞、线程池耗尽、大量 WAITING/BLOCKED 线程。

### 4. jmap（堆内存）

```
# 导出堆快照
jmap -dump:format=b,file=heap.hprof <pid>
```

> ⚠️注意：`jmap‑dump`会 STW，生产尽量业务低峰执行；优先用 jcmd。

### 5. jstat —— 运行期统计监控（实时看 GC、编译）

持续观测 GC，不需要停应用

```
# GC统计，每500ms输出一次
jstat -gc <pid> 500
```

重点看列：

- S0C S1C EC OC：各个代容量
- YGC YGCT：YoungGC 次数、总耗时
- FGC FGCT：FullGC 次数、总耗时

> 如果 YGC 频繁、FGCT 持续上涨，说明内存压力大。

## 二、JFR Java Flight Recorder【⭐生产环境首选】

> **极低开销，生产安全，开销 < 2‑5%**，不需要停机，可以录制 CPU 采样、GC、锁、JDBC、IO、线程事件，输出`.jfr`文件，拿到本地 JMC 分析。

### 两种开启方式

1）**运行时动态开启，无需重启服务（最推荐）**

```
# 开启录制，120秒，profile完整配置，输出文件
jcmd <pid> JFR.start name=rec filename=/data/test.jfr duration=120s settings=profile

# 手动停止录制（不用duration就用这个）
jcmd <pid> JFR.stop name=rec
```

参数说明：

- `settings=profile`：完整性能采集；`settings=default`轻量采集，开销更低。

2）JVM 启动参数预先开启（程序启动就开启）

```
-XX:+FlightRecorder -XX:StartFlightRecording=filename=app.jfr,duration=300s,settings=profile
```

拿到`.jfr`下载到本地，用 JDK Mission Control (JMC) 图形化分析：

- GC 停顿、CPU 热点方法、锁竞争、线程阻塞、JDBC 慢 SQL、SocketIO、内存分配。

> 优点：比 jstack/jmap 更全面，不是某一瞬间快照，是一段时间的运行录像。

## 三、OOM 

自动堆转储（故障发生自动 dump，不用人工干预）

JVM 启动参数配置，发生 OOM 自动输出堆快照，不用人在场：

```
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dump
```

当程序发生 OOM 崩溃，自动生成 hprof 堆文件，事后下载分析内存泄漏。

> 线上 attach 到 Java 进程，不用重启，命令行看方法耗时、线程、内存、异常。 适合临时应急排查问题；注意：生产不要长时间挂着 Arthas。

## 六、操作系统层诊断（Linux）

JVM 的很多"假故障"根因在系统层：swap 换页、磁盘 IO 打满、CPU 被别的进程抢占、OOM Killer。这些命令全部系统自带，零安装：

```bash
top -Hp <pid>        # 看进程内每个线程的 CPU（定位飙 CPU 的 Java 线程）
vmstat 1             # si/so（swap 换入换出）、cs（上下文切换）、r（就绪队列）
pidstat -p <pid> -t 1 # 线程级 CPU/内存趋势（sysstat 包）
iostat -x 1          # 磁盘 IO，await 高说明存储瓶颈
free -m              # 物理内存与 swap 使用
dmesg -T | grep -i -E "oom|kill"   # 判断进程是否被 OOM Killer 干掉
pmap -x <pid> | sort -k3 -rn | head # 进程内存映射，看 RSS 大头
lsof -p <pid>        # 进程打开的文件/连接数（fd 泄漏）
ss -s                # 连接状态汇总
```

典型对应关系：

| 系统层现象                  | JVM 层表现                          |
| --------------------------- | ----------------------------------- |
| si/so 长期非 0（swap 活跃） | GC 停顿时间剧烈抖动                 |
| iowait 高、磁盘 util 100%   | GC 日志/dump 写入卡顿，接口整体变慢 |
| dmesg 有 oom-killer 记录    | 进程直接消失，无 OOM 日志、无 dump  |
| cs 上下文切换异常高         | 线程数过多，锁竞争激烈              |

> 内存换页是低延迟服务大敌：数据库、JVM 建议部署时 `vm.swappiness=1` 或直接关闭 swap。

## 七、JDK 进阶诊断能力

### 1. jinfo —— 查看与运行期修改参数

```
jinfo -flags <pid>                 # 全部 JVM 参数
jinfo -flag MaxHeapSize <pid>      # 单个参数当前值
jinfo -flag +HeapDumpOnOutOfMemoryError <pid>   # 运行期开启（manageable 参数）
```

JDK 9+ 出于安全考虑只有少量 manageable 参数支持运行期修改（如 HeapDump 系列、Min/MaxHeapFreeRatio）。

### 2. jhsdb —— JDK 9+ 诊断后端（jstack 卡死时的替代品）

```
jhsdb jmap --heap --pid <pid>                          # 堆配置与占用概况
jhsdb jstack --pid <pid>                               # 线程栈
jhsdb jmap --binaryheap --pid <pid> --file /data/dump/heap.hprof   # 堆 dump
```

### 3. jcmd 补充命令

```
jcmd <pid> VM.flags                   # 当前生效参数及来源（命令行/默认值/ergonomics）
jcmd <pid> VM.uptime                  # 运行时长
jcmd <pid> GC.class_histogram         # 对象直方图（等价 jmap -histo）
jcmd <pid> Thread.print -l            # 线程栈，含 native 栈帧与锁信息
jcmd <pid> VM.native_memory summary   # 配合 NMT 看堆外内存
jcmd <pid> GC.heap_dump /data/dump/heap.hprof   # 默认只导存活对象（导出前触发一次 Full GC）
```

> `GC.heap_dump` 不加 `-all` 只导可达对象；排查泄漏通常存活对象就够了，而且文件更小。

### 4. 对象增长对比法（不导 dump 快速定位泄漏类）

```
jmap -histo <pid> | head -30 > /tmp/h1.txt
# 等待 10~30 分钟（业务正常运行）
jmap -histo <pid> | head -30 > /tmp/h2.txt
diff /tmp/h1.txt /tmp/h2.txt
```

某个类的实例数与字节数持续单调上涨，基本就是泄漏点。注意：`:live` 变体会先触发 Full GC，生产慎用；普通 `-histo` 只有短暂 STW，开销远小于 dump。

### 5. NMT（Native Memory Tracking）—— 堆外内存定位

堆没满但 RSS 持续涨（容器 OOMKilled 高发场景），用 NMT 看 JVM 内存都花在哪：

```
# 启动参数（需重启生效，开销约 5% 以内，排查期开启即可）
-XX:NativeMemoryTracking=summary

jcmd <pid> VM.native_memory summary
jcmd <pid> VM.native_memory baseline       # 打基线
# 运行一段时间后看增量
jcmd <pid> VM.native_memory summary.diff
```

分类含义：`Thread`（线程栈×线程数）、`Class`（元空间）、`Code`（JIT 代码缓存）、`GC`（卡表/region 元数据）、`Internal`（**DirectByteBuffer 直接内存计入此项**）。

### 6. Safepoint 日志 —— 停顿了但不是 GC 的锅

GC 日志显示停顿很正常，但接口依然周期性卡顿，查 safepoint：

```
# JDK 9+
-Xlog:safepoint:file=/data/logs/safepoint.log:time,uptime:filecount=3,filesize=20m
```

`Reaching safepoint` 耗时长说明有线程长时间跑在不可打断的代码里（大结果集循环、不加 safepoint poll 的 native/JIT 代码），STW 等它等到超时。

## 八、GC 日志（生产必开的黑匣子）

开销 < 1%，生产环境建议**永远常开**——出了问题回溯有据可查，平时不看而已。

JDK 9+（统一日志）：

```
-Xlog:gc*:file=/data/logs/gc-%t.log:time,uptime,level,tags:filecount=5,filesize=50m
```

JDK 8：

```
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/data/logs/gc.log
-XX:+UseGCLogFileRotation -XX:NumberOfGCLogFiles=5 -XX:GCLogFileSize=50M
```

配合查看实时 GC 原因（LGCC/GCC 列会直接写明触发原因）：

```
jstat -gccause <pid> 1000
```

分析工具（日志文件拿到本地/上传在线分析）：

| 工具                | 形态         | 用途                                                         |
| ------------------- | ------------ | ------------------------------------------------------------ |
| GCeasy（gceasy.io） | 在线上传     | 自动出报告：停顿分布、吞吐率、各代回收效率、内存泄漏趋势预判 |
| GCViewer            | 本地开源 jar | 同上，数据不出内网时用                                       |

## 十、容器与 Kubernetes 专项

### 1. JVM 容器感知参数（JDK 8u191+ / JDK 10+ 默认开启感知）

```
-XX:InitialRAMPercentage=50.0   # 未显式设置 -Xmx/-Xms 时生效
-XX:MaxRAMPercentage=75.0       # 堆 = 容器内存 limit × 该比例
-XX:ActiveProcessorCount=4      # CPU limit < 1 核时修正 GC/JIT 并行度
-XX:+ExitOnOutOfMemoryError     # OOM 立即退出，交给 K8s 重启，避免半死不活
```

CPU limit 给 0.5 核这类配置会让 JVM 按单核算并行线程数，GC 严重退化；`ActiveProcessorCount` 显式指定更稳。

### 2. K8s 排障命令

```bash
kubectl top pod <pod> -n <ns>              # 实时 CPU/内存
kubectl describe pod <pod>                 # 看 Last State: OOMKilled、Restart Count、Events
kubectl exec -it <pod> -n <ns> -- jcmd 1 GC.heap_info
kubectl cp <ns>/<pod>:/data/dump/heap.hprof ./heap.hprof
```

退出码 **137**（128+SIGKILL）= OOM Killer 或 liveness probe 强杀。

> 容器内 dump 注意：hprof 体积 ≈ 堆大小，直接写容器可写层会撑爆 ephemeral storage 导致 Pod 被驱逐，务必落到挂载盘或 emptyDir（sizeLimit 要够大）。

### 3. 云原生 JVM 配套工具

| 工具                              | 解决什么                                                     |
| --------------------------------- | ------------------------------------------------------------ |
| Jolokia                           | 把 JMX 暴露为 HTTP/JSON，Prometheus 无需开 JMX 端口直接抓    |
| Cryostat（红帽开源）              | K8s 内自动发现所有 JVM，集中管理/定时触发 JFR 录制，Web UI 下载，不改一行代码 |
| Micrometer + Spring Boot Actuator | `/actuator/metrics/jvm.*` 暴露指标，Spring 系零成本接 Prometheus |
| jattach                           | 单文件约 100KB 静态二进制，无 JDK/JRE 的精简镜像（distroless/Alpine）里也能执行 heapdump、threaddump、jcmd |

## 十一、APM 与持续剖析

JMX/GC 指标监控只能回答"现在多少"，APM 与持续剖析回答"慢在哪一段、哪个方法"：

| 工具                          | 类别              | 生产适用点                                                   |
| ----------------------------- | ----------------- | ------------------------------------------------------------ |
| Apache SkyWalking             | APM（Java Agent） | 链路追踪 + JVM 指标 + 告警一体，无侵入字节码增强，中文生态好 |
| Pinpoint                      | APM               | 链路可视化直观，适合大流量微服务拓扑分析                     |
| Elastic APM                   | APM               | 与 ELK / Kibana 联动                                         |
| OpenTelemetry + Jaeger/Zipkin | 链路标准          | 厂商中立，云原生事实标准，避免 Agent 绑定                    |
| Grafana Pyroscope             | 持续剖析          | "永远在线的 profiler"，全天候火焰图，支持 JFR 数据源；出问题回看任意历史时刻的 CPU/内存热点 |
| eBPF（bpftrace / bcc）        | 系统级            | 零侵入进程，直接看 syscall、内核延迟、off-CPU；适合有内核排障能力的团队 |

持续剖析 = 把 JFR 的"事后取证"变成"全程录像"：Pyroscope 常驻采集，周一的接口抖动周四还能回看当时的火焰图。JDK 14+ 还可用 JFR Event Streaming（`jdk.jfr.consumer.RecordingStream`）把 JFR 事件实时消费进自研监控。

## 十二、JVM 调优实践

### 1. 先定目标，再看数据

延迟（P99 GC 停顿）、吞吐（GC 时间占比）、资源占用（内存）三者最多同时优化两个。调优前必须有基线：GC 日志 + 监控指标至少跑一周，没有数据的调参是玄学。

### 2. GC 选型

| 收集器     | 版本                          | 典型停顿           | 适用场景                      |
| ---------- | ----------------------------- | ------------------ | ----------------------------- |
| Parallel   | JDK 8 默认                    | Full GC 秒级       | 离线批处理、吞吐优先          |
| CMS        | JDK 8（JDK 14 已移除）        | 百毫秒             | 存量老系统维护                |
| G1         | JDK 9+ 默认                   | 可设目标，几十毫秒 | 在线服务通用，4G~32G 堆       |
| ZGC        | JDK 15+ 正式；JDK 21 支持分代 | < 1ms              | 低延迟大堆（交易、网关、8G+） |
| Shenandoah | 部分发行版（Corretto 等）     | 毫秒级             | ZGC 的替代选项                |

### 3. 通用原则

- `-Xms` = `-Xmx`，避免堆动态伸缩带来的抖动
- 堆不超过容器/物理内存的 75%，剩下留给元空间、线程栈、直接内存、GC 元数据和 page cache
- G1 下**不要**手动设置 `-Xmn`、`SurvivorRatio`，交给自适应
- 元空间设上限兜底类加载泄漏，直接内存设上限管住 Netty/NIO
- 禁用显式 GC 前先想清楚：NIO 直接内存回收依赖 `System.gc()`，用 `-XX:+ExplicitGCInvokesConcurrent`（CMS/G1 下生效）比一刀切的 `DisableExplicitGC` 安全
- 绝大多数"GC 问题"本质是**分配速率问题**：先 JFR 看分配热点（大集合、字符串拼接、装箱），代码层面的收益远大于调参数

### 4. G1 关键参数

```
-XX:MaxGCPauseMillis=200            # 软目标，驱动 region 回收调度
-XX:InitiatingHeapOccupancyPercent=45   # 并发标记触发阈值（默认45）
-XX:G1HeapRegionSize=8m             # 大对象多时调大（humongous 判定 = region/2）
-XX:ConcGCThreads=2                 # 并发标记线程，约 1/4 核数
```

G1 排障信号（看 GC 日志）：`humongous allocation` 频繁 → region 调大或拆大对象；`to-space exhausted`（Evacuation Failure）→ 堆不够或晋升过快。

### 5. ZGC 要点

```
-XX:+UseZGC -XX:+ZGenerational   # JDK 21+；分代版大幅降低内存开销
```

停顿与堆大小解耦（< 1ms 不随堆增长），代价是多映射/转发表的额外内存，堆 8G 以下收益不明显。

### 6. 常见 Full GC 根因速查

| 现象                   | 根因                                          | 处理                                                         |
| ---------------------- | --------------------------------------------- | ------------------------------------------------------------ |
| 老年代持续上涨至打满   | 内存泄漏或堆不足                              | dump + MAT；临时扩堆续命                                     |
| 元空间 M 区打满        | 动态类泄漏（Groovy 脚本、CGLib 代理、热部署） | `-XX:MaxMetaspaceSize` 兜底 + MAT 类加载器分析               |
| 每小时整点一次 Full GC | RMI 分布式 GC 定时调用 `System.gc()`          | `-Dsun.rmi.dgc.server.gcInterval=9223372036854775807` 或禁显式 GC |
| to-space exhausted     | 混合回收速度跟不上晋升                        | 扩堆、降低分配速率、检查 IHOP                                |
| humongous 频繁         | 大数组/大报文一次分配                         | region 调大或业务侧分片                                      |

### 7. 堆外各区域边界参数

```
-Xss512k                          # 线程数上万时降栈大小（64位默认1MB）
-XX:MaxMetaspaceSize=512m
-XX:ReservedCodeCacheSize=256m    # JIT 代码缓存（分层编译默认240m）
-XX:MaxDirectMemorySize=1g        # Netty 等 NIO 直接内存上限
```

## 十三、生产 JVM 参数模板

可直接复制修改的"防事故底线配置"（G1 + JDK 11/17，注释按需删）：

```bash
# ---- 内存 ----
-Xms4g -Xmx4g
-XX:MaxMetaspaceSize=512m
```

## 十四、线上故障排查手册

生产环境排障按问题类型选工具，核心原则是“服务器只采集、本地做分析”：

### 1. CPU 100%

```
top -Hp <pid>                     # 找 CPU 最高的线程 TID
printf "%x\n" <TID>               # 转 16 进制
jstack <pid> | grep -A 30 "nid=0x<hex>"
```

- 线程是 `GC Thread#` / `G1 Conc` → 不是业务问题，转去查内存
- 线程是 `C2 CompilerThread` → JIT 预热期，观察即可
- 业务线程 → JFR 采 120s profile 或 async-profiler 出火焰图定位方法：

```
# async-profiler（Linux）
./asprof -d 30 -e cpu  -f /tmp/cpu.html  <pid>   # CPU 火焰图
./asprof -d 30 -e alloc -f /tmp/alloc.html <pid> # 分配火焰图
./asprof -d 30 -e lock -f /tmp/lock.html <pid>   # 锁竞争
```

### 2. OOM / 内存泄漏

1. 拿 hprof（OOM 自动 dump，或 `jcmd GC.heap_dump`）
2. MAT 打开 → **Leak Suspects 报告** → 支配树（Dominator Tree）找 Retained Heap 最大的对象
3. 高频元凶：无上限缓存（本地 Map 当缓存）、线程池 + ThreadLocal 不清理、大结果集一次 `select *` 全量加载、监听器/连接未反注册

### 3. Full GC 频繁

按第十二节根因表排查；`jstat -gccause <pid> 1000` 的 LGCC 列直接给原因；GC 日志丢 GCeasy 看整体趋势。

### 4. 容器 OOMKilled（退出码 137）

JVM 实际内存 = 堆 + 元空间 + 代码缓存 + 线程栈×线程数 + 直接内存 + GC 数据结构。**容器 limit 只按堆大小配必然被杀**。处理：`MaxRAMPercentage` 控堆占比 ≤ 75%，NMT + `pmap` 核对真实 RSS，Netty 服务检查 `MaxDirectMemorySize`。

### 5. 死锁 / 线程池耗尽

`jcmd <pid> Thread.print`，死锁会直接打印 `Found one Java-level deadlock`。**连采 3~5 次、间隔 10 秒**才有对比价值；拿不准就丢给 fastThread 自动分析。线程池耗尽看 `RUNNABLE` 少、`WAITING (on object monitor)` 堆积在哪把锁上。

### 6. 接口偶发慢

APM trace 先分段（DB / 下游 RPC / 自身耗时），自身耗时高再 JFR 录 2 分钟看三件事：Java Monitor Blocked（锁竞争）、Socket Read（慢 IO）、Allocation Rate（分配压力导致的 GC 连带）。

### 7. jstack / jcmd 全部 attach 不上

进程大概率卡在 safepoint，attach 通道本身也需要 safepoint。Linux 兜底：

```
gcore -o /data/core <pid>         # 导 core 文件（进程短暂暂停，低峰执行）
jhsdb jstack --core /data/core.<pid> --exe $JAVA_HOME/bin/java
```

JDK 8 可用 `jstack -F <pid>` 强制导出。

# ⚠️生产环境重要注意事项

1. `jmap‑dump`、手动 FullGC 会 STW，尽量低峰执行；优先 JFR，STW 极少。
2. JFR 的 profile 模式开销可控，但不建议持续几小时不间断录制；一般录制 30‑120s 抓现场。
3. hprof 堆文件体积很大，注意服务器磁盘空间。
4. Arthas 适合临时排查，排查完退出，不要常驻生产进程。
5. Windows 服务器生产几乎不用；绝大多数 Java 生产环境为 Linux。
6. 不要随意在线上执行 `jmap -dump:live`、`jcmd GC.run`（手动 FullGC），STW，尽量业务低峰；
7. hprof 体积巨大，导出后及时转移，避免磁盘打满；
8. JFR 录制建议 30‑120s，不要连续录制几小时；
9. Arthas 用于临时排查，问题定位完关闭，不要常驻进程。

# 案例

## 一、CPU 过高完整排查步骤（Linux 生产环境）

> 现象：服务器 CPU 负载高，Java 进程占用大量 CPU，接口响应慢、超时。 核心思路：找到占用 CPU 的 Java 线程 → 定位对应代码。

### 方案 1：JFR（优先推荐，生产低开销）

1. 拿到 Java 进程 PID：`jps -l`
2. 开启 JFR 录制 30‑120 秒，抓 CPU 采样：

```
jcmd <pid> JFR.start name=cpu_record filename=/tmp/cpu.jfr duration=60s settings=profile
```

1. 录制结束，把 

   ```
   cpu.jfr
   ```

    下载到本地，用 JMC 打开

   - 进入「方法概要分析」，按 CPU 占比排序，直接看到消耗 CPU 最高的方法。
   - 同时可以查看线程、锁、GC 事件，判断是业务代码、GC 疯狂执行、还是锁自旋导致 CPU 高。

> 优点：完整记录一段时间，不是瞬时快照，可以区分是用户代码、VM、GC 线程消耗 CPU。

### 方案 2：传统命令行方式（无 JFR 时应急）

1. 找到 Java 进程 PID

```
top -H -p <java_pid>
```

`‑H` 显示线程，记下高 CPU 的**线程 LWP 号（十进制）**。

1. 将线程 ID 转为 16 进制（printf 转换）

```
printf "%x\n" <线程LWP>
```

1. 输出线程栈

```
jcmd <pid> Thread.print > thread.txt
```

1. 在 `thread.txt` 搜索上面得到的十六进制 nid，找到对应线程栈，定位正在跑的业务方法。

### 方案 3：Arthas 应急排查

```
java -jar arthas-boot.jar
# 看CPU占比最高线程
thread -n 10
# 采样生成火焰图
profiler start --cpu
# 采集一段时间后停止输出html火焰图
profiler stop --file /tmp/cpu-flame.html
```

### CPU 高常见根因

1. 业务死循环、复杂算法、大量字符串处理、频繁序列化反序列化；
2. GC 线程占用 CPU：频繁 YGC / FullGC，大量对象创建销毁；
3. 锁自旋、无限重试；
4. 正则表达式回溯卡死 CPU。

> 区分：看是**应用线程**CPU 高，还是**GC 线程**CPU 高。如果 GC 线程 CPU 高，优先排查内存问题。

## 二、OOM & 内存泄漏排查完整步骤

> OOM 常见报错：`java.lang.OutOfMemoryError: Java heap space` 内存泄漏：对象不再使用，但无法被 GC 回收，堆内存持续上涨，最终 OOM。

### 步骤 1：提前准备（线上预先配置，故障自动留现场）

JVM 启动参数，发生 OOM 自动 dump 堆快照，**不需要人工干预**：

```
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dump
```

OOM 发生时，自动生成 `xxx.hprof` 文件。

> ⚠️注意：hprof 文件很大，确保磁盘有足够空间。

### 步骤 2：故障发生后，收集现场信息

1. 查看 GC 运行状态，确认内存趋势

```
jstat -gc <pid> 1000
```

观察：老年代 OC/OU 持续上涨，FullGC 频繁，回收后内存几乎不下降，大概率内存泄漏。

1. 两种获取堆 dump 的方式

- 方式 A：OOM 自动生成 hprof（推荐，故障瞬间现场）
- 方式 B：还没崩溃，想要手动导出（**业务低峰执行，会 STW**）

```
jcmd <pid> GC.heap_dump -all /data/dump/heap.hprof
```

> 不要频繁手动 dump，大堆会造成长时间 STW。

### 步骤 3：下载 hprof 到本地工具分析

工具：**Eclipse MAT（Memory Analyzer Tool）** 操作流程：

1. MAT 打开 hprof 文件；
2. 选择【Leak Suspects Report】泄漏嫌疑报告；
3. 重点看：
   - 大对象、占用内存最多的对象；
   - 对象引用链：**谁持有这个对象，导致无法 GC**；
   - 对比快照：多次 dump 对比，看哪些对象在持续增长。

**MAT 重点关注点**

1. 哪个类的对象实例数量疯狂增长；
2. GC Roots 引用链，找到是谁 holds 住对象不释放；
3. 区分：是**内存泄漏**（不该存活的对象被持有），还是**内存溢出**（确实需要这么大内存，Xmx 设置太小）。

### 步骤 4：辅助使用 JFR 验证

JFR 开启录制，查看**对象分配采样**：

```
jcmd <pid> JFR.start name=heap filename=/tmp/heap.jfr duration=120s settings=profile
```

JMC 打开 jfr，查看「对象统计」，看短时间哪些对象大量创建，定位分配对象的方法。

### 内存泄漏常见原因

1. 静态集合（static List/Map）不断 add 对象，没有清理；
2. 线程池、ThreadLocal 没有 remove，线程复用导致对象堆积；
3. 缓存没有设置过期 / 淘汰策略，无限膨胀；
4. 第三方框架 bug、未关闭资源，长生命周期持有短生命周期对象；
5. 大对象频繁分配。

> 区分场景：
>
> - OOM：内存不够用，调大 Xmx 可以临时缓解，但不能解决泄漏；
> - 内存泄漏：调大 Xmx 只是延迟 OOM，最终依然会崩。

## 三、生产实战案例集

> 九个案例覆盖：CPU 类（案例 1、2）、堆内存类（案例 3、4）、堆外/元空间类（案例 5、6）、资源耗尽类（案例 7）、中间件与链路类（案例 8、9）。
> 每个案例结构：**背景 → 故障现象 → 排查过程 → 根因 → 解决 → 后续警惕**。

### 案例 1：正则灾难性回溯，单台机器 CPU 100%

**背景**：营销短信平台，SpringBoot 2.7 / JDK17，6 台 8C8G 实例，手机号批量导入校验接口。

**故障现象**

周五 16:20 告警：`sms-gateway-03` CPU 98%，接口 P99 从 80ms 涨到 12s，其余 5 台完全正常。摘除该节点流量后，其余节点恢复正常——问题锁定在这台机器正在处理的请求上。

**排查过程**

```
jps -l                          # 拿到 pid
top -H -p <pid>                 # 前 4 个线程 CPU 均 99%
```

关键观察：线程名是 `http-nio-8080-exec-3` —— **是 Tomcat 业务线程，不是 GC 线程**，直接排除内存问题，转入代码定位：

```
printf "%x\n" 28471             # 线程 LWP 转 16 进制 → 6f57
jcmd <pid> Thread.print > /tmp/t1.txt
grep -A 20 "nid=0x6f57" /tmp/t1.txt
```

栈顶反复出现：

```
at java.util.regex.Pattern$Curly.match(Pattern.java:...)
at java.util.regex.Pattern$GroupCurly.match(...)
```

间隔 10 秒连抓 3 次线程栈，同一个线程仍然停在同一个 matcher 的 match 里——不是瞬时慢，是**卡死在正则回溯**。

**根因**

手机号校验正则使用了嵌套量词的写法（示意）：

```java
// 反例：(\d|\d\d)+ 对超长数字串产生指数级回溯组合
private static final Pattern MOBILE = Pattern.compile("^(\\d|\\d\\d)+$");
```

当天下午运营导入了脏数据：一批 30 位的纯数字串被送进校验。嵌套量词在匹配失败时会枚举所有分组组合，30 位输入的回溯次数是天文数字，单次 match 卡住分钟级，4 个线程同时中招，CPU 打满。

**解决**

- 止血：LB 摘除 + 重启该实例；
- 根治：正则改为无回溯歧义的号段写法 `^1[3-9]\d{9}$`；入口先做长度预判（`length != 11` 直接拒绝，不进正则）；Pattern 全部 `static final` 预编译（顺带消除了每次编译的分配开销）。

**后续警惕**

- 对外输入**先限长再校验**，长度预判是最便宜的前置防线；
- 含嵌套量词（`(a+)+`、`(\d|\d\d)+`）的正则，上线前必须用超长畸形输入做回溯测试；
- 告警补一项：**单线程 CPU 持续 100% 超过 1 分钟**——普通 CPU 告警只看整机均值，单线程卡死时均值可能只有 30%，完全发现不了。

### 案例 2：GC 线程吃满 CPU，根因是每秒 900MB 的对象分配

**背景**：订单服务，8C16G，堆 8G + G1，JDK17，大促前全链路压测。

**故障现象**

压测到 3000 QPS 时整机 CPU 85% 但 RT 正常；加压到 4000 QPS 后 YGC 每秒 2 次，P99 从 120ms 抖到 600ms，CPU 逼近 100%。

**排查过程**

1. `top -Hp <pid>`：CPU 最高的前 8 个线程全是 `GC Thread#N` 和 `G1 Conc`——**GC 线程吃掉了 CPU**，问题从"代码慢"转为"内存分配过快"；
2. `jstat -gc <pid> 500`：Eden 区（E）每 500ms 清空一次，YGC 计数肉眼可见地跳，FGC = 0——新生代被打爆，老年代健康；
3. 按 CPU 排查流程的方案 1 开 JFR：

```
jcmd <pid> JFR.start name=alloc filename=/tmp/alloc.jfr duration=60s settings=profile
```

JMC 打开，看「对象分配（TLAB Allocation）」视图：**一个日志脱敏方法占了 62% 的分配量**，每秒分配约 900MB 的 `char[]`、`String`、`Pattern` 对象。

**根因**

脱敏工具类在循环里对每个字段调用：

```java
// 反例：replaceAll 每次调用内部都 Pattern.compile 一次
for (OrderField f : fields) {
    f.setValue(f.getValue().replaceAll("(1[3-9]\\d)\\d{4}(\\d{4})", "$1****$2"));
}
```

一单 40 个字段 × 4000 QPS = **每秒 16 万次正则编译**，全是短命对象，分配速率直接把新生代打穿，GC 线程疲于奔命。

**解决**

Pattern 提为 `static final` 预编译，循环内只做 matcher 匹配；高频字段增加脱敏结果缓存。改完压测：分配速率从 900MB/s 降到 110MB/s，YGC 从每秒 2 次降到 15 秒 1 次，同 QPS 下 CPU 下降 20 个百分点。

**后续警惕**

- CPU 高的**第一件事永远是区分 GC 线程还是业务线程**，方向错了后面全是弯路；
- `String.replaceAll` / `split` 在热路径上等于隐形的 `Pattern.compile`，代码扫描要重点查；
- G1 时代多数"GC 问题"本质是**分配速率问题**，JFR 的分配采样视图是定位它的最快路径；
- 监控加一项：JVM 分配速率（MB/s）——它比 GC 次数更早暴露问题。

### 案例 3：static ConcurrentHashMap 只进不出，两周后必然 OOM

**背景**：支付回调服务，4C8G 堆 4G，JDK17，已配置 `-XX:+HeapDumpOnOutOfMemoryError`。

**故障现象**

上线后第 13 天凌晨触发 `java.lang.OutOfMemoryError: Java heap space`，自动重启后第 14 天同一时间再次 OOM——**周期性、可复现**。

**排查过程**

1. dump 文件已自动生成：`/data/dump/java_pid1.hprof`（2.9G），下载到本地；
2. MAT 打开，Leak Suspects 报告第一条：**一个 ConcurrentHashMap 占了堆的 71%（2.9G），约 4700 万个 Entry**，key 是 String（交易流水号），value 是 `CallbackTask` 对象；
3. 点开引用链：`com.pay.callback.PayCallbackService.retryTaskMap` ← **GC Root（类静态字段）**，铁证。

**根因**

```java
// 反例：重试暂存表，只有 put 没有 remove
private static final ConcurrentHashMap<String, CallbackTask> retryTaskMap = new ConcurrentHashMap<>();

public void onCallback(CallbackTask task) {
    if (execute(task)) {
        updateDbStatus(task, SUCCESS);   // 成功只更新 DB
    } else {
        retryTaskMap.put(task.getTxNo(), task);  // 失败的也只 put
    }
}
```

回调失败重试任务放 static Map 暂存，等定时任务扫描重试；重试成功后只更新了 DB 状态，**忘了 `retryTaskMap.remove()`**，失败任务也从未清理。每笔失败交易泄漏一个 Entry，日均 300 万笔回调 × 2% 失败率，13 天攒满 4G。

**解决**

- 止血：重启恢复 + 临时把 Xmx 提到 6G（只是延长时间，心里清楚治不了本）；
- 根治：本地暂存换 Caffeine（`maximumSize(100_000)` + `expireAfterWrite(3h)`，自带上限兜底）；重试任务本就该持久化——改落 DB 表 + 定时扫描，本地 Map 彻底删除；回调防重改由 DB 唯一索引保证。

**后续警惕**

- **所有 static 集合必须 code review 登记**：谁写入、谁删除、上限多少，三问缺一不可；
- 本地缓存必须有上限和过期，"内存不够再说"等于埋雷；
- `-XX:+HeapDumpOnOutOfMemoryError` 是这次能 10 分钟定位根因的前提——如果没配，凌晨 OOM 重启后现场全无，只能等下次；
- dump 目录磁盘要有告警（2.9G 的 dump，磁盘满会让下次 OOM 连现场都留不下）。

### 案例 4：方法内 new ThreadLocal，Dubbo 线程池 18 天缓慢泄漏

**背景**：用户中心 Dubbo 服务，fixed 线程池 200 线程，JDK17 堆 4G。

**故障现象**

稳定运行 18 天后 OOM。重启后又是 18 天左右 OOM——**周期极长、斜率极缓的泄漏**，jstat 天级观测根本看不出趋势。

**排查过程**

1. MAT 打开 dump，Dominator Tree 排序：前 200 行全是 `DubboServerHandler-xxx` 线程对象，每个持有 10~18MB；
2. 展开线程 → Thread → `ThreadLocalMap` → 大量 Entry，其 **key 已经是 null（弱引用被回收），value 还活着**：`AuditContext` 对象，内部 ArrayList 累计了几千个权限元素；
3. 全局搜索代码里 ThreadLocal 的使用点，找到元凶。

**根因**

```java
// 反例：ThreadLocal 定义在方法里，每次调用产生新实例
public void handle(Request req) {
    ThreadLocal<List<Permission>> auditCtx = new ThreadLocal<>();
    auditCtx.set(loadPermissions(req));   // 权限集合，单个可达几百KB
    try {
        doBusiness(req);
    } finally {
        // 写了 finally，但 remove 的是另一个 ThreadLocal / 或干脆漏了
    }
}
```

两个叠加因素：

1. ThreadLocal 定义在方法内，**每次调用都是新 ThreadLocal 对象**。线程池线程的 ThreadLocalMap 里，旧 Entry 的 key（弱引用）被 GC 回收成 null，但 value 仍被 Entry 强引用——又没有下一次 `set(同一个ThreadLocal)` 来覆盖它，**value 永久滞留**；
2. Dubbo 线程池是 fixed 200 线程长命线程，每个线程 18 天累计十几个孤儿 Entry。

**解决**

ThreadLocal 提为 `static final` 类字段；所有 set 严格 `try/finally { remove() }`；审计上下文这类大对象从 ThreadLocal 挪到显式参数传递。改后连续观察 40 天无泄漏。

**后续警惕**

- **方法内 new ThreadLocal 是重大反模式**：key 弱引用回收 + value 滞留，是最隐蔽的泄漏形态；
- 线程池 + ThreadLocal = 泄漏温床，finally remove 是铁律；
- 长周期缓慢泄漏的检测手段：NMT 或 `jcmd GC.class_histogram` **固定间隔采样对比**（如每小时一次，跑一周 diff），比盯 jstat 有效；
- MAT 里"key 为 null 的 Entry"是这类泄漏的指纹，看到直接定向查 ThreadLocal。

### 案例 5：Groovy 规则引擎动态编译，Metaspace 缓慢打满

**背景**：风控决策服务，JDK17 堆 6G，Groovy 规则引擎支持运营在线编辑规则脚本，日均保存/测试脚本上千次。

**故障现象**

每运行 5~7 天，FullGC 越来越频繁（从一天 1 次涨到一小时十几次），最终抛出 `java.lang.OutOfMemoryError: Metaspace`。

**排查过程**

1. `jstat -gc <pid> 1000`：M 列（Metaspace 已用）从正常的 90MB 一路爬到 800MB+，**每次 FullGC 后 M 几乎不下降**——类卸载没有发生；
2. `jcmd <pid> GC.class_histogram | grep -i groovy | head`：groovy 运行时生成的脚本类 `Script1`、`Script2`…… 累计 **60 多万个类**；
3. 结合代码确认编译路径。

**根因**

```java
// 反例：每次规则保存/测试都新编译一个类，缓存按"时间戳"key，永不复用
public Rule compileRule(String script) {
    GroovyClassLoader loader = new GroovyClassLoader(parent);
    Class<?> clazz = loader.parseClass(script);   // 每次生成全新 Class
    ruleCache.put("rule_" + System.currentTimeMillis(), clazz);
}
```

类卸载的条件非常苛刻：该类的所有实例不可达 + 加载它的 ClassLoader 不可达 + 无其他引用。运营每改一个字符保存一次，就产生一个新 Class 和一条永不复用的缓存引用——**类只进不出，Metaspace 单调上涨**。堆内存完全健康，问题出在堆外。

**解决**

- 脚本内容 MD5 作为缓存 key，相同内容直接复用已编译的 Class（编译量下降 95%）；
- `-XX:MaxMetaspaceSize=512m` 设上限兜底，配 80% 告警——宁可提前报警也不能无限涨到进程被杀；
- 上线巡检任务：每天低峰跑一次 `GC.class_histogram`，脚本类数量突增即告警。

**后续警惕**

- 一切**动态类生成**（Groovy 脚本、CGLib 代理、Javassist、大量反射 lambda）都要问一句：这些类卸载得了吗；
- 特征信号记住一条：**Metaspace 持续上涨 + FullGC 后不降**，与堆泄漏（老年代上涨）是两条独立战线，排查时别只盯着堆；
- Metaspace 默认无上限（直到物理内存耗尽），生产必须显式设 MaxMetaspaceSize；
- 第三方脚本能力（Groovy/QLExpress/Aviator）引入时，把"编译缓存与复用"当作评审必过项。

### 案例 6：K8s Pod 反复重启退出码 137，堆内存明明很健康

**背景**：Spring Cloud Gateway 网关，K8s 部署，Pod limit 2C2G，启动参数 `-Xms1500m -Xmx1500m`。

**故障现象**

流量高峰期 Pod 每 10~20 分钟被重启一次，`kubectl get pod` 的 RESTARTS 持续增长，期间偶发 502。应用日志里**没有任何 OOM 异常**，GC 日志显示堆最大只用到 60%——"堆明明没满，为什么被杀"。

**排查过程**

1. `kubectl describe pod`：Last State: Terminated, **Reason: OOMKilled, Exit Code: 137**——不是 Java 抛 OOM，是**容器 cgroup 内存超限被 K8s 直接杀死**；
2. 通过 node_exporter / `kubectl top pod` 看容器 RSS：高峰期冲到 1.95G，贴着 2G limit；
3. NMT 拆解真实内存构成（`-XX:NativeMemoryTracking=summary` 已配置）：

```
jcmd 1 VM.native_memory summary
                 Java Heap: 1500MB
                 Class(metaspace + ...): 120MB
                 Code: 110MB
                 Thread(栈): 205MB     # 网关线程 + Netty 线程约 200+ 个 × 1M
                 Internal: 380MB       # DirectByteBuffer（Netty 网络缓冲）
```

合计约 2.3G——**超出 2G limit**，堆外内存（尤其 Netty 的直接内存）是把 RSS 顶爆的最后一根稻草。

**根因**

容器 limit 是按"堆大小"配置的，而 **JVM 实际内存 = 堆 + 元空间 + 代码缓存 + 线程栈 × 线程数 + 直接内存 + GC 数据结构**。堆 1500m 看似只占 75%，其余区域加起来早就越界；Netty 网关的直接内存波动大，高峰期被 cgroup 杀。

**解决**

```
-Xss512k                          # 线程栈减半
-XX:MaxRAMPercentage=60           # 堆改为 limit 的 60%（约 1.2G）
-XX:MaxDirectMemorySize=512m      # 直接内存显式设上限
```

limit 升到 2.5G，并加容器 RSS 告警（超过 limit 85%）。此后一个月零重启。

**后续警惕**

- **退出码 137 = 被 OOM Killer / cgroup 杀**，Java 层面不会有任何异常日志，只能从 K8s 侧发现；
- 容器内存预算公式：`limit ≥ (堆 + 元空间 + CodeCache + 线程栈×线程数 + 直接内存) × 1.3`，照表逐项核算，别只看堆；
- 监控哨兵：**容器 RSS 与堆使用量的差值**——差值持续扩大就是堆外泄漏的早期信号；
- CPU limit 小于 1 核的 Pod 要配 `-XX:ActiveProcessorCount`，否则 GC/JIT 并行度按单核算，性能悄悄腰斩。

### 案例 7：微服务扩容后数据库连接打满，全站超时

**背景**：订单系统 30 个微服务，MySQL 8.0（16C64G，`max_connections=1000`）。大促把订单服务从 8 实例扩到 50 实例，每实例 HikariCP `maximum-pool-size=20`。

**故障现象**

扩容完成后 10 分钟，全站接口开始报 `Connection is not available, request timed out after 30000ms.`，错误率 40%，DB CPU 飙到 90%。

**排查过程**

1. MySQL `show processlist`：**980+ 连接**，大量 Sleep 状态挂着，少量慢查询在跑；
2. 算总账：订单服务 50 实例 × 20 = **1000 连接**，加上报表、BI、周边系统常驻的 200+，**总需求 1200+ > max_connections 1000**——扩容那一刻就注定超卖；
3. DB CPU 高的原因是另一条线：扩容放大的流量暴露了一条没走索引的查询，连接处理变慢 → 归还变慢 → 连接更不够——**正反馈雪崩**；
4. 应用侧：HikariCP 拿不到连接默认等 30s（connection-timeout: 30000），Tomcat 线程成批挂住，不依赖 DB 的接口也一起超时。

**根因**

**连接是全局共享资源，扩容评审只看了应用容量，没算数据库侧的账**；同时 30s 的取连接超时把"资源不足"放大成了"全站线程耗尽"。

**解决**

- 止血：DBA 评估内存后临时 `set global max_connections=1600`；kill 长时间 Sleep 连接；紧急给慢 SQL 加索引；
- 根治：订单服务连接池降到 10（50×10=500，占总容量一半）；慢 SQL 治理纳入上线门禁；读流量切读写分离；
- 参数修正：`connection-timeout` 从 30000 改 3000——快速失败 + 告警，比挂住 30 个线程强。

**后续警惕**

- 全局公式钉在墙上：**Σ(实例数 × maximum-pool-size) ≤ max_connections × 75%**，扩容评审单必须有"共享资源容量"一栏；
- 连接池水位（active/total）和 DB 连接数要双告警，水位 > 80% 就要动作，别等报错；
- `connection-timeout` 是雪崩放大器：长超时把局部资源不足放大为全站线程耗尽，3~5s 足够；
- 数据库慢会反向加剧连接不足（归还变慢），两个告警要关联分析。

### 案例 8：爆款商品大 key + 缓存击穿，十分钟拖垮全站

**背景**：电商商品服务，Redis 6 主从架构，商品详情一个聚合 key 存整页 JSON。

**故障现象**

大促 0 点整，商品接口 P99 从 1ms 涨到 8s，Redis 大量命令超时，DB CPU 打满 100%，10 分钟后商品页全白。

**排查过程**

1. Redis `SLOWLOG GET 10`：`GET product:detail:10086` 单次耗时 **45ms**（正常亚毫秒级）；
2. `MEMORY USAGE product:detail:10086`：**8.2MB**——把评论第一页 500 条整包打进了 value；
3. 回看监控：0 点该 key 的 TTL 恰好集中到期，该 key QPS 3 万，miss 后**全部回源 DB**；
4. DB 慢查询日志：`select * from comment where product_id=? limit 500` 全表扫描打满 CPU。

**根因**

两个经典问题在同一秒叠加：

- **大 key**：8.2MB 的 value 每次读取都要完整序列化 + 网络传输，占住 Redis 单线程 45ms，期间**所有命令排队**——Redis 本身先被打慢，导致其余命令连锁超时；
- **击穿**：爆款 key 集中过期，无互斥重建，3 万 QPS 同时打到 DB。

**解决**

- 止血：手动 `SETNX` 加互斥锁，单线程回填缓存，DB 流量立刻回落；
- 根治：拆 key——基础信息 / 价格 / 评论拆三个 key，评论再按页拆；热 key 改**逻辑过期**（value 内嵌过期时间戳，物理永不过期，后台异步刷新，热 key 永不断供）；本地加 Caffeine 一级缓存（TTL 5s）兜住爆款流量；评论查询补索引 + 限制深度。

**后续警惕**

- `redis-cli --bigkeys` 纳入每周巡检，String > 10KB、集合元素 > 5000 就要治理；
- 热点 key 上线前必须过"过期瞬间"评估：逻辑过期或互斥重建二选一；
- TTL 一律加随机偏移（`基础时长 + random(0,600s)`），防止同一批 key 同秒到期；
- Redis SLOWLOG 常态化采集——它是大 key 最灵敏的哨兵，等接口慢了才发现就晚了。

### 案例 9：Feign 默认 60s 超时，下游抖 5 秒引发全链路雪崩

**背景**：微服务链路 `gateway → order → inventory → DB`，Spring Cloud OpenFeign 全部默认配置。

**故障现象**

inventory 依赖的 DB 出现一次 5 秒的慢查询抖动，5 分钟后 order 服务 Tomcat 线程池耗尽**全接口**不可用（包括不依赖 inventory 的接口），网关 5xx 飙升，用户不断刷新进一步放大流量。

**排查过程**

1. SkyWalking 链路：order 的 span 卡在等待 inventory 响应，单次 5s+；
2. `jcmd <order-pid> Thread.print`：180 个 `http-nio-8080-exec` 线程 WAITING 在 Feign 响应读取上——**200 个工作线程被下游拖死**；
3. 检查 Feign 配置：项目未显式配置超时，**readTimeout 走默认 60s**——下游 5s 慢根本等不到超时，线程只进不出。

**根因**

三连缺失：**默认超时 60s 远大于下游正常 RT（50ms）**（慢调用不会快速失败）；**无熔断**（依赖劣化时照单全收）；**无线程隔离**（一个依赖拖死全部接口）。加上用户端刷新重试，形成流量正反馈。

**解决**

- Feign 超时收紧：`connect-timeout: 1000` / `read-timeout: 3000`，慢接口单独放宽；
- 关闭默认重试（仅幂等 GET 显式开启）；
- Sentinel 慢调用熔断：RT > 1s 比例超 50% 熔断 10s，半开试探恢复；
- order 对 inventory 的调用移入独立线程池（舱壁隔离），故障半径不再波及全服务。

**后续警惕**

- **超时预算自外向内收紧**：网关 > Feign > Redis/DB，任何一层用了"默认值"都要当成隐患过一遍；
- 上线 checklist 必查三项：默认超时、默认重试、默认线程池——三者的默认值都为"挂"准备好了条件；
- "部分接口不可用"和"全接口不可用"是两种故障：后者几乎必然是**线程池被某一类依赖拖死**，直接查线程栈 WAITING 在哪；
- 定期做依赖故障演练（主动给下游注入延迟），验证熔断真的会开。

## 四、从案例到体系：复盘与预防

### 1. 事故复盘模板（每个案例都按这个格式沉淀）

```
【时间线】几点几分：第一个告警 → 人工介入 → 定位根因 → 止血 → 恢复，每步耗时
【影响面】持续时长、错误率、资损
【根因】直接原因 + 为什么防线没拦住（问五层为什么）
【止血动作】当时做了什么让系统恢复
【根治动作】代码/架构/配置的永久修复
【预防清单】本次暴露的告警缺失、流程缺失、参数默认值
```

复盘只回答一个问题：**同样的故障再来一次，能不能在用户感知之前发现**。九个案例里，没有一个的根因是"工具不够"，全都是"防线缺失或默认值埋雷"。

### 2. 案例反推的告警清单

| 告警项                        | 来自案例 | 阈值建议                                 |
| ----------------------------- | -------- | ---------------------------------------- |
| 单线程 CPU 持续 100%          | 案例 1   | 持续 1 分钟                              |
| JVM 分配速率                  | 案例 2   | 超基线 3 倍                              |
| 堆使用量斜率（而非瞬时值）    | 案例 3   | 6 小时线性上涨告警                       |
| Metaspace 使用量              | 案例 5   | MaxMetaspaceSize 的 80%                  |
| 容器 RSS 与 limit 差值        | 案例 6   | > 85% limit                              |
| HikariCP 池水位 + DB 连接总数 | 案例 7   | 水位 > 80%；总数 > max_connections × 75% |
| Redis SLOWLOG 条目数          | 案例 8   | 单条 > 10ms 即采集                       |
| 下游依赖 RT 突增              | 案例 9   | 超基线 2 倍（熔断前哨）                  |
| dump 目录磁盘                 | 案例 3   | 使用率 > 80%（保证下次 OOM 能留下现场）  |

### 3. 上线前检查清单（把默认值雷区排完）

1. JVM：HeapDumpOnOutOfMemoryError、GC 日志、容器内存预算（案例 3、6）；
2. 超时三层收紧：网关 > RPC > 存储，禁用任何默认超时（案例 9）；
3. 连接池：全局容量公式核算 + 水位告警（案例 7）；
4. static 集合与 ThreadLocal：登记上限与清理责任（案例 3、4）；
5. 动态类来源：编译缓存复用策略（案例 5）；
