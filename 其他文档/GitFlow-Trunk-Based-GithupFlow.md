# Git Flow -Trunk‑Based-GitHupFlow

> 核心一句话： **Git Flow：多分支、长周期、版本驱动；Trunk‑Based：单主干、短周期、持续集成。**GitHub Flow**：**单主干、PR 驱动、合并即发布****

## 1、Git Flow

### 分支模型（固定 5 种分支）

1. `main` / `master`：生产环境代码，永远可发布
2. `develop`：开发主干，集成所有功能
3. `feature/*`：新功能分支，从`develop`切出，完成合并回`develop`
4. `release/*`：发布分支，从`develop`切出，测试完成合并到`main`+`develop`
5. `hotfix/*`：线上紧急修复，从`main`切出，修复后合并`main`+`develop`

### 工作流程

1. 新功能：`develop` → `feature/xxx` → 完成合并回`develop`
2. 准备发布：`develop` → `release/v1.2.0` → 测试修复 → 合并`main`打 tag，同步回`develop`
3. 线上 bug：`main` → `hotfix/xxx` → 合并`main`打 tag，同步回`develop`

### 优点

- 版本管理清晰，**适合有明确版本周期、定期发版**的项目
- 发布、热修复流程标准化，适合传统软件、版本化交付
- 适合大团队、周期长的项目

### 缺点

- 分支多，**合并冲突多，合并成本高**
- 分支生命周期长，容易出现 “代码腐烂”，很久才合并回主干
- 不适合高频持续发布；每次 release 需要走完整流程
- 分支太多，仓库维护复杂

## 2、Trunk‑Based Development（主干开发，TBD）

> 现在互联网、云原生、CI/CD 团队主流模式。

### 分支模型

- 只有一条**主干分支（trunk /main）**，没有 develop 分支
- 功能使用**短生命周期 feature 分支**（小时 / 天级别，不超过 1‑2 天）
- 不做长期 release 分支；**小批量频繁合并回主干**
- 线上 bug：直接在主干修复，或者短分支修复合并回主干

### 工作流程

1. 开发者从`main`切出短生命周期 feature 分支
2. 开发完成，**立刻 MR/PR 合并回 main**，CI 自动跑测试
3. 主干永远保持可发布状态，随时可以部署上线
4. 线上紧急 bug：切小分支修复，快速合并回 main，直接发布
5. 版本号：基于主干打 tag，不需要 release 分支

> 关键：**禁止长期在 feature 分支开发，尽量频繁合并到主干，减少冲突**。

### 优点

- 合并冲突少，代码持续集成，**CI/CD 友好**
- 交付速度快，适合持续部署、高频发布
- 分支简单，维护成本低
- 代码不会在分支里堆积腐烂

### 缺点

- 对团队工程能力要求高：单元测试、自动化测试必须完善；如果测试不足，合并到主干容易把主干搞挂
- 不适合那种 “大版本集中交付” 的传统软件；不适合开发周期以月为单位的大功能

## 4、对比表格

| 维度         | Git Flow                             | Trunk‑Based Development(TBD)              |
| ------------ | ------------------------------------ | ----------------------------------------- |
| 主干         | `develop`为开发主干，`main`生产      | 只有`main`作为唯一主干                    |
| feature 分支 | 生命周期长（周 / 月）                | **短生命周期（小时～1‑2 天）**            |
| release 分支 | ✅有，专门做发布准备                  | ❌无，主干直接发布                         |
| hotfix       | 从 main 切出，合并 main+develop      | 小分支修复，直接合并 main                 |
| 合并频率     | 少，等到功能做完才合并               | 高频，频繁合并回主干                      |
| 适合场景     | 传统软件、版本周期长、定期大版本发布 | 互联网、云原生、CI/CD、持续部署、高频迭代 |
| 冲突风险     | 高，长分支容易大量冲突               | 低，频繁合并减少冲突                      |
| 工程要求     | 中等                                 | 高，必须完善自动化测试                    |
| CI/CD 适配   | 较差，需要处理多分支                 | 原生友好，CI 直接跑主干                   |

## 5、怎么选

1. ✅选 

   Git Flow

   - 桌面软件、传统项目，有明确的版本号，按月 / 按季度发版；
   - 团队自动化测试不完善，需要独立 release 分支做测试隔离。

2. ✅选 

   Trunk‑Based

   - 后端服务、云原生项目，持续部署，一天多次发布；
   - 团队有完善单元测试、CI 流水线；
   - 小迭代，功能拆小，快速交付。

> 补充：很多团队会做折中：**简化版 Git Flow**，去掉 release 分支，保留 main+feature+hotfix，介于两者之间。

3. GitHup Flow

4. 个人项目折中：如果要做正式软件版本，可以**只保留 main + feature + hotfix，**

| 场景                                 | 推荐                                        | 说明                                                         |
| :----------------------------------- | :------------------------------------------ | :----------------------------------------------------------- |
| 个人项目、无正式版本                 | `main` + 短 feature 分支，甚至直接 main     | 打 tag 即发布，无需流程                                      |
| 个人项目、有版本交付(游戏、桌面软件) | `main` + `feature/*` + `hotfix/*` + tag     | 您做 Godot/LibGDX 游戏，属这类——版本化交付，不需要 develop/release 分支 |
| 2-5 人小团队                         | GitHub Flow                                 | main 受保护 + PR 评审(1 人批)+ CI 必须绿                     |
| 5 人以上、多环境多服务               | 进入之前文档的方案(主干开发 + release 分支) |                                                              |

核心判断只看一条：**发布形态**。持续部署的后端服务选主干类；按版本交付(游戏、客户端、外包项目)留 main + tag + hotfix,别用完整 Git Flow——分支维护成本会吃掉小团队全部精力。

## 6、常见误区

1. Git Flow ≠ 不能用 CI；只是原生设计不适合高频持续部署。
2. TBD 不是禁止 feature 分支，**禁止长生命周期 feature 分支**；
3. TBD 不是所有人直接往 main 硬 push，依然要用 PR/MR，走 CI 校验。
