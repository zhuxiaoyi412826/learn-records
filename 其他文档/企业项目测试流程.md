# 测试内容

### 1. 按测试阶段划分

| 阶段            | 测试对象         | 执行方      | 常用手段                                                 |
| :-------------- | :--------------- | :---------- | :------------------------------------------------------- |
| 单元测试        | 函数/类/模块     | 开发人员    | JUnit、pytest、JUnit5 + Mockito，结合 SonarQube 静态扫描 |
| 集成测试        | 模块间接口与交互 | 开发 + 测试 | 接口测试（Postman、JMeter、RestAssured）                 |
| 系统测试        | 完整系统         | 测试团队    | 功能测试 + 非功能测试                                    |
| 验收测试（UAT） | 业务场景端到端   | 用户/产品方 | 按业务场景走查，Alpha/Beta 测试                          |

### 2. 按测试方法划分

- **黑盒测试**：等价类划分、边界值分析、判定表、因果图、场景法、正交实验法、错误推测法
- **白盒测试**：语句覆盖、分支覆盖、条件覆盖、路径覆盖（通常在单元测试层实施）
- **灰盒测试**：结合接口文档与内部逻辑，常用于接口测试

### 3. 非功能测试内容

| 类别       | 关注点                                                       | 常用工具                            |
| :--------- | :----------------------------------------------------------- | :---------------------------------- |
| 性能测试   | 负载测试、压力测试、稳定性（浸泡）测试、并发指标（TPS、响应时间、错误率） | JMeter、Locust、LoadRunner          |
| 安全测试   | SQL 注入、XSS、CSRF、越权访问、敏感信息泄露                  | OWASP ZAP、Burp Suite、依赖漏洞扫描 |
| 兼容性测试 | 浏览器、操作系统、分辨率、多端数据一致性                     | BrowserStack、真机/云测平台         |
| 易用性测试 | 交互流畅度、提示友好性、操作路径合理性                       | 人工走查 + 用户反馈                 |
| 可靠性测试 | 故障恢复、容灾、7×24 小时稳定性                              | 混沌工程（ChaosBlade 等）           |
| 数据库测试 | 数据一致性、事务完整性、索引与慢查询                         | SQL 审查、慢日志分析                |

### 4. 企业级项目常见专项内容

- **接口自动化**：回归阶段的核心防线，纳入 CI/CD 流水线
- **UI 自动化**：核心业务流程的自动化（Selenium、Playwright、Cypress）
- **Mock 测试**：依赖第三方服务时使用 Mock Server 解耦
- **配置与环境测试**：多环境（开发/测试/预发/生产）配置一致性

### 5. 质量度量指标（测试报告核心内容）

| 指标                | 说明                               |
| :------------------ | :--------------------------------- |
| 用例执行率 / 通过率 | 衡量测试覆盖与版本质量             |
| 缺陷密度            | 每千行代码缺陷数，评估代码质量     |
| 缺陷收敛趋势        | 判断版本是否趋于稳定、可发布       |
| 缺陷逃逸率          | 线上发现的缺陷占比，衡量测试有效性 |
| 缺陷修复周期        | 评估开发响应效率                   |

**核心原则**：测试左移（需求阶段即介入）+ 测试右移（线上监控与反馈闭环），全程以“质量门禁”驱动发布决策。

### 6. 测试方式

#### 一、总体格局：测试金字塔

Plain Text



```
        /  UI 手动探索测试  \        ← 少量，靠人的经验
       /  UI/端到端自动化    \       ← 核心业务流程
      /    接口自动化测试     \      ← 回归主力，占比最大
     /   集成测试（半自动）    \
    /      单元测试（自动）      \   ← 开发编写，全自动
```

**层次越低越自动化，层次越高人工占比越大**。投入产出比最高的自动化层是接口测试。

#### 二、手动测试 vs 自动化测试的分工

| 维度     | 手动测试                                                | 自动化测试                               |
| :------- | :------------------------------------------------------ | :--------------------------------------- |
| 适用场景 | 新功能首次验证、探索性测试、易用性/兼容性测试、UAT 验收 | 回归测试、冒烟测试、性能压测、接口测试   |
| 执行时机 | 每轮提测后按用例执行                                    | CI/CD 流水线触发（提测、合并、每日定时） |
| 优势     | 能发现预期外的问题、判断体验好坏                        | 快速、可重复、可 7×24 执行、防回归       |
| 劣势     | 慢、易疲劳遗漏、人力成本高                              | 无法发现用例之外的缺陷、有开发和维护成本 |

#### 三、典型企业分工模式

| 测试类型           | 手动         | 自动化     | 说明                                                      |
| :----------------- | :----------- | :--------- | :-------------------------------------------------------- |
| 冒烟测试           | 少量         | ✅ 主力     | 打包部署后自动跑核心接口，不通过直接打回                  |
| 功能测试（新功能） | ✅ 主力       | 补充       | 新功能首次测试靠人工探索                                  |
| 回归测试           | 只看新增改动 | ✅ 主力     | 老功能全靠自动化回归，这是自动化的核心价值                |
| 接口测试           | 临时调试     | ✅ 主力     | Postman 手动调试 → 沉淀为 RestAssured/pytest 脚本进流水线 |
| UI 测试            | 视觉/体验类  | 核心流程   | 纯界面自动化维护成本高，只自动化高价值路径                |
| 性能/压力测试      | ❌            | ✅ 全自动   | JMeter/Locust 脚本化，人无法模拟千级并发                  |
| 安全扫描           | 专项人工渗透 | ✅ 工具扫描 | SAST/依赖扫描进流水线，渗透测试定期人工做                 |

#### 四、典型流转：从手动到自动化的沉淀过程

```
新需求提测
  ↓
测试人员手动执行用例（Postman 点接口 / 页面点功能）
  ↓
发现并修复缺陷
  ↓
本迭代结束前，把核心接口用例脚本化（沉淀到自动化工程）
  ↓
进入 CI/CD 流水线：下次提测自动回归，无需重复手动执行
```

#### 五、常见的量化参考（成熟团队）

- **回归自动化覆盖率**：核心接口 80%+ 自动化
- **自动化收益判断**：一个用例重复执行 3 次以上，就值得脚本化
- **流水线门禁**：冒烟自动化不通过 → 禁止部署到测试环境；回归不通过 → 禁止发布

**一句话总结**：人工测试负责“发现新问题”，自动化测试负责“守住老问题不复发”。企业里不可能全手动（回归会累死人），也不可能全自动（机器不会质疑需求是否合理）
