# JVM

分为：内存区域、垃圾回收 GC、类加载、JVM 参数、故障排查、OOM、调优，面试最常考。

## 一、JVM 内存结构（运行时数据区）

1. **JVM 运行时数据区分为哪几块？每块作用？哪些线程私有 / 共享？**

> 答： 线程私有：**程序计数器、虚拟机栈、本地方法栈** 线程共享：**堆、元空间（Metaspace，取代永久代 PermGen）**

- 程序计数器：记录当前线程执行字节码行号，唯一一个没有 OOM 的区域。
- 虚拟机栈：Java 方法执行，栈帧（局部变量表、操作数栈、动态链接、返回地址）；栈深度过大抛出`StackOverflowError`。
- 本地方法栈：给 native 本地 C/C++ 方法使用。
- 堆：所有对象实例、数组；GC 主要工作区域，分年轻代 (Eden、S0、S1)、老年代。
- 元空间：存放类信息、常量、静态变量、编译后的代码；使用本地内存，不在堆内。

1. **栈帧里面有什么？** 局部变量表、操作数栈、动态链接、方法返回地址。
2. **对象在堆中布局？对象头包含什么？MarkWord 作用？**

- 对象头 MarkWord、类型指针、实例数据、对齐填充。
- MarkWord：哈希码、分代年龄、锁状态标志（无锁、偏向锁、轻量级锁、重量级锁）。

1. **什么是逃逸分析？栈上分配？** 对象不会逃逸出方法，则对象可以分配在栈上，方法执行完自动回收，减少 GC 压力。

## 二、垃圾回收 GC（重中之重）

1. **GC 为什么不扫描程序计数器？哪些区域发生 GC？** GC 主要发生在堆；元空间也会回收废弃类；栈、程序计数器不会 GC。
2. **怎么判断对象是垃圾？引用计数法可达性分析？优缺点？**

- 引用计数：对象被引用计数 + 1，为 0 回收；缺点**循环引用无法解决**。
- 可达性分析 (JVM 采用)：GC Roots 向下搜索，不可到达对象判定垃圾。

> GC Roots：栈局部变量、静态变量、元空间常量、本地方法引用。

1. **Java 四种引用：强、软、弱、虚引用，使用场景？**

- 强引用：普通 new，不会回收；
- 软引用 SoftReference：内存不足才回收，适合做缓存；
- 弱引用 WeakReference：下次 GC 直接回收，WeakHashMap；
- 虚引用 PhantomReference：仅收到回收通知，堆外内存释放。

1. **年轻代、老年代分配比例？Eden:S0:S1 为什么是 8:1:1？S0 S1 作用？** Eden 占 8，Survivor0、Survivor1 各 1；复制算法，始终一块空，作为复制备份，防止内存碎片。对象在 Survivor 来回拷贝，年龄达到 15 晋升老年代。

2. **对象什么时候晋升到老年代？** ① 年龄达到阈值默认 15； ② Survivor 放不下，触发担保机制； ③ 大对象直接进入老年代（‑XX:PretenureSizeThreshold）。

3. **GC 算法：标记清除、标记复制、标记整理，优缺点**

   表格

   | 算法      | 优点     | 缺点                     |
   | --------- | -------- | ------------------------ |
   | 标记‑清除 | 实现简单 | 产生大量内存碎片         |
   | 标记‑复制 | 无碎片   | 需要预留一块同等内存空间 |
   | 标记‑整理 | 无碎片   | 移动对象，STW 时间长     |

4. **常见垃圾收集器（重点）：Serial、Parallel、CMS、G1、ZGC**

- Serial：单线程收集，STW 长，客户端模式。
- Parallel GC：多线程，吞吐量优先，JDK8 默认。
- CMS：并发标记清除，低停顿；碎片多；JDK8 后期废弃。 四个阶段：初始标记 (STW)、并发标记、重新标记 (STW)、并发清除。

> CMS 缺点：内存碎片、浮动垃圾。

- G1（JDK9 默认）：Region 分块，可预测停顿；既有年轻代也处理老年代；混合收集。
- ZGC（JDK11+）：几乎无 STW，染色指针，支持 TB 级堆，生产新选择。

> 面试高频：**CMS 和 G1 区别，G1 和 ZGC 区别**

1. **什么是 STW Stop‑The‑World？哪些阶段会 STW？** Stop The World，所有业务线程暂停，GC 线程执行；用户线程全部停止。 Serial 全部 STW；CMS：初始标记、重新标记 STW；G1 多个阶段 STW；ZGC STW 极短。
2. **Minor GC、Major GC、Full GC 区别，触发条件**

- Minor GC：只回收年轻代，频繁；Eden 满触发。
- Major GC：只回收老年代，很少。
- Full GC：整堆回收（年轻 + 老年代 + 元空间），STW 时间很长；尽量避免。 触发 FullGC：老年代空间不足、System.gc ()、CMS 碎片担保失败、元空间满。

1. **什么是空间分配担保？** MinorGC 前，判断老年代剩余空间 > 新生代全部对象；不满足直接触发 FullGC。

## 三、类加载机制

1. **类加载全过程：加载、验证、准备、解析、初始化，每个阶段干什么**
2. 加载：读 class 字节码，生成 Class 对象；
3. 验证：校验字节码合法性；
4. 准备：静态变量分配内存，赋**默认零值**；
5. 解析：符号引用转直接引用；
6. 初始化：执行静态代码块，给静态变量赋程序设定值。
7. **双亲委派模型是什么？破坏双亲委派场景？** 双亲委派：类加载收到请求，先交给父加载器，父加载不了自己才加载。 好处：防止重复加载，安全防护。 破坏：Tomcat 容器、SPI、自定义类加载器。
8. **有哪些类加载器？** 启动类加载器 Bootstrap、扩展类加载器 Extension、应用程序类加载器 AppClassLoader，自定义类加载器。

## 四、JVM 故障、OOM、排查（生产面试高频）

1. **有哪些 OOM 场景？分别什么原因？**
2. Java heap space：堆内存不足，对象太多无法回收；内存泄漏 / 内存溢出。
3. Metaspace：元空间满，大量动态生成类。
4. Unable to create new native thread：线程数过多。
5. Direct buffer memory：堆外内存溢出，NIO ByteBuffer。
6. **内存泄漏 vs 内存溢出区别** 内存泄漏：程序不再使用对象，仍然持有引用，GC 无法回收，越积越多；多次泄漏最终导致 OOM。 内存溢出 OOM：没有足够内存分配新对象。
7. **线上 JVM 故障排查工具命令？**`jps`：查看 java 进程`jstat ‑gc pid`：实时 GC 统计`jmap ‑dump`：dump 堆快照文件`jhat`：分析 dump 文件`jstack pid`：打印线程栈，死锁、死循环、线程阻塞 可视化：MAT (Memory Analyzer Tool)、Arthas（阿里线上神器）
8. **CPU 飙高排查完整流程**
9. top 找到高 CPU Java 进程 pid
10. `jstack pid`打印线程栈；top‑H 找到高消耗 tid 线程
11. tid 转 16 进制，在线程栈搜索定位代码位置。
12. **频繁 FullGC 怎么排查？**

- 看 jstat 观察 GC 情况；dump 堆快照 MAT 分析，看大对象、内存泄漏；
- 原因：内存太小、内存泄漏、对象过快晋升老年代、元空间满、System.gc 被调用。

1. **什么是内存抖动？** 短时间大量创建销毁临时对象，频繁 MinorGC，影响性能。

## 五、JVM 参数 & 调优

1. **常见 JVM 参数**`‑Xms`初始堆；`‑Xmx`最大堆；建议 Xms=Xmx，避免运行时扩容消耗性能`‑Xmn`年轻代大小`‑XX:MetaspaceSize`元空间初始；`‑XX:MaxMetaspaceSize`最大元空间`‑XX:+PrintGCDetails`打印 GC 日志`‑XX:+HeapDumpOnOutOfMemoryError` OOM 自动 dump 堆文件
2. **JVM 调优目标是什么？** 降低 FullGC 频率；减少 STW 停顿时间；提高吞吐量。

> 调优不是追求零 GC，是平衡吞吐量和延迟。

## 六、进阶综合面试题（中高级必问）

1. **CMS 的浮动垃圾是什么？为什么产生？** 并发清除阶段业务线程还在产生垃圾，这部分本次 GC 无法清理，留给下一次。
2. **G1 的 Region，Humongous 大对象区域是什么？** 大于 Region 一半大小对象直接放在 Humongous 区。
3. **ZGC 原理，染色指针，读屏障，为什么停顿极低？**
4. **System.gc () 调用一定会触发 Full GC 吗？** 不一定，`‑XX:+DisableExplicitGC`会屏蔽。
5. **发生 OOM 之后进程还能继续运行吗？** 如果 OOM 发生在一个线程，该线程死掉，其他线程可以继续运行；不一定进程直接挂。
6. **jstack 排查死锁，死锁发生四个条件？** 互斥、占有且等待、不可剥夺、循环等待。

## 七、CPU 过高排查

**核心思路**

定位高 CPU 线程，找到执行的业务代码，区分是业务代码还是 GC 线程占用 CPU。

1. **优先 JFR（生产推荐，低开销）**

```
jcmd <pid> JFR.start name=cpu filename=/tmp/cpu.jfr duration=60s settings=profile
```

下载 jfr 到本地用 JMC 分析，查看**方法概要**，按 CPU 占比排序定位热点方法。

1. **传统 Linux 命令应急方案** ① `top -H -p <pid>` 找到高 CPU 线程 LWP 号（十进制） ② `printf "%x\n 线程号"` 转为十六进制 ③ `jcmd <pid> Thread.print > thread.txt` 导出线程栈 ④ 在文件搜索十六进制 nid，定位线程堆栈与业务代码
2. **Arthas 应急**`thread -n 10` 查看 CPU 最高线程；`profiler`生成 CPU 火焰图。

> ✨CPU 高常见原因：死循环、复杂运算、大量字符串处理、正则回溯、GC 频繁、锁自旋。

## 八、OOM / 内存泄漏排查

> 区分：**内存泄漏**：对象无用但被引用无法回收，调大 Xmx 只能延迟崩溃；**内存溢出**：业务确实需要更大内存，Xmx 配置过小。

1. **提前配置 JVM 参数，故障自动保存现场（必背）**

```
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dump
```

OOM 崩溃自动生成`hprof`堆快照。

1. 线上观测：`jstat‑gc <pid> 1000` 观察老年代持续上涨，FullGC 后内存几乎不下降，大概率内存泄漏。
2. 获取堆 dump

- 优先：OOM 自动输出 hprof
- 手动导出（低峰执行，会 STW）：`jcmd <pid> GC.heap_dump -all xxx.hprof`

1. **本地 MAT 工具分析 hprof** 选择`Leak Suspects Report`泄漏报告： ① 查看实例数量多、占用内存大的对象 ② 追踪**GC Roots 引用链**，找到是谁持有对象导致无法回收
2. 辅助验证：JFR 录制，查看对象分配统计，定位大量创建对象的方法。

> ✨内存泄漏常见原因：static 集合未清理、ThreadLocal 未 remove、缓存无淘汰策略、线程池持有对象、资源未关闭，长生命周期对象持有短生命周期对象。

Q：为什么优先用 JFR 而不是 jmap/jstack？ A：JFR 开销低（2‑5%），记录一段时间完整运行数据；jmap/jstack 只是瞬时快照，dump 会发生 STW。

Q：内存泄漏和内存溢出区别？ A：内存泄漏：对象不再使用仍被 GC Roots 引用，无法回收；内存溢出：堆内存不足以存放业务所需对象。泄漏久了最终会导致 OOM。

Q：生产可以随便执行 jmap dump 吗？ A：不可以，会触发 STW，大堆停顿时间长，尽量业务低峰执行，优先使用 OOM 自动 dump。

## 九、内存模型与运行时数据区（4 题）

### 1. 说说 JVM 运行时数据区的划分，以及 JDK 8 之后哪些区域发生了变化？

**参考答案要点：**

- 五大区域：程序计数器、虚拟机栈、本地方法栈、堆、方法区（元空间）
- JDK 8 变化：永久代（PermGen）→ 元空间（Metaspace），字符串常量池移入堆
- 线程私有：程序计数器、虚拟机栈、本地方法栈；线程共享：堆、方法区
- 元空间使用本地内存（direct memory），不再受 -XX:MaxPermSize 限制，受系统内存限制

**考察点：** 内存基础是否扎实，是否能说清元空间与永久代的区别及原因（永久代 OOM 频繁、与 HotSpot 耦合难移除等）

------

### 2. 一个对象从创建到回收，完整经历了哪些内存区域和过程？

**参考答案要点：**

1. 类加载 → 分配内存（指针碰撞 / 空闲列表，配合 TLAB 避免竞争）
2. 逃逸分析：栈上分配 / 标量替换 / 锁消除
3. 对象头初始化 → 对象进入 Eden 区
4. Minor GC 后存活对象经 Survivor 区（年龄 +1）→ 晋升老年代（动态年龄判定 / 大对象直接进老年代）
5. 老年代 Major/Full GC → 回收

**考察点：** 对对象生命周期整体链路是否清晰，能否讲出 TLAB、逃逸分析、年龄晋升等细节

------

### 3. 什么是 TLAB？它解决了什么问题？为什么不是所有对象都能在 TLAB 分配？

**参考答案要点：**

- TLAB（Thread Local Allocation Buffer）：线程本地分配缓冲区，Eden 区为每个线程划分的一块私有小空间
- 解决的问题：多线程并发分配内存时的指针碰撞竞争，减少 CAS 开销
- 不能全走 TLAB 的原因：TLAB 空间有限，大对象直接进入老年代或直接在 Eden 公共区分配；分配失败时退化到加锁 / CAS 分配
- 相关参数：-XX:+UseTLAB、-XX:TLABSize、-XX:TLABWasteTargetPercent

**考察点：** 是否理解并发分配内存的底层机制，而不只是背概念

------

### 4. 线上出现 "java.lang.OutOfMemoryError: Metaspace" 怎么排查？

**参考答案要点：**

- 原因：类元数据加载过多（动态生成类、反射、CGLIB/ASM 代理类、热部署未卸载）
- 排查步骤：
  1. jmap -clstats /jstat 观察类加载数量
  2. 用 MAT /jcmd GC.class_stats 分析元空间占用
  3. 检查是否存在动态代理类泄漏（如每次请求 new Proxy）
  4. 检查类加载器是否无法被 GC（自定义 ClassLoader 持有引用）
  5. 确认元空间参数 -XX:MaxMetaspaceSize 是否合理
- 常见误区：不是简单调大 MaxMetaspaceSize 就完事，要根因分析

**考察点：** 实战排查思路，能否区分 "参数问题" 和 "泄漏问题"

## 十、垃圾回收（5 题）

### 5. 详细讲一下 CMS 和 G1 的回收过程，各自适用什么场景？CMS 有哪些缺点？

**参考答案要点：**

- CMS：初始标记 (STW)→并发标记→重新标记 (STW)→并发清除，主打低延迟
- CMS 缺点：内存碎片（浮动垃圾）、无法处理浮动垃圾、需要预留空间（Concurrent Mode Failure）、需要 -XX:CMSFullGCsBeforeCompaction 配合
- G1：Region 化堆内存（Eden/Survivor/Old/Humongous），基于 Remembered Set 的跨 Region 引用追踪，通过 GC 停顿预测模型（-XX:MaxGCPauseMillis）控制停顿；Mixed GC 同时回收年轻代 + 部分老年代
- 适用：CMS 适合堆内存较小、追求低停顿的老系统；G1 适合大堆（>4G）、可控停顿

**考察点：** 是否真正理解两者机制差异而非背优缺点列表

------

### 6. 什么是三色标记算法？G1/CMS 如何解决并发标记中的漏标问题？

**参考答案要点：**

- 三色：白（未访问）、灰（自身已访问但引用的对象未访问完）、黑（自身及引用都已访问）
- 漏标条件：黑色对象新增了指向白色对象的引用，且灰色对象到该白色对象的引用被删除
- 解决：
  - 增量更新（CMS）：记录黑色对象新增的引用，重新标记时再扫描
  - 原始快照 SATB（G1）：记录被删除的引用，标记期间保留快照，防止漏标（可能产生浮动垃圾）
- G1 还会配合写屏障（pre-write barrier）实现 SATB

**考察点：** 高级考点，能区分增量更新与 SATB 的差异是 "深 vs 浅" 的分水岭

------

### 7. 什么是安全点（Safepoint）？为什么 GC 必须等所有线程到达安全点？

**参考答案要点：**

- 安全点：线程可以暂停执行、检查 GC 状态的位置（方法调用、循环回跳、异常抛出等）
- 原因：GC 需要修改对象引用、移动对象（复制 / 压缩），若线程正在操作堆内存则会造成数据不一致
- 问题：安全点太少 → STW 等待时间长；太频繁 → 性能损耗
- 相关：安全区域（Safe Region，用于线程处于 Blocked 状态）、-XX:+UseCountedLoopSafepoints 等
- JIT 编译后循环可能没有安全点，可能导致长循环无法进入 GC（老问题）

**考察点：** 是否理解 STW 的底层机制，能否讲出 JIT 与安全点的联动问题

------

### 8. 说说垃圾回收器的分代模型：为什么新生代用复制算法、老年代用标记 - 整理 / 标记 - 清除？

**参考答案要点：**

- 新生代：对象存活率低，复制算法只需复制少量存活对象，效率高、无碎片
- 老年代：存活率高，复制成本大，标记 - 清除有碎片、标记 - 整理无碎片但移动对象成本高（需更新引用，需 STW）
- 引申：为什么 JVM 不统一用某一种算法 → 结合对象生命周期统计特性
- G1/ZGC 通过 Region / 分页打破传统分代物理结构，但逻辑上仍分代

**考察点：** 是否理解算法选择的本质原因（存活率与成本权衡）

------

### 9. 聊聊 ZGC 和 Shenandoah，它们如何实现 "几乎无停顿" 的垃圾回收？

**参考答案要点：**

- ZGC：染色指针（Colored Pointer）+ 读屏障（Load Barrier）+ 分页（Region 动态大小）
  - 标记、转移、重映射并发执行，STW 极短（毫秒级）
  - 通过指针染色解决对象移动后的引用更新，避免大范围扫描
- Shenandoah：Brooks Pointer（转发指针），对象头部存 forwarding pointer，读屏障在访问时转发
- 两者对比：ZGC 通过指针染色实现（只支持 64 位、有指针压缩代价）；Shenandoah 通过对象内转发指针
- 适用：大堆（上百 GB）、低延迟场景；JDK 15+ ZGC 转正，JDK 17+ Shenandoah 转正

**考察点：** 是否跟得上 JVM 前沿，能否讲出 "染色指针" 的核心思想

## 十一、类加载与字节码（3 题）

### 10. 类加载的双亲委派模型是什么？为什么要这样设计？什么场景需要打破它？

**参考答案要点：**

- 流程：自下而上委派给父加载器，父加载不了再由子加载
- 目的：避免类重复加载、保证核心类库安全（防止自定义 java.lang.String 替换核心类）
- 打破场景：SPI（JDBC DriverManager 用线程上下文类加载器）、Tomcat（Web 应用隔离）、OSGi、热部署
- Tomcat 打破方式：先自己加载 webapp 的类，再委派父加载器（不严格遵守）
- 注意：打破 ≠ 全盘否定，通常 "局部打破"

**考察点：** 是否理解设计动机，能否举例说明打破的典型场景及原因

------

### 11. 类加载的三个阶段（加载、链接、初始化）各自做什么？被动引用为什么不会触发初始化？

**参考答案要点：**

- 加载：读取字节码，生成 Class 对象
- 链接：验证（格式 / 语义 / 符号引用）、准备（分配静态变量默认值）、解析（符号引用→直接引用）
- 初始化：执行 static 块、静态变量赋值（clinit 方法）
- 被动引用不触发初始化：子类引用父类静态字段、数组定义、常量（编译期进入常量池）
- 引申：static final 常量在编译期就替换，不触发类初始化

**考察点：** 能否区分 "类加载" 与 "类初始化"，这是经典考点

------

### 12. 什么是方法内联？什么情况下 JIT 不会进行内联？

**参考答案要点：**

- 方法内联：JIT 编译时将被调用方法体直接复制到调用处，消除方法调用开销（栈帧创建、参数传递、跳转）
- 不内联情况：方法体过大（超过 -XX:MaxInlineSize，默认 35 字节）、虚方法 / 多态调用（除非可去虚化 devirtualization）、递归方法、被 -XX:CompileCommand 排除
- 相关：热点方法判定（-XX:CompileThreshold 默认 10000 次）、C1/C2 编译层级
- 内联是 JIT 最重要的优化之一，常与逃逸分析配合

**考察点：** 是否理解 JIT 优化机制，能否结合性能调优谈

## 十二、性能调优与问题排查（5 题）

### 13. 线上 CPU 飙升到 100%，如何定位到具体代码行？

**参考答案要点：**

1. top 找到 CPU 最高的 Java 进程 PID
2. top -Hp PID 找到高 CPU 的线程 TID
3. printf '% x' TID 转十六进制
4. jstack PID | grep -A 线程 ID 查看线程栈
5. 定位到业务代码 / GC 线程 / JIT 编译线程（C2 CompilerThread）

- 补充：若是 GC 线程飙高 → 看 GC 日志（频繁 Full GC）；若是业务线程 → 检查死循环、锁竞争、大计算
- 也可以用 arthas thread -n 3 一键定位

**考察点：** 实战命令是否熟练，能否区分业务问题与 GC 问题

------

### 14. 线上出现频繁 Full GC，怎么排查？

**参考答案要点：**

1. 看 GC 日志（-Xlog:gc* 或 -verbose:gc）确认 Full GC 频率、耗时
2. 老年代占满原因分析：
   - 内存泄漏：用 jmap -dump 导堆，MAT 查支配树 / 泄漏嫌疑人（Leak Suspects）
   - 晋升过快：年轻代过小 / Survivor 空间不足 / 对象过大直接进老年代
   - 元空间 / 直接内存问题
3. 检查是否存在大对象、集合未清理、静态持有等
4. 观察 JVM 参数是否合理（堆大小、GC 选择）
5. 用 jstat -gcutil 看各代使用率变化趋势

**考察点：** 排查思路的完整性和工具熟练度

------

### 15. jmap、jstack、jstat、jinfo、jcmd 各自用途是什么？线上哪些命令要慎用？

**参考答案要点：**

- jstack：查看线程栈（死锁、阻塞分析）
- jmap：堆信息、dump 堆（-dump:format=b）
- jstat：GC 统计、类加载统计（-gcutil）
- jinfo：查看 / 修改运行时 JVM 参数
- jcmd：多功能综合工具（替代部分 jmap/jstack）
- 慎用 / 注意：jmap -dump 会 STW（老版本）；jmap -histo:live 会触发 Full GC；线上谨慎用 jmap dump 大堆，会暂停应用、占用磁盘
- 补充：arthas 是线上排查利器（无需重启、动态增强）

**考察点：** 工具链熟练度 + 是否知道工具本身的风险

------

### 16. 你如何设置和调整一个服务的 JVM 参数？给出一套你常用的调优思路。

**参考答案要点：**

- 思路：先保证稳定，再追求性能；基于实际业务（吞吐型 vs 延迟型）选择
- 基础参数：-Xms=-Xmx（堆初始 = 最大，避免扩容抖动）、-XX:MetaspaceSize、-Xss
- GC 选择：JDK8 小堆可 CMS，大堆 G1；JDK17+ 默认 G1，低延迟可 ZGC
- 日志：-Xlog:gc*:file=... 或 -verbose:gc，便于事后分析
- 关键：不盲目复制别人的参数，基于压测 + GC 日志数据决策；先排查问题再调优（避免 "优化一个没问题的系统"）
- 上线前做容量评估、压测验证

**考察点：** 是否具备工程化的调优方法论，而非背参数

------

### 17. 什么是 Stop-The-World？哪些操作会触发 STW？如何减少 STW 时间？

**参考答案要点：**

- STW：GC 或其他操作导致所有用户线程暂停
- 触发：GC 标记（部分阶段）、类加载的验证、偏向锁撤销（老版本）、Full GC、堆 dump
- 减少 STW：选择合适的 GC（G1/ZGC 低停顿）、调整堆大小与分区、避免 Full GC、减少锁竞争（减少偏向锁撤销）、降低对象分配速率
- 注意：STW 无法完全消除（ZGC 也只是尽量缩短），关键是 "可控"

**考察点：** 对 STW 成因的理解广度（不只 GC 一种来源）

## 十三、JVM 并发与锁（3 题）

### 18. 讲一下 synchronized 的锁升级过程：偏向锁 → 轻量级锁 → 重量级锁。

**参考答案要点：**

- 偏向锁：无竞争时，记录线程 ID 到对象头，避免 CAS 开销（JDK15 起默认废弃偏向锁）
- 轻量级锁：有竞争时，线程在栈帧中创建锁记录，CAS 尝试获取；适合锁持有时间短、线程交替执行
- 重量级锁：竞争激烈时升级为 Monitor（依赖 OS 互斥量），涉及用户态 / 内核态切换
- 锁只能升级不能降级；JDK6 起锁默认开启偏向锁，后续版本（JDK15+）默认关闭偏向锁
- 引申：锁消除（逃逸分析发现锁只被单线程访问）、锁粗化

**考察点：** 是否能讲清锁升级触发条件和各自代价

------

### 19. JMM（Java 内存模型）解决了什么问题？volatile 和 synchronized 的内存语义差异？

**参考答案要点：**

- JMM：定义主内存 + 工作内存模型，解决可见性、有序性、原子性问题
- volatile：保证可见性（写后立即刷主内存）+ 有序性（禁止指令重排序，内存屏障），不保证原子性
- synchronized：保证原子性 + 可见性 + 有序性（Monitor 锁的 happens-before）
- 内存屏障：LoadLoad、LoadStore、StoreLoad、StoreStore；volatile 写 = StoreStore+StoreLoad，读 = LoadLoad+LoadStore
- happens-before 规则：程序顺序、锁、volatile、传递性等 8 条规则

**考察点：** 并发三大特性的理解 + 底层内存屏障机制

------

### 20. 线上出现大量线程 BLOCKED 状态，如何定位是锁竞争还是死锁？

**参考答案要点：**

- jstack 查看线程状态与堆栈：
  - 死锁：jstack 会直接提示 "Found one Java-level deadlock"，两个线程互相持有对方需要的锁
  - 锁竞争：多个线程 BLOCKED 在同一个锁对象上（同一 monitor），等待同一把锁
- 工具：jconsole/jvisualvm 线程面板、arthas thread -b（找阻塞的线程）
- 处理：死锁 → 调整加锁顺序 / 使用 tryLock 超时；锁竞争 → 减小锁粒度、读写分离、减少持锁时间、使用并发容器（ConcurrentHashMap）或乐观锁
- 引申：分布式场景下还有数据库锁、分布式锁的排查

**考察点：** 能否区分两类问题的表现特征和对应解法

## 面试简短高频问答总结（口述版）

1. JVM 内存分为线程私有（程序计数器、虚拟机栈、本地方法栈）；线程共享堆、元空间。
2. GC 判断垃圾使用**可达性分析**，GC Roots。
3. 收集器：Parallel 吞吐量优先；CMS 低停顿有碎片；G1 可预测停顿；ZGC 几乎无停顿。
4. STW：GC 暂停业务线程；CMS 只有初始标记、重新标记 STW。
5. OOM 常见几种：堆溢出、元空间、堆外内存、线程过多。
6. 排查工具：jps/jstat/jmap/jstack；MAT、Arthas。
7. 类加载 5 步：加载、验证、准备、解析、初始化；双亲委派模型。

# 分析工具

## MAT

### Q1：MAT 是什么？

> A：Eclipse 开源免费离线堆分析工具，解析 hprof 堆快照，定位 OOM、内存泄漏；只本地使用，不上生产服务器。

### Q2：浅堆和深堆区别？

> A：浅堆是对象本身内存；深堆是回收对象后总共释放内存，排查泄漏看深堆 Retained Heap。

### Q3：Path to GC Roots 为什么要排除弱 / 软 / 虚引用？

> A：弱软虚引用 GC 可以回收；内存泄漏是**强引用**无意持有对象，只看强引用链。

### Q4：Leak Suspects Report 和 Dominator Tree 区别？

> A：Leak Suspects 是 MAT 自动给出嫌疑报告，快速定位；Dominator Tree 手动分析支配关系，精准定位泄漏根源。

### Q5：为什么不建议用 arthas heapdump 做泄漏分析？

> A：会把 arthas agent、netty 对象写入 dump，干扰业务对象分析；优先使用 OOM 自动 dump。

## Arthas

1. Arthas 是临时诊断工具，**排查结束一定要执行`stop`卸载 agent，不要常驻**。
2. trace/watch 会字节码增强，高频方法会带来性能开销，尽量加`‑n`限制采样次数。
3. heapdump、profiler 会消耗 CPU/IO，避开业务高峰。
4. attach 时必须和目标 Java 进程**同一个操作系统用户**，否则挂载失败。
5. 不建议直接在公网暴露 Arthas web 控制台（默认 8563 端口），有安全风险

## JMC

> JMC 是 JDK 自带的性能分析工具，搭配**JFR（Java Flight Recorder）飞行记录器**，用于采集 JVM 运行数据，分析性能、内存、GC、线程、锁竞争。 注意：JDK8 需要单独下载 JMC；JDK11 + 内置 JMC。

### 1. 什么是 JMC？什么是 JFR？两者关系？

**JFR（Java Flight Recorder）**：JVM 内置的**事件采集器**，低开销，记录 JVM 内部事件（GC、线程、锁、IO、内存分配、方法执行）。 **JMC（Java Mission Control）**：可视化客户端，用来**打开、分析 JFR 录制出来的`.jfr`文件**。

> 关系：**JFR 负责采集数据，JMC 负责可视化分析**。 JFR 开销很低，生产环境可以开启，性能损耗通常 < 1%。

### 2. JFR 和 heapdump、jstack、arthas 对比？

表格

| 工具            | 用途                                                | 特点                                                         |
| --------------- | --------------------------------------------------- | ------------------------------------------------------------ |
| **JFR**         | 全维度 JVM 事件采集，性能分析、内存、锁、GC、慢方法 | **低开销，生产可用，时序数据**，可以回放完整过程；不是 dump 快照，是事件流。 |
| heapdump(hprof) | 堆内存快照，分析 OOM、内存泄漏                      | 瞬间快照，体积大，**只能看某一时刻**，无法看过程；开销高。   |
| jstack          | 线程栈快照，死锁、线程阻塞                          | 瞬时快照，只能看那一刻线程状态。                             |
| Arthas          | 在线诊断，实时查看指标、方法采样                    | 在线 attach，适合临时排查；**不保存完整时序事件**。          |

> 重点：JFR 是**时序事件记录**，可以看一段时间内发生了什么；heapdump 是某一瞬间的 “照片”。

### 3. JFR 的开启方式？

1. JDK8：需要下载 JMC，JFR 需要开启 JVM 参数

```
-XX:+FlightRecorder
-XX:StartFlightRecording=duration=60s,filename=recording.jfr
```

1. JDK11+：内置 JFR，命令行直接启动录制

```
jcmd <pid> JFR.start duration=60s filename=recording.jfr
jcmd <pid> JFR.stop
jcmd <pid> JFR.dump filename=recording.jfr
```

### 4. JFR 录制有哪些模式？

- **持续录制（Continuous recording）**：循环保存事件，保留最近一段时间数据，生产环境常用。
- **限时录制**：指定 duration，录制一段时间后停止输出 jfr 文件。
- **一次性录制**：手动启动停止。

### 5. JFR 的开销大吗？生产环境能不能用？

> 官方：**正常开启 JFR 性能损耗一般 0.5‑1%**，生产环境可以使用。 不要开启全部事件，只开启需要的事件；不要录制过大的时间窗口。

### 6. JMC 可以分析哪些问题？

1. **GC 问题**：GC 停顿时间、GC 频率、大对象分配、TLAB 分配；
2. **内存问题**：对象分配热点，哪些类大量创建对象；
3. **线程问题**：锁竞争、线程阻塞、线程等待、死锁、线程池状态；
4. **CPU 问题**：CPU 热点方法，采样分析哪些方法占用 CPU；
5. **IO 问题**：文件 IO、网络 IO；
6. **JVM 内部**：类加载、编译、逃逸分析。

### 7. JFR 和 MAT 的区别？

- **JFR/JMC**：**时序事件**，看一段时间内的**动态过程**；可以看对象分配的行为、什么时候分配、哪个线程分配。**不能直接定位内存泄漏**。
- **MAT**：分析 hprof 堆快照，**某一瞬间堆对象全貌**，专门用来排查**内存泄漏**。

> 组合使用：JFR 观察内存分配行为；如果怀疑泄漏，导出 heapdump 用 MAT 分析。

### 8. JFR 中什么是对象分配采样（Allocation Sample）？

JFR 可以采样对象分配事件，统计**哪个线程、哪个方法分配了大量对象**。

> 注意：是**采样**不是全部记录，减少开销；可以定位 “热点分配”，找到大量创建对象的代码。

### 9. 什么是大对象（Large Object）？JFR 如何发现？

大于 `-XX:PretenureSizeThreshold` 的对象直接分配到老年代。 JFR 会记录大对象分配事件，可以看到哪些代码直接创建大对象，导致老年代快速膨胀。

### 10. JMC 中如何定位 CPU 高的问题？

打开 JFR 文件 → **Method Profiling（方法分析）** 看**Self Time（自身时间）**，代表方法本身消耗 CPU，排除调用子方法时间。

> 区分：Total Time（总时间，包含子调用）；Self Time（方法自身耗时）。

### 11. 如何定位锁竞争（锁等待高）？

JMC 的**Lock Contention（锁竞争）**视图。 看到哪些锁发生大量竞争，线程等待锁的时间，定位 synchronized/Lock 锁的热点。

### 12. JFR 和 AsyncProfiler 对比？

- JFR：JVM 内置，不需要额外 agent，事件完整（GC、线程、IO、编译），开销低；但是采样粒度有限。
- AsyncProfiler：第三方，CPU 采样、火焰图，性能极强；需要引入 agent；不包含 GC/JVM 内部事件。

### 13. JFR 录制时，怎么避免生成超大 jfr 文件？

1. 设置`maxsize`最大文件大小；
2. 使用持续录制，只保留最近窗口；
3. 关闭不需要的事件，只启用需要的事件；
4. 不要录制过长时间。

### 14. JFR 能不能用来排查内存泄漏？

> ❗不能直接定位内存泄漏。 JFR 只能看到**对象分配行为**：哪里大量创建对象。 但是无法判断对象是否被回收。 内存泄漏必须要 heapdump + MAT。

### 15. JDK8 和 JDK11+ JMC/JFR 差异

1. JDK8：JMC 是独立下载工具；JFR 需要开启`‑XX:+FlightRecorder`，部分功能有限；
2. JDK11+：JMC 内置在 JDK 中；JFR 大幅优化，事件更多，命令行`jcmd`操作更方便。

### Q：线上 CPU 很高，你会怎么排查？

1. 先用`top`确认进程 CPU；
2. 可选：jstack 看线程栈；
3. **使用 JFR 录制一段时间，用 JMC 打开，查看 Method Profiling，看 Self Time 高的方法，定位热点代码**。

> 或者使用 AsyncProfiler 生成火焰图。

### Q：线上老年代持续上涨，怀疑内存泄漏？

1. JFR 看对象分配热点，看哪里大量创建对象；
2. 触发 OOM 时，用`‑XX:+HeapDumpOnOutOfMemoryError`导出 hprof；
3. MAT 分析 hprof，定位泄漏根源。

### Q：线上线程阻塞，大量线程 WAITING/BLOCKED？

1. jstack 看线程状态；
2. JFR 录制，看 Lock Contention 锁竞争视图，定位竞争锁。

### 易错坑点

1. JFR 是**事件采样，不是全部记录**，不是 100% 全部捕获；
2. JFR 不能替代 MAT 做内存泄漏分析；
3. JMC 分析的是`.jfr`文件，**不是 hprof 文件**；MAT 分析 hprof；
4. JFR 的开销虽然低，但不要在生产开启全部事件。
