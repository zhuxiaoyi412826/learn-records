# 第一部分　架构与环境规划

## 1.1 整体架构拓扑

一次用户请求在大型微服务体系中的完整路径如下：

```
用户 (App / Web / 小程序)
   │  HTTPS
   ▼
DNS 解析 ──▶ CDN（静态资源、图片、页面加速）
   │
   ▼
WAF（防 CC、防 SQL 注入、防爬虫）
   │
   ▼
负载均衡 SLB / Keepalived + Nginx（四层/七层转发、健康检查）
   │
   ▼
网关集群 Spring Cloud Gateway / APISIX（统一鉴权、限流、灰度路由、协议转换）
   │           ▲ 依赖 Nacos 做服务发现
   │  ┌────────┴─────────┬──────────────┬──────────────┐
   ▼  ▼                  ▼              ▼              ▼
用户服务           订单服务          商品服务        支付服务   …（20~200 个服务）
   │                  │              │              │
   │  服务间调用 OpenFeign / Dubbo，熔断降级 Sentinel
   ▼
数据与中间件层
   MySQL 主从（+ ShardingSphere 分库分表）
   Redis Cluster（缓存 / 分布式锁 / Session）
   RocketMQ / Kafka（异步、削峰、解耦）
   Elasticsearch（检索、日志）
   MinIO / OSS（文件对象存储）

横切支撑层（所有服务共用）
   Nacos（注册中心 + 配置中心）
   Seata（分布式事务）
   XXL-Job（分布式任务调度）
   Prometheus + Grafana（指标监控）
   ELK / EFK（日志收集检索）
   SkyWalking（全链路追踪）
   Harbor + GitLab CI / Jenkins + Argo CD（CI/CD）
```

各层职责与常见替代方案：

| 层级 | 默认选型 | 核心职责 | 常见替代 |
| --- | --- | --- | --- |
| 接入层 | CDN + WAF + SLB | 流量入口、安全防护、四层转发 | 云厂商自带，或 Nginx + Keepalived 自建 |
| 网关层 | Spring Cloud Gateway | 路由、鉴权、限流、灰度 | APISIX、Kong、Higress |
| 服务层 | Spring Boot / Spring Cloud Alibaba | 业务逻辑 | Dubbo、gRPC |
| 注册配置 | Nacos | 服务发现、动态配置 | Consul、Eureka、Apollo、Zookeeper |
| 熔断限流 | Sentinel | 流控、熔断、热点防护 | Resilience4j、Hystrix（已停更） |
| 数据层 | MySQL 主从 | 持久化 | PostgreSQL |
| 缓存 | Redis Cluster | 缓存、锁、计数 | Memcached、本地缓存 Caffeine |
| 消息 | RocketMQ | 异步解耦、削峰 | Kafka、RabbitMQ、Pulsar |
| 可观测 | Prometheus / ELK / SkyWalking | 指标、日志、链路 | VictoriaMetrics、Loki、Zipkin、Jaeger |

## 1.2 环境划分

大型项目至少四个环境，物理隔离或用 K8s Namespace 隔离：

| 环境 | 用途 | 数据 | 配置来源 | 谁能发布 |
| --- | --- | --- | --- | --- |
| dev | 开发联调 | 造数 | Nacos namespace: dev | 开发自助 |
| test | 功能测试、自动化回归 | 脱敏后导入 | Nacos namespace: test | 测试触发流水线 |
| staging（预发） | 上线前最后验证，与生产同版本中间件 | 生产脱敏数据 | Nacos namespace: staging | 发布负责人 |
| prod | 对外服务 | 真实数据 | Nacos namespace: prod | 审批后流水线 |

预发环境的机器规格、中间件版本、JVM 参数要与生产一致，只缩小规模。否则会出现"预发正常、上线就崩"的经典事故。

多环境隔离的三种手段，按隔离强度排列：

1. 独立 K8s 集群（大型团队，成本最高，隔离最彻底）
2. 同集群不同 Namespace + ResourceQuota（主流做法）
3. 同 Namespace 用 label 区分（只适合小团队，不推荐）

## 1.3 服务器集群规划

以日活百万级电商、约 40 个微服务为参考，生产环境机器规划：

| 用途 | 数量 | 参考规格 | 部署内容 | 高可用要求 |
| --- | --- | --- | --- | --- |
| K8s Master | 3 | 4C8G SSD | kube-apiserver、etcd、调度器 | 3 节点保证 etcd 多数派 |
| K8s Worker | 6~12 | 16C64G | 业务服务 Pod | 跨可用区打散 |
| MySQL | 2 起 | 16C64G SSD（IO 性能优先） | 主从，大促再挂只读副本 | 主从 + 半同步 + MHA/Orchestrator 自动切换 |
| Redis | 6 | 8C16G | Cluster（3 主 3 从）或哨兵 3 节点 | Cluster 自动故障转移 |
| RocketMQ | 3 起 | 8C16G SSD | NameServer 2 节点 + Broker 主从 | 主从同步复制 |
| Nacos | 3 | 4C8G | 注册 + 配置中心集群 | 3 节点 + 内嵌/外置 MySQL |
| 监控日志 | 3~5 | 8C32G，大容量数据盘 | Prometheus、Grafana、ES、Kibana、SkyWalking OAP | ES 3 节点起步 |
| MinIO | 4 起 | 普通盘大容量 | 对象存储 | 纠删码或副本 |
| CI/CD | 2 | 8C16G | GitLab、Jenkins、Harbor | 可接受短暂不可用 |

规划时遵循三条原则：

- 无单点：任何组件至少两个实例，跨可用区部署。
- 存算分离：有状态服务（MySQL、Redis、MQ）独立于 K8s 业务节点或独立维护，避免业务 Pod 抢占 IO。
- 容量留余：常态资源使用率控制在 60% 以下，给突发流量和故障转移留余量。

## 1.4 网络与安全

- VPC 内网互通，公网只暴露 SLB 入口和堡垒机，其余端口一律不开公网。
- 安全组按最小开放原则：网关安全组只放行 SLB 网段，服务间只放行内网。
- SSH 关闭密码登录，只留密钥；生产机器通过堡垒机跳转，操作留审计录像。
- 敏感信息（数据库密码、云 AK/SK）放 K8s Secret 或 Nacos 加密配置，禁止明文进 Git 仓库，密钥定期轮换。
- 内部服务间调用可启用 mTLS（服务网格 Istio 或 APISIX 上配）。

# 第二部分　生产环境完整软件栈

## 2.1 系统层

操作系统选 Ubuntu Server 22.04 / CentOS Stream 9（或 Alibaba Cloud Linux、OpenEuler），最小化安装无图形界面。基础工具清单：

| 工具 | 核心用途 | 排错场景 |
| --- | --- | --- |
| vim | 修改配置文件 | 改 yml、nginx、redis 配置 |
| curl | HTTP 接口调试 | 测试 SpringBoot 健康接口，排查接口不通 |
| wget | 下载文件 | 下载 JDK、安装包、脚本 |
| net-tools | 网络端口查询 | netstat 看 8080、3306 端口是否监听 |
| htop | CPU 内存进程监控 | 看 Java 进程内存占用，OOM 时定位 |
| iostat | 磁盘 IO 性能 | 排查 MySQL 慢、磁盘读写瓶颈 |
| rsync | 增量文件备份同步 | 备份数据库、日志、项目文件 |
| sysstat 全套 | sar、pidstat、mpstat | 历史性能回溯、进程级定位 |
| lsof | 文件句柄 | 找端口被谁占用、已删除未释放的文件 |
| tcpdump | 抓包 | 网络不通时的最终手段 |

安全层三件套：防火墙 firewalld/ufw、fail2ban 防暴力破解、SSH 密钥登录。

文件句柄与内核参数是 Java 服务最容易踩的坑，部署时统一调整：

```bash
# /etc/security/limits.conf
* soft nofile 655350
* hard nofile 655350
* soft nproc  655350

# /etc/sysctl.conf 常用项
net.ipv4.tcp_tw_reuse = 1          # TIME_WAIT 快速回收（仅客户端侧连接）
net.core.somaxconn = 65535
vm.swappiness = 1                  # 尽量不用 swap，交换会让 GC 停顿暴涨
net.ipv4.ip_local_port_range = 1024 65535
```

## 2.2 Java 运行时

- JDK 选 LTS 版本：JDK 8（存量）、JDK 17（当前主流）、JDK 21（虚拟线程）。发行版选 OpenJDK / Amazon Corretto / Temurin，生产不用 Oracle 商业授权版。
- SpringBoot 内嵌 Tomcat，不需要单独装 Tomcat 容器；只有老式 SSM 打 war 包的项目才外置 Tomcat。
- 容器化部署注意：JDK 8u191+ 与 JDK 10+ 才能正确感知容器 CPU/内存限制，否则 JVM 会按宿主机内存计算默认堆大小。

生产 JVM 参数模板（4C8G 容器、G1 收集器）：

```bash
java -Xms4g -Xmx4g \
  -XX:MaxMetaspaceSize=512m \
  -XX:+UseG1GC -XX:MaxGCPauseMillis=200 \
  -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump/ \
  -Xlog:gc*:file=/data/logs/gc-%t.log:time,uptime,level,tags:filecount=10,filesize=50m \
  -XX:+ExitOnOutOfMemoryError \
  -jar app.jar
```

参数要点：

| 参数 | 作用 | 说明 |
| --- | --- | --- |
| -Xms = -Xmx | 堆初始等于最大 | 避免运行期扩容抖动 |
| -XX:+UseG1GC | G1 收集器 | JDK 9+ 默认；大堆低延迟首选 |
| -XX:MaxGCPauseMillis | 目标停顿 | 200ms 起步，按 SLA 调 |
| HeapDumpOnOutOfMemoryError | OOM 自动导堆 | 线上排查 OOM 的第一手证据 |
| -Xlog:gc* | GC 日志 | 排查 GC 问题的唯一依据，必须开 |
| ExitOnOutOfMemoryError | OOM 直接退出 | 配合 K8s 重启拉起，避免半死不活 |

容器场景更推荐用百分比代替固定值：`-XX:MaxRAMPercentage=70.0`，同一镜像可跑不同规格机器。

## 2.3 容器与编排

| 组件 | 版本建议 | 说明 |
| --- | --- | --- |
| Docker / containerd | 24+ | 打包与运行时；K8s 1.24 后默认 containerd |
| Kubernetes | 1.28+ | 集群编排；二进制或 kubeadm 自建，云上直接用托管（ACK/EKS/TKE） |
| Harbor | 2.x | 私有镜像仓库，带漏洞扫描与镜像同步 |

自建 K8s 与云托管的选择：中小团队直接用云托管 Master，省掉 etcd 运维；只有强合规要求才自建。

## 2.4 微服务中间件

| 中间件 | 解决的问题 | 生产要点 |
| --- | --- | --- |
| Nacos | 服务注册发现 + 动态配置 | 3 节点集群，配置持久化到 MySQL；客户端心跳 5s，15s 未收到即摘除实例 |
| Spring Cloud Gateway | 南向流量入口 | 网关无状态多副本，超时配置要小于前端超时 |
| OpenFeign / Dubbo | 服务间调用 | 配连接池与超时重试，重试要保证下游幂等 |
| Sentinel | 熔断、限流、热点防护 | 规则持久化到 Nacos，否则重启丢失 |
| Seata | 分布式事务 | AT 模式最常用，注意 undo_log 表与全局锁 |
| XXL-Job | 定时任务调度 | 调度中心 HA，执行器自动注册，失败重试与告警 |

## 2.5 数据层

### MySQL

- 版本 8.0，一主一从起步，写多读少时再加只读副本。
- 主从复制用半同步（semi-sync）降低丢数据风险，配 Orchestrator/MHA 做自动故障切换。
- 每日 mysqldump 或 XtraBackup 全量 + binlog 增量，备份要定期演练恢复。
- 必开：慢查询日志、binlog（ROW 格式）、audit 插件（视合规要求）。
- 单表超过 500 万行或 20GB 后考虑分库分表（ShardingSphere），或先归档历史数据。

### Redis

三种部署形态对比：

| 形态 | 最小节点 | 适用 | 特点 |
| --- | --- | --- | --- |
| 主从 + 哨兵 | 2 数据 + 3 哨兵 | 数据量中等，写少读多 | 部署简单，容量受单机限制 |
| Cluster | 3 主 3 从 | 数据量大、QPS 高 | 16384 槽分片，自动故障转移，客户端要求高 |
| 单机 | 1 | 测试/缓存允许丢 | 禁止生产使用 |

### Elasticsearch

业务检索与日志检索二选一场景时分开部署：日志场景写量大，会拖垮业务检索集群。

## 2.6 消息队列选型

| 维度 | RocketMQ | Kafka | RabbitMQ |
| --- | --- | --- | --- |
| 吞吐 | 十万级/秒 | 百万级/秒 | 万级/秒 |
| 延迟 | 毫秒级 | 毫秒级（攒批影响） | 微秒级 |
| 功能 | 事务消息、延迟消息、重试队列 | 流式处理生态强 | 路由灵活、管理界面友好 |
| 典型场景 | 电商交易类异步 | 日志采集、大数据管道 | 中小团队业务异步 |

业务量达到日均百万订单以上必须上 MQ，用来做短信、邮件、日志、订单异步处理与削峰填谷；小型单体项目可以暂缓。

## 2.7 对象存储

| 方案 | 适用 | 说明 |
| --- | --- | --- |
| 本地磁盘 + Nginx | 小项目、临时 | 无高可用，机器挂即丢 |
| MinIO 自建 | 中大型、私有化 | S3 协议，纠删码保护，成本低 |
| 阿里云 OSS / 腾讯云 COS | 云上项目 | 免运维，配合 CDN 使用，按量付费 |

## 2.8 可观测性三支柱

线上排查能力完全取决于这三套系统建得好不好，属于"平时不用、出事救命"的基建：

| 支柱 | 组件组合 | 回答的问题 |
| --- | --- | --- |
| Metrics 指标 | Prometheus + Grafana + Alertmanager | 现在是否有问题？哪里不正常？ |
| Logging 日志 | Filebeat → Kafka → Logstash → ES → Kibana（EFK） | 具体错在哪一行？当时发生了什么？ |
| Tracing 链路 | SkyWalking / Zipkin / Jaeger | 一个慢请求，时间花在了哪个服务哪一段？ |

SpringBoot 侧接入方式：Actuator + Micrometer 暴露 `/actuator/prometheus` 给 Prometheus 抓取；日志用 logback 输出带 traceId 的 JSON 格式；SkyWalking 用 `skywalking-agent` 的 `-javaagent` 无侵入接入。

轻量替代方案：日志量不大时用 Loki + Grafana 替代 ELK，运维成本显著更低。

# 第三部分　部署全流程

## 3.1 分支与版本管理

大型项目推荐简化版 GitFlow：

| 分支 | 生命周期 | 用途 | 合并方向 |
| --- | --- | --- | --- |
| main / master | 永久 | 与生产运行版本对应，打 tag | release → main |
| release/x.y | 发布周期内 | 集成测试、预发验证 | develop → release → main |
| develop | 永久 | 日常集成 | feature → develop |
| feature/xxx | 短 | 单个功能开发 | 从 develop 拉出，合并回 develop |
| hotfix/xxx | 紧急 | 生产紧急修复 | 从 main 拉出，同时回合 main 和 develop |

版本号规范 `主版本.次版本.修订号`（如 2.3.1），镜像 tag 与 Git tag 一一对应，保证任何线上版本都能追溯到确切代码。

## 3.2 CI/CD 流水线

主流方案：GitLab CI（自建 GitLab 自带）、Jenkins（老牌灵活）、云效/CodeArts（云上）、Argo CD（GitOps，声明式发布，K8s 环境首选组合是 GitLab CI 负责构建 + Argo CD 负责部署）。

一条标准流水线的阶段：

| 阶段 | 动作 | 失败处理 |
| --- | --- | --- |
| 1 提交触发 | push / MR 触发 | — |
| 2 门禁 | 编译、单元测试、SonarQube 静态扫描、代码规范 | 阻断合入 |
| 3 构建镜像 | 多阶段构建出镜像，打 `分支-commitID-时间戳` tag | 中止 |
| 4 推送 Harbor | 镜像入库，触发漏洞扫描 | 高危漏洞阻断 |
| 5 部署 test | 自动更新 test 环境 | 通知开发 |
| 6 自动化验证 | 接口自动化、冒烟测试 | 阻断 |
| 7 部署 staging | 自动或一键 | 阻断 |
| 8 人工审批 | 发布负责人确认变更单 | 阻断 |
| 9 部署 prod | 灰度发布（见 3.6） | 自动回滚 |
| 10 线上验证 | 健康检查、核心接口拨测 | 自动回滚 |

GitLab CI 示例（.gitlab-ci.yml 核心片段）：

```yaml
stages: [build, package, deploy]

build:
  stage: build
  image: maven:3.9-eclipse-temurin-17
  script:
    - mvn clean package -DskipTests -pl order-service -am
  artifacts:
    paths: [order-service/target/*.jar]

package:
  stage: package
  image: docker:24
  script:
    - docker build -t harbor.local/shop/order-service:$CI_COMMIT_SHORT_SHA .
    - docker push harbor.local/shop/order-service:$CI_COMMIT_SHORT_SHA

deploy-prod:
  stage: deploy
  when: manual          # 人工审批点
  script:
    - kubectl set image deployment/order-service
        order-service=harbor.local/shop/order-service:$CI_COMMIT_SHORT_SHA -n prod
    - kubectl rollout status deployment/order-service -n prod --timeout=5m
```

## 3.3 镜像构建规范

多阶段构建 Dockerfile 示例：

```dockerfile
# 第一阶段：构建
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline          # 依赖层单独缓存，代码改动不重下依赖
COPY src ./src
RUN mvn package -DskipTests

# 第二阶段：运行
FROM eclipse-temurin:17-jre
WORKDIR /app
RUN useradd -r appuser && mkdir -p /data/logs && chown -R appuser /data
COPY --from=builder /app/target/*.jar app.jar
USER appuser
EXPOSE 8080
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=70.0", "-jar", "app.jar"]
```

镜像规范要点：

| 规范 | 原因 |
| --- | --- |
| 禁止用 latest tag，一律 commitID 或版本号 | latest 无法回滚、无法追溯 |
| 多阶段构建，运行层只留 JRE | 镜像从 1GB 降到 300MB，拉取快、攻击面小 |
| 非 root 用户运行 | 容器逃逸时降低风险 |
| 基础镜像统一维护、定期更新 | 修 CVE、统一时区 |
| 不往镜像里塞配置与密码 | 配置走 Nacos/ConfigMap，密码走 Secret |
| 镜像里预置 arthas-boot.jar | 线上排障可以直接 exec 进容器使用 |

不想写 Dockerfile 的团队可以用 Jib 插件，Maven 直接产出分层镜像。

## 3.4 K8s 部署清单

一份生产可用的核心 YAML（省略了 namepace 等上下文）：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  namespace: prod
spec:
  replicas: 4
  revisionHistoryLimit: 5              # 保留 5 个历史版本供回滚
  strategy:
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }   # 不停机滚动
  selector:
    matchLabels: { app: order-service }
  template:
    metadata:
      labels: { app: order-service }
    spec:
      terminationGracePeriodSeconds: 60
      containers:
        - name: order-service
          image: harbor.local/shop/order-service:a1b2c3d
          ports: [{ containerPort: 8080 }]
          env:
            - name: JAVA_OPTS
              value: "-XX:MaxRAMPercentage=70.0 -Xlog:gc*"
            - name: SPRING_PROFILES_ACTIVE
              value: prod
          resources:
            requests: { cpu: "1", memory: 2Gi }    # 与 HPA 联动
            limits:   { cpu: "2", memory: 3Gi }
          readinessProbe:                          # 就绪：没通过就不接流量
            httpGet: { path: /actuator/health/readiness, port: 8080 }
            initialDelaySeconds: 30
            periodSeconds: 5
            failureThreshold: 3
          livenessProbe:                           # 存活：失败就重启
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            initialDelaySeconds: 60
            periodSeconds: 10
            failureThreshold: 5
          lifecycle:
            preStop:                               # 优雅下线：先摘流量再停进程
              exec: { command: ["sh", "-c", "sleep 10"] }
---
apiVersion: v1
kind: Service
metadata:
  name: order-service
  namespace: prod
spec:
  selector: { app: order-service }
  ports: [{ port: 80, targetPort: 8080 }]
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service
  namespace: prod
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: order-service }
  minReplicas: 4
  maxReplicas: 12
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 65 } }
```

关键字段与线上稳定性直接相关：

| 字段 | 作用 | 配置不当的后果 |
| --- | --- | --- |
| maxUnavailable: 0 | 滚动发布不减少可用副本 | 发布瞬间掉容量、雪崩 |
| readinessProbe | 只让健康 Pod 接流量 | 启动慢的服务被过早接入，5xx 尖刺 |
| livenessProbe | 挂死自动重启 | 探针太敏感会误杀；一定要与 readiness 分开路径 |
| preStop + 优雅停机 | 先摘流量再杀进程 | 发布时网关仍有请求打到正在退出的实例 |
| resources.requests | 调度与 HPA 基准 | 配低会被"超卖"节点打爆 |
| PodDisruptionBudget | 驱散保护 | 节点维护时一次性杀掉多副本 |

## 3.5 数据库变更管理

禁止手工在 DBA 端口直连生产改表，全部通过版本化脚本随流水线执行（Flyway / Liquibase）：

```sql
-- V20260826_01__add_order_remark.sql
ALTER TABLE t_order ADD COLUMN remark VARCHAR(512) DEFAULT NULL COMMENT '订单备注';
```

大表变更规则：

- 千万行级大表禁止直接 ALTER，用 gh-ost 或 pt-online-schema-change 在线改表。
- 变更窗口避开业务高峰，DDL 前确认主从延迟状态。
- 回滚脚本与正向脚本一起提交评审。

## 3.6 发布策略与回滚

| 策略 | 做法 | 停机 | 回滚速度 | 资源成本 | 适用 |
| --- | --- | --- | --- | --- | --- |
| 滚动 | 逐批替换实例 | 无 | 分钟级 | 低 | 常规版本 |
| 蓝绿 | 两套环境切流量 | 秒级切换 | 秒级（切回） | 2 倍 | 大版本、基础设施升级 |
| 金丝雀灰度 | 5% 流量先跑新版本 | 无 | 分钟级 | 低 | 高风险变更 |
| 按标签灰度 | 白名单用户/地区先行 | 无 | 分钟级 | 低 | To C 大功能 |

灰度发布实现方式：网关按请求头（灰度标）路由到打了 `version: canary` 标签的 Pod；或使用 Flagger/Argo Rollouts 自动化渐进式交付（5% → 25% → 50% → 100%，指标异常自动回滚）。

线上 80% 的故障由发布引起，因此回滚要当成一等公民设计：镜像 tag 可追溯 + revisionHistoryLimit 保留历史 + 一条命令回滚：

```bash
kubectl rollout undo deployment/order-service -n prod
# 回到指定版本
kubectl rollout undo deployment/order-service -n prod --to-revision=3
```

Nacos 配置组织约定：

- group 按团队或大业务域：`TRADE_GROUP`、`USER_GROUP`。
- dataId 命名：`order-service-prod.yaml`，公共配置抽 `common-redis-prod.yaml` 用 `spring.config.import` 的 extension-configs 共享。

# 第四部分　线上问题排查

## 4.1 排查总纲

线上问题的标准定位路径——先看"面"再看"点"，从入口逐层下钻：

```
告警/用户报障
   │
   ▼ ① Grafana 大盘：错误率、P99、QPS 哪个服务异常？（1 分钟）
   │
   ▼ ② 网关日志：报错集中在哪个接口、哪个上游？（1 分钟）
   │
   ▼ ③ SkyWalking：挑一条慢/失败 trace，看时间花在哪个服务哪一段（2 分钟）
   │
   ▼ ④ 定位到具体服务后，三选一下钻：
   │     ├─ 应用层：ELK 查该服务日志（按 traceId）
   │     ├─ JVM 层：Arthas / jstack / jstat（CPU、GC、线程）
   │     └─ 依赖层：MySQL / Redis / MQ 的对应指标与日志
   ▼ ⑤ 确认根因 → 止血 → 修复 → 复盘
```

下钻顺序的三条经验法则：

1. 最近有发布先怀疑发布——80% 故障与变更相关，先回滚再定位，不与业务赌命。
2. 先看监控再登机器——大部分问题在 Grafana/SkyWalking 上五分钟内可见，登服务器是最后手段。
3. 保留现场再动手——重启前先 `jstack` + `jmap` 留 dump，现场没了就只剩猜测。

黄金四指标（Google SRE），所有服务告警围绕它们配置：

| 指标 | 含义 | 异常说明 |
| --- | --- | --- |
| 延迟 Latency | P50/P95/P99 响应时间 | 变慢即容量或依赖问题 |
| 流量 Traffic | QPS / MQ 消息速率 | 突增即攻击或运营活动 |
| 错误 Errors | HTTP 5xx 比例、业务错误码 | 最直接的故障信号 |
| 饱和度 Saturation | CPU、内存、连接池、队列深度 | 水位高是故障前兆 |

## 4.2 系统层排查

### CPU 高

```bash
top                     # 全局：哪个进程 CPU 高，load 是否超核数
top -Hp <pid>           # 该进程内哪个线程 CPU 高（衔接 4.3 JVM 定位）
pidstat -u -p <pid> 1   # 进程 CPU 按线程持续观察
vmstat 1                # r 列（等待运行的进程数，持续大于 CPU 核数即过载）、cs 上下文切换
mpstat -P ALL 1         # 各核分布；%soft 高说明软中断（网络）
```

看懂 top 的 CPU 分布再下结论：

| 列 | 含义 | 高的常见原因 |
| --- | --- | --- |
| us | 用户态 | 业务代码死循环、正则回溯、GC 线程也算用户态 |
| sy | 内核态 | 系统调用频繁、线程上下文切换过多、锁竞争自旋 |
| wa | IO 等待 | 磁盘慢，MySQL、日志写阻塞的典型表现 |
| si | 软中断 | 网络包处理（高流量、SYN 洪泛） |
| st | 被虚拟化偷走 | 宿主机超卖，云上机器常见 |

### 内存高 / OOM

```bash
free -h                          # 看 available，不是看 free；buff/cache 可回收
ps aux --sort=-%mem | head -5    # 内存大户
dmesg -T | grep -i -E 'out of memory|killed process'   # OS 级 OOM Killer 记录
```

区分两种 OOM：`dmesg` 里有 Killed process 是操作系统 OOM Killer 杀的（容器场景对应 K8s 的 OOMKilled，exitCode 137）；只有 Java 日志里有 `OutOfMemoryError` 才是 JVM 堆 OOM。两者处理方向完全不同——前者是容器 limit 与 JVM 参数不匹配，后者是代码内存问题。

### 磁盘问题

```bash
df -h                             # 空间；df -i 看 inode 是否耗尽（海量小文件场景）
du -h --max-depth=1 /data 2>/dev/null | sort -hr | head    # 逐层找大目录
iostat -x 1                       # %util 接近 100% 即磁盘饱和，await 为 IO 等待毫秒数
iotop -o                          # 哪个进程在疯狂读写
lsof | grep deleted               # 已删除但仍被进程持有句柄的文件（日志 rm 后空间不释放）
```

磁盘写满的典型后果与处理：日志写满导致服务卡死（清日志注意用 `truncate -s 0` 或删后 `> /proc/<pid>/fd/<n>`，正在写的文件直接 rm 不释放空间）、MySQL binlog 满导致写库报错（`PURGE BINARY LOGS` 并调整 `expire_logs_days`）。

### 网络不通

```bash
ping <ip>                        # 三层连通
mtr <ip>                         # 链路逐跳丢包定位（比 tracert 好用）
telnet <ip> <port>               # 四层端口通不通；或 nc -zv <ip> <port>
ss -tlnp                         # 本机监听端口与所属进程
ss -s                            # 连接数总览；TIME_WAIT 异常时排查连接模式
tcpdump -i any host <ip> and port <port> -w dump.pcap   # 终极手段抓包
netstat -s | grep -i retrans     # 重传计数，判断网络质量
curl -v -w '\ntime_total=%{time_total}s\n' http://<url>  # 应用层验证与耗时分解
```

连通性排查顺序固定为：ping（网络层）→ telnet（传输层）→ curl（应用层），从下往上定位断点。K8s 网络问题见 4.8。

## 4.3 JVM 层排查

命令行工具一览：

| 工具 | 用途 | 备注 |
| --- | --- | --- |
| jps | 找 Java 进程 PID | 容器内用 `ps -ef` |
| jstat -gcutil <pid> 1000 | 每秒输出 GC 情况 | 看 O、E、YGC、FGC 趋势 |
| jstack <pid> | 线程 dump | 死锁、线程阻塞、CPU 高定位 |
| jmap -dump | 堆 dump | 生产大堆会长时间 STW，低峰执行 |
| jmap -histo <pid> | 堆内对象直方图 | 比 dump 轻，先看这个 |
| jinfo | 查看/修改 JVM 参数 | 运行期开 GC 日志 |
| Arthas | 一体化诊断（推荐） | 无侵入 attach，功能覆盖上面所有 |

### 场景一　CPU 100%

标准四步，两分钟内定位到代码行：

```bash
# 1. 找到 CPU 最高的 Java 进程
top
# 2. 找到该进程里 CPU 最高的线程
top -Hp <pid>
# 3. 线程号转 16 进制
printf '%x\n' <tid>
# 4. 在线程栈里搜这个 16 进制线程号
jstack <pid> | grep <hex_tid> -A 30
```

Arthas 等价操作更快：

```bash
curl -O https://arthas.aliyun.com/arthas-boot.jar
java -jar arthas-boot.jar            # 选择目标进程
[arthas]$ thread -n 3                 # 最忙的 3 个线程直接给出栈
[arthas]$ thread <tid>                # 看单个线程详情
```

栈内容判读：

| 栈中看到 | 结论 | 处理 |
| --- | --- | --- |
| 业务代码循环/正则 | 死循环、正则回溯、大集合遍历 | 修复代码 |
| GC 线程（GC task thread） | CPU 被 GC 吃掉，本质是内存问题 | 转 OOM/内存排查 |
| JIT 编译线程（C2 CompilerThread） | 预热期正常现象 | 观察是否自行恢复 |
| 锁相关（BLOCKED 状态居多） | 锁竞争 | jstack 看谁持有锁 |

### 场景二　OOM（OutOfMemoryError）

先看 OOM 类型再动手，类型决定排查方向：

| OOM 日志关键字 | 根因方向 |
| --- | --- |
| Java heap space | 堆泄漏或瞬时大对象：无分页大查询、本地缓存无界、ThreadLocal 未清理、队列堆积 |
| GC overhead limit exceeded | 堆将满前反复 Full GC，同上 |
| Metaspace | 动态代理/CGLib 反复生成类、Groovy 表达式未缓存 |
| unable to create new native thread | 线程数超 ulimit 或线程池无界 |
| Direct buffer memory | NIO/Netty 直接内存未释放 |

取证与分析流程：

```bash
# 1. 自动导出的堆 dump（依赖 HeapDumpOnOutOfMemoryError）
ls -lh /data/dump/

# 2. 没有 dump 时手动导（低峰执行，会 STW）
jmap -dump:live,format=b,file=heap.hprof <pid>

# 3. Arthas 方式（可只导 live 对象）
[arthas]$ heapdump /data/dump/heap.hprof
```

用 Eclipse MAT 打开 hprof：Leak Suspects 报告给嫌疑结论，Dominator Tree 按支配大小排序，找到最大对象 → 看 GC Roots 引用链 → 直接定位到业务类。也可以先用 `jmap -histo <pid> | head -20` 看对象数量排行做快速判断。

容器场景公式：容器 limit ≥ -Xmx + MaxMetaspaceSize + 线程数 × 1MB 栈 + 直接内存 + 300MB 余量。不满足就会 JVM 明明没报 OOM、Pod 却被 OOMKilled。

### 场景三　Full GC 频繁

```bash
jstat -gcutil <pid> 1000
#  S0    S1    E     O     M    YGC  YGCT  FGC  FGCT
#  0.0 95.2  80.1  99.6  96.1  1024  12.3  87   145.6
#                                        ^^^        ^^^^
# 老年代 99.6% + FGC 持续增加 → 内存不足或泄漏
```

判读规则：

- FGC 后 O 能降到 20% 以下：内存确实不够 → 扩堆或优化大对象。
- FGC 后 O 仍接近 100%：泄漏 → 走 OOM 取证流程。
- FGC 正常但间隔短、YGC 也频繁：可能堆太小或对象朝生夕死太多 → 检查 -Xms 是否误设小。
- 配合 GC 日志（`-Xlog:gc*`）看每次 FGC 的原因（Allocation Failure / Metadata GC Threshold / System.gc() 被误调）。

### 场景四　死锁与线程阻塞

```bash
jstack <pid> | grep -A 5 'deadlock'    # 死锁时末尾直接打印 Found one Java-level deadlock
[arthas]$ thread --blocked              # 列出阻塞中的线程及等待的锁
[arthas]$ thread --state WAITING        # 按状态过滤
```

常见阻塞源：数据库行锁（栈里在 socketRead 等待 MySQL 响应）、外部接口无超时（HTTP 客户端没设 connect/read timeout，线程无限等待）、synchronized 热点、连接池耗尽（栈中大量线程 WAITING 在 HikariPool.getConnection）。

### Arthas 高频命令

| 命令 | 作用 | 排查场景 |
| --- | --- | --- |
| dashboard | 总览面板 | CPU/内存/线程一屏看 |
| thread -n 3 | 最忙线程 | CPU 高 |
| thread --blocked | 阻塞线程 | 死锁、连接池耗尽 |
| trace com.a.OrderService create | 方法调用链耗时分解 | 慢接口定位到具体子调用 |
| watch com.a.OrderService create '{params, returnObj, throwExp}' -x 2 | 观察入参出参异常 | 线上"猜不出参数"的问题 |

## 4.4 数据库排查（MySQL）

### 慢 SQL 定位

```sql
SHOW VARIABLES LIKE 'slow_query%';
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.5;      -- 生产建议 0.5~1s
-- 慢日志文件里每条记录：耗时、锁时间、扫描行数、返回行数、SQL 原文
```

拿到 SQL 后 `EXPLAIN` 是必经一步，重点看四列：

| 列 | 好的值 | 坏的值与含义 |
| --- | --- | --- |
| type | const / eq_ref / ref / range | ALL（全表扫描） |
| key | 实际用到的索引 | NULL（没用上） |
| rows | 预估扫描行数 | 百万级即危险 |
| Extra | Using index | Using filesort（额外排序）、Using temporary（临时表） |

索引失效的六个高发场景，EXPLAIN 看到 ALL 先对照这张表：

| 场景 | 反例 | 正例 |
| --- | --- | --- |
| 不满足最左前缀 | 联合索引 (a,b)，只查 b | 查询条件从 a 开始 |
| 列上做运算/函数 | WHERE YEAR(create_time)=2026 | WHERE create_time >= '2026-01-01' |
| 隐式类型转换 | varchar 列 phone 传数字 13800000000 | 传字符串 '13800000000' |
| 前缀模糊匹配 | LIKE '%张' | LIKE '张%'（可走范围） |
| or 两侧未全有索引 | id 有索引 or name 无索引 | 两侧都建索引或改写为 UNION |
| 优化器判定回表代价高 | 查询列不在索引里且命中大量行 | 覆盖索引（把查询列纳入索引） |

### 连接与锁

```sql
SHOW PROCESSLIST;                      -- 当前连接与正在执行的 SQL
KILL <id>;                             -- 杀掉作恶连接
SHOW STATUS LIKE 'Threads_connected';  -- 与 max_connections 对比水位
SHOW ENGINE INNODB STATUS\G           -- LATEST DETECTED DEADLOCK 段看死锁双方 SQL
```

应用侧连接池排查：Druid 打开 `/druid` 监控页看 ActiveCount 与 WaitThreadCount；HikariCP 在 Prometheus 看 `hikaricp_connections_active`、`hikaricp_connections_pending` 指标。连接池耗尽的根因十有八九是慢 SQL 占住连接不放，先治慢 SQL，再谈加连接数（盲目调大 max_connections 只会把库打挂）。

### 主从延迟

```sql
SHOW SLAVE STATUS\G     -- Seconds_Behind_Master 一列
```

延迟突增的常见诱因：大事务（批量 update 百万行）、大 DDL、从库单线程回放瓶颈、网络。对一致性敏感的读写分离场景，核心交易路由强制走主库（ShardingSphere/动态数据源均支持 hint）。

### 深分页与大表

```sql
-- 慢：offset 越大扫描越多
SELECT * FROM t_order ORDER BY id LIMIT 1000000, 20;
-- 优化一：子查询先定位主键
SELECT * FROM t_order t
JOIN (SELECT id FROM t_order ORDER BY id LIMIT 1000000, 20) x ON t.id = x.id;
-- 优化二：游标翻页（产品允许"上一页/下一页"时最优）
SELECT * FROM t_order WHERE id > #{lastId} ORDER BY id LIMIT 20;
```

## 4.5 Redis 排查

### 基础诊断命令

```bash
redis-cli -h <ip> -p 6379 -a <pwd>
INFO memory                          # used_memory_human、fragmentation_ratio、evicted_keys
SLOWLOG GET 10                       # 慢命令（默认 >10ms 记录）
redis-cli --bigkeys                  # 各类型最大 key 扫描（低峰执行）
redis-cli --hotkeys                  # 热 key（需 LFU 淘汰策略）
MEMORY USAGE <key>                   # 单个 key 占用
CLIENT LIST                          # 连接来源排查
LATENCY HISTORY event                # 延迟事件（需先 CONFIG SET latency-monitor-threshold 100）
```

### bigkey 与热 key

| 问题 | 危害 | 发现 | 处理 |
| --- | --- | --- | --- |
| bigkey | DEL 阻塞主线程、序列化慢、网络放大、集群数据倾斜 | --bigkeys、RDB 离线分析 | 拆分（大 hash 分桶）、删除用 UNLINK、过期异步 |
| 热 key | 单分片 CPU 打满、缓存击穿源头 | --hotkeys、proxy 侧统计 | 本地缓存 Caffeine 兜底、key 加随机后缀打散到多分片 |

### 缓存三大经典故障

| 故障 | 现象 | 判定依据 | 解决 |
| --- | --- | --- | --- |
| 穿透 | 查询大量不存在的 key，全部打到 DB | 缓存 miss 率突增，DB QPS 突增，key 分布显示查询的 key 根本不存在 | 空值缓存短 TTL、布隆过滤器、参数合法性校验 |
| 击穿 | 某个热点 key 过期瞬间大量并发直击 DB | 单一 key 的 miss，DB 出现同一 SQL 并发风暴 | 互斥锁重建（一个线程回源）、逻辑过期不物理过期 |
| 雪崩 | 大批 key 同时过期或 Redis 整体不可用 | DB QPS 曲线与缓存命中率曲线同时剧变 | 过期时间加随机值、Redis 集群高可用、DB 侧限流、服务降级返回兜底数据 |

### 内存与持久化

- `used_memory` 逼近 `maxmemory` 后写入变慢并开始淘汰（看 `evicted_keys` 增速），淘汰策略推荐 `allkeys-lru` 或 `volatile-lru`；缓存场景禁止 `noeviction`。
- RDB 的 `fork` 在大堆实例上会引发百毫秒级卡顿（`latest_fork_usec` 指标），表现为周期性毛刺。
- 哨兵/Cluster 切换后客户端是否自动感知：看应用日志有无 `MOVED`/重连记录，连接池配置要支持拓扑刷新。

### 分布式锁现场

Redisson 看门狗默认续期 30s，排查锁相关问题看三点：业务执行时间是否超过锁 TTL 且未开看门狗（默认 30s 不触发）、unlock 是否在 finally 中保证执行、是否校验了 value 防止误删他人锁。

## 4.6 消息队列排查

### 消息堆积

以 RocketMQ 为例，控制台看消费组的 `Diff Total`（积压量）与消费 TPS 趋势，然后分三类处理：

| 原因 | 特征 | 处理 |
| --- | --- | --- |
| 消费者全部挂了 | TPS 归零 | 拉起消费者，优先看其报错日志 |
| 消费能力不足 | TPS 低于生产速率，单条消息耗时高 | 扩消费者数（不超过 queue 数）、批量消费、消费逻辑里的慢操作（DB、外部接口）异步化或加缓存 |
| 消息倾斜 | 个别 queue 堆积 | 生产端按业务 key 重新散列，或临时增加 queue |

堆积量过大影响业务时效时：新建临时 topic 转储堆积消息 → 业务侧离线补偿，先恢复实时链路。

### 消息丢失三段排查

| 环节 | 丢失原因 | 预防 |
| --- | --- | --- |
| 生产端 | 发送失败无重试、进程在确认前退出 | 同步发送 + 失败重投；重要业务用事务消息或本地消息表兜底 |
| Broker | 异步刷盘时宕机、异步复制时主挂 | 同步刷盘 + 同步复制（牺牲吞吐换可靠） |
| 消费端 | 自动 ACK 下消费失败但已确认 | 手动 ACK；消费失败进重试队列，超限进死信队列人工处理 |

### 重复与顺序

- 重复消费：MQ 语义是至少投递一次，重复不可避免，消费端必须幂等（唯一索引、Redis setnx、状态机判断）。
- 顺序消息：相同业务 key（如同一订单号）必须路由到同一 queue，消费端对该 key 串行处理；排查顺序错乱先看生产端是否换了散列 key。

## 4.7 网关与服务间调用排查

### 网关层错误码定位

| 状态码 | 含义 | 第一步排查 |
| --- | --- | --- |
| 502 | 上游连接失败 | Nacos 上该服务实例是否存在、是否全被摘除 |
| 503 | 无可用实例 / 主动限流 | 实例数、Sentinel 限流规则 |
| 504 | 上游处理超时 | 下游服务 RT 曲线，超时配置链是否层层递减 |
| 401/403 | 鉴权失败 | token 是否过期、鉴权服务是否正常 |

### Nacos 注册排查

服务调用不通时按序确认：控制台服务列表存在该服务 → 实例数健康（临时实例 15s 未心跳即摘除，先查实例进程是否存活）→ IP 端口从网关可达（telnet）→ 客户端 namespace/group 与服务端一致 → Nacos 2.x 的 gRPC 端口 9848/9849 网络可达（很多"注册不上"是安全组漏放 gRPC 端口）。

### 超时链与熔断

超时配置必须严格递减：前端超时 > 网关超时 > Feign 超时 > 底层业务耗时。任何一层配置颠倒都会出现"上游已超时重试、下游还在跑"的雪崩放大。

Sentinel 熔断发生时特征：接口 RT 正常但错误率/慢调用比例先升高、流量突然跌零、fallback 日志出现。处理顺序：先看是依赖真实故障（正确熔断）还是阈值过敏（调规则），恢复期利用半开状态自动探测。

## 4.8 Kubernetes 排查

### 常用命令

```bash
kubectl get pods -n prod -o wide                    # Pod 状态总览
kubectl describe pod <pod> -n prod                 # Events 段是第一现场
kubectl logs <pod> -n prod --previous              # 上一次崩溃的日志（CrashLoop 必用）
kubectl logs -f <pod> -n prod -c <container>       # 多容器时指定
kubectl exec -it <pod> -n prod -- bash             # 进入容器
kubectl top pod -n prod                             # 实时资源用量
kubectl get events -n prod --sort-by='.lastTimestamp'   # 事件时间线
kubectl get endpoints <svc> -n prod                 # Service 背后的 Pod 列表
kubectl rollout history deployment/<name> -n prod  # 发布历史
kubectl rollout undo deployment/<name> -n prod     # 回滚
kubectl scale deployment <name> --replicas=6 -n prod   # 手动扩容
kubectl cp <pod>:/data/dump/heap.hprof ./ -n prod  # 拷出 dump 文件
```

### Pod 异常状态速查

| 状态 | 含义 | 排查动作 |
| --- | --- | --- |
| Pending | 调度失败 | describe 看 Events：资源不足、PVC 未绑定、节点选择器不匹配 |
| ImagePullBackOff | 镜像拉不下来 | 镜像名/tag 拼写、Harbor 凭证 imagePullSecrets |
| CrashLoopBackOff | 容器反复崩溃 | `logs --previous` 看启动报错：端口占用、配置缺失、启动异常 |
| OOMKilled | 容器内存超 limit 被杀 | describe 看 Last State exitCode 137；对照 4.3 容器内存公式 |
| Evicted | 节点资源压力被驱逐 | 节点磁盘/内存水位，检查 requests 配置是否过低 |
| Completed | 正常退出 | 定时任务 Pod 属正常 |

### Service 不通的标准排查

```bash
kubectl get endpoints <svc> -n prod
# endpoints 为空 → selector 与 Pod label 不匹配，或 Pod 没通过 readiness
kubectl describe pod <pod> -n prod | grep -A 5 'Readiness'
# Pod 有但 curl service 不通 → 端口映射 targetPort 是否正确
# 跨 Pod DNS 不通 → kubectl exec 进 Pod: nslookup kubernetes.default
```

readiness 探针失败导致"Pod 起来了但不接流量"是发布期最常见问题：启动慢的服务调大 `initialDelaySeconds` 或改用 SpringBoot 优雅启动配合 `failureThreshold`。

### 发布卡住

滚动发布停在中间不动：`kubectl rollout status` 挂起 → 新 Pod readiness 不通过（看 describe Events）→ 卡 `maxUnavailable: 0` 时旧 Pod 不会让位。旧版本 `kubectl rollout undo` 即可脱困。

## 4.9 链路追踪定位慢接口

SkyWalking 排查路径：按 URL / 服务名 / traceId 检索 → 打开 Trace 详情看 Span 瀑布图 → 直接看到耗时集中在哪个服务的哪个 Span（一段 SQL、一次 Redis、一次外部 HTTP）→ 拿 traceId 去 Kibana 对应查日志上下文。

三类典型瀑布形态与结论：

- 瓶颈在 DB Span：走 4.4 慢 SQL 排查。
- 耗时均匀分散在服务间跳转：链路过长，考虑聚合接口或缓存。
- 某次调用特别长而前后正常：偶发性问题，用 traceId 拉日志看当时参数与状态。

## 4.10 日志检索

ELK/Kibana 中用 KQL：

```
service: "order-service" and level: "ERROR" and traceid: "a1b2c3d4*"
message: "timeout" and not kubernetes.pod.name: "canary-*"
```

服务器本地日志三板斧（grep / awk / sed 配合管道）：

```bash
grep 'ERROR' app.log | grep 'a1b2c3d4'        # 按 traceId 过滤错误
tail -f app.log | grep --line-buffered 'ERROR' # 实时跟踪错误（--line-buffered 必须）
zcat app.2026-08-25.log.gz | grep 'timeout'    # 查压缩历史日志
grep -c 'orderTimeout' app.log                  # 计数看趋势
awk '/ERROR/ {print $1,$2,$NF}' app.log | head  # 抽取字段
sed -n '10000,10100p' app.log                   # 看指定行段
```

日志规范是排查效率的前提：JSON 结构化输出、traceId 贯穿全部服务（MDC + SkyWalking）、ERROR 级别只记真实异常（避免告警疲劳）、日志按天滚动并压缩。

# 第五部分　线下问题排查

## 5.1 线上与线下的分工

| 问题类型 | 处理位置 | 原因 |
| --- | --- | --- |
| 配置错误、流量突增、资源不足、网络策略 | 线上直接处理 | 与生产环境状态绑定，换环境无法复现 |
| 代码逻辑 bug、性能瓶颈、并发与时序问题 | 线下复现修复 | 需要断点、改代码、反复验证 |
| 偶发问题、压测类问题 | 线下复现 + 线上取证 | 线上拿证据，线下做实验 |
| OOM、死锁、CPU 高 | 线上留 dump，线下分析 | 现场证据（dump/栈）可带回 |

## 5.2 本地调试手段

- IDEA 断点调试：条件断点（右键断点加布尔表达式，只停特定订单）、Evaluate Expression（断点处执行表达式观察中间状态）、Force Return（模拟异常分支）。
- 远程调试：预发/测试环境进程加启动参数，IDEA 配 Remote JVM Debug 连接。

```bash
# 被调试进程（测试环境可用，生产禁止——断点会挂住线程拖垮服务）
java -agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005 -jar app.jar
```

- Arthas 热更新快速验证：`jad` 反编译 → 本地改完 `mc` 编译 → `retransform` 加载，测试环境验证补丁无需重新发布。
- 把线上入参写成单元测试用例，用失败的单测固化问题，修复后回归，防止复发。

## 5.3 接口调试

- Apifox/Postman：环境变量管理多环境域名与 token，公共请求头（traceId、灰度标）抽成全局配置，接口自动化沉淀。
- curl 完整用法：

```bash
curl -v \
  -H "Content-Type: application/json" \
  -H "X-Trace-Id: debug-0001" \
  -d '{"orderId": 123}' \
  -w '\ndns=%{time_namelookup}s connect=%{time_connect}s ttfb=%{time_starttransfer}s total=%{time_total}s\n' \
  http://order-service:8080/api/order/detail
```

`-w` 输出的分段耗时可以直接判断问题是出在 DNS、建连还是服务端处理。

## 5.4 压测验证

| 工具 | 适用 | 特点 |
| --- | --- | --- |
| wrk / wrk2 | 单接口基准测试 | 轻量高速，适合快速摸底 |
| JMeter | 复杂场景编排 | 图形化、协议全、报告全 |
| k6 | 脚本化压测 | JS 写场景，易进 CI |

压测排查的操作路径：先单接口基准（摸清单实例容量）→ 全链路压测（暴露级联瓶颈）→ 观察各服务 P99 与资源水位曲线，第一个到达瓶颈的组件就是短板。生产环境压测用影子库/影子表隔离数据，或专用压测环境。

## 5.5 环境差异定位法

"线下正常、线上异常"的排查维度表：

| 维度 | 检查方法 |
| --- | --- |
| 代码版本 | 比对镜像 tag 与 Git commit；Arthas `jad` 反编译确认线上真实运行的代码 |
| 配置 | 导出两环境 Nacos 配置做 diff（重点：超时、连接池、开关、数据源） |
| JVM 参数 | `jinfo -flags <pid>` 对比；容器内存 limit 与本地差异 |
| 数据量级 | 线上千万行的表 vs 线下几千行，慢 SQL 表现完全不同；把线上数据量级模拟出来 |
| 网络 | 安全组、跨可用区延迟、专线带宽 |
| 依赖版本 | 中间件版本、依赖 jar 冲突（`mvn dependency:tree` diff） |
| 时间因素 | 时区不一致、定时任务重复触发 |

实操技巧：拿同一个请求（相同 header 与参数）在两个环境各跑一遍，用 Arthas `trace` 或日志对比两边的耗时分解，第一处分叉点就是原因所在。

## 5.6 把线上样本带回线下

| 线上证据 | 获取方式 | 线下分析手段 |
| --- | --- | --- |
| 完整错误日志 | kubectl logs 重定向导出 / Kibana 导出 CSV | 本地 grep 分析、还原时间线 |
| 堆 dump | `kubectl cp` 拉回 hprof | MAT 离线深挖，不受线上干扰 |
| 线程 dump | `kubectl exec` 内 jstack 多次采样 | 快照对比找阻塞线程 |
| 一次完整请求 | traceId 在 SkyWalking 导出 trace | 对照日志复现参数，本地重放 |
| 数据现场 | binlog 按时间区间导出 | 线下库重放，复盘数据如何变脏 |
| GC 日志 | 容器内拉回 gc.log | GCViewer / gceasy.io 在线分析 |

进阶手段是流量录制回放：在生产录制真实请求（GoReplay 复制流量、或 JVM 层用 byteman/sandbox 录制），回放到测试环境复现问题或验证修复，避免"测试环境测不出、一上线就炸"。

# 第六部分　典型故障案例复盘

## 案例一　CPU 100% 导致全站超时

- 现象：网关大面积 504，order-service Pod CPU 全部打满，重启无效。
- 排查：kubectl top 定位到具体 Pod → exec 进入执行 arthas → `thread -n 3` 显示最忙线程栈停在 `Pattern.matcher` → 某接口用正则校验用户输入的备注字段。
- 根因：恶意请求提交超长字符串，正则存在嵌套量词回溯，CPU 被回溯计算吃光。
- 解决：HPA 扩容 + 网关对该接口限流止血；代码加输入长度上限，正则改为预编译并去掉嵌套量词。
- 预防：代码评审关注正则与输入校验；压测覆盖异常长文本。

## 案例二　服务每两天 OOM 一次

- 现象：Pod 周期性重启，Last State 为 OOMKilled，同时 JVM 日志有 heap space OOM。
- 排查：HeapDumpOnOutOfMemoryError 自动留下 dump → MAT Dominator Tree 显示一个静态 ConcurrentHashMap 占用 1.2GB，key 是 token、value 是用户对象 → 查代码：本地 token 缓存只 put 不清理。
- 根因：无界本地缓存随时间线性增长，两天堆满。
- 解决：换 Caffeine，设 maximumSize 与 expireAfterWrite；大缓存统一迁到 Redis。
- 预防：静态集合列入评审红线；Grafana 配老年代趋势告警，在 OOM 前预警。

## 案例三　Full GC 频繁，接口周期性变慢

- 现象：每天 10 点接口 P99 尖刺，Grafana 上 FGC 曲线与尖刺完全重合。
- 排查：GC 日志显示 FGC 原因为 Allocation Failure，且每次晋升对象巨大 → SkyWalking 看当时慢接口为报表导出 → 代码一次性 `select *` 拉全表到内存做 Excel。
- 根因：大对象直接进老年代，触发 Full GC。
- 解决：导出改游标流式查询 + 分页写临时文件；该类任务移到低峰执行。
- 预防：导出类接口强制分页；数据量大的聚合走离线任务。

## 案例四　列表接口偶发超时

- 现象：订单列表接口 P99 从 80ms 涨到 3s，偶发。
- 排查：SkyWalking trace 显示耗时集中在 SQL → 该 SQL 抓出来 EXPLAIN，type 为 ALL 全表扫描 → 但联合索引明明建了 → 对比正常与异常请求参数：异常请求的商户编号传了数字，正常请求传的是字符串。
- 根因：隐式类型转换导致索引失效（varchar 列与数字比较）。
- 解决：MyBatis 参数类型改为字符串；沉淀开发规范"where 条件类型必须与列类型一致"。
- 预防：开启慢查询日志 long_query_time=0.5；EXPLAIN 加入发布前自检。

## 案例五　缓存雪崩打挂数据库

- 现象：整点活动开始后数据库连接数瞬间打满，服务全面超时。缓存命中率曲线同一时刻从 95% 跌到 10%。
- 排查：Redis 中该批 key 的 TTL 完全相同（预热脚本统一写入），活动开始时刻集中过期。
- 根因：大批 key 同时失效，流量全部穿透到 DB。
- 解决：止血——DB 侧限流 + 非 core 服务降级；根治——TTL 加随机偏移、热点数据逻辑过期、DB 前加本地缓存二级兜底。
- 预防：预热脚本强制随机 TTL；压测模拟集中过期场景。

## 案例六　RocketMQ 堆积八百万条

- 现象：积分服务消费组积压量持续上涨，用户投诉积分延迟到账。
- 排查：控制台看消费 TPS 只有 200/s 且单条消息耗时 30ms+ → 消费逻辑里同步调外部风控接口（平均 20ms）→ 积分消费者并发为单线程。
- 根因：消费能力不足，串行外部调用拖慢消费。
- 解决：消费并发线程调到 20，外部调用加 100ms 超时与熔断，存量堆积临时扩容消费者消化。
- 预防：MQ 消费逻辑禁止慢外部依赖；堆积量配告警（Diff > 10 万告警）。

## 案例七　Pod 反复 OOMKilled 但 JVM 不报 OOM

- 现象：服务每隔几小时被 K8s 杀掉重启，exitCode 137，JVM 日志没有任何 OutOfMemoryError。
- 排查：这是容器 cgroup 内存超限，不是堆 OOM → 核对配置：容器 limit 2Gi，`-Xmx1536m`，MaxMetaspace 256m，线程数峰值 300+（300MB 栈）→ 1536+256+300+直接内存已超 2Gi。
- 根因：容器内存预算没有覆盖堆之外的内存。
- 解决：limit 提到 3Gi，改用 `-XX:MaxRAMPercentage=65.0` 统一策略。
- 预防：见 4.3 容器内存公式；容器内存使用率告警阈值设在 80%。

## 案例八　分布式锁引发的超卖

- 现象：秒杀库存出现负数，DB 里出现超卖记录。
- 排查：日志时间线显示两个请求同时通过 `setnx` 判断 → 代码里锁的 value 没校验、unlock 直接删；且存在锁过期后业务未执行完的场景（未开 Redisson 看门狗）。
- 根因：锁误删 + 锁提前过期，双重失效。
- 解决：value 存唯一请求 ID，unlock 前 Lua 校验再删；换 Redisson 并确认看门狗生效；库存扣减 DB 层再加 `where stock > 0` 条件兜底。
- 预防：库存类强一致场景优先 DB 原子操作/乐观锁，分布式锁只做第一道防线。

# 第七部分　应急响应流程

## 7.1 故障分级

| 级别 | 定义 | 响应要求 | 通知范围 |
| --- | --- | --- | --- |
| P0 | 核心服务不可用、资金损失、数据泄露 | 5 分钟响应，全员到场，CTO 知情 | 全员通报 + 客户公告 |
| P1 | 核心功能降级、部分用户受影响 | 10 分钟响应，值班 + 模块负责人 | 技术群 + 业务方 |
| P2 | 非核心功能异常、性能劣化 | 当班处理 | 技术群 |
| P3 | 边缘问题、体验类缺陷 | 排期修复 | 记录跟踪 |

## 7.2 响应流程

```
监控告警 / 用户报障
   → 确认与定级（5 分钟内，值班群同步"现象 + 影响 + 初步判断"）
   → 止血优先（见 7.3，目标是恢复，不是找根因）
   → 保留现场（重启前 jstack/jmap 拉快照）
   → 根因定位（第四部分排查路径）
   → 恢复验证（业务指标回归正常，观察 30 分钟）
   → 复盘（24 小时内出报告，改进项带责任人与期限）
```

## 7.3 止血手段优先级

| 优先级 | 手段 | 命令/入口 | 适用 |
| --- | --- | --- | --- |
| 1 | 回滚 | `kubectl rollout undo` / Nacos 配置回退 | 最近有发布，优先怀疑 |
| 2 | 降级 | Sentinel 开关、关闭非核心功能 | 依赖组件故障 |
| 3 | 限流 | 网关/Sentinel 收窄流量 | 流量突增、能力不足 |
| 4 | 扩容 | HPA 上调 / 手动 scale | 水位高、消费堆积 |
| 5 | 重启 | 滚动重启（重启前必留 dump） | 最后手段，现场会丢失 |

## 7.4 复盘模板

- 时间线：发现 → 各关键动作 → 恢复，精确到分钟。
- 影响面：持续时长、受影响用户量、资损估算。
- 根因：技术根因（直接原因）+ 流程根因（为什么没拦住：评审、监控、发布流程缺了哪环）。
- 改进项：每条带负责人与截止日期，分"立即 / 短期 / 长期"三档，下次复盘先检查上次改进项完成度。

复盘对事不对人，根因落在系统与流程上，不落在个人上，否则会催生瞒报文化。

## 附录B　一页纸排查路径

```
故障

 │    ├─ SkyWalking 慢在 SQL → 慢日志 + EXPLAIN
```
