

# 全栈自测 

## 测试内容

1. **静态检查（Lint）**：不运行程序，检查语法、规范、潜在缺陷
2. **本地编译打包，确认无报错**
3. **单元测试 Unit**：独立函数、工具类，隔离外部依赖
4. **手动调试接口 UI 操作（web 项目），走一遍完整用户流程**
5. 边界场景：空输入、非法参数、异常报错 确认配置文件、环境变量可以正常加载
6. **集成测试 Integration**：模块之间交互、接口调用
7. **E2E 端到端测试**：模拟真实用户完整操作
8. **构建验证**：编译、打包、镜像构建是否正常
9. **可选：性能、安全、兼容性**

### 1. 静态代码检查 Lint

- 后端 (Java/Go/Python)：代码规范、语法校验、静态 bug 扫描
  - Java：Checkstyle、SpotBugs
  - Go：golint、golangci‑lint
  - Python：flake8、ruff
- 前端 (JS/TS)：ESLint + Prettier 格式校验

> CI 中执行，不通过阻断提交。 作用：抓低级语法错误、格式混乱、潜在空指针、不安全写法。

### 2. 构建 / 编译验证

> 最重要：保证代码可以正常打包编译。

- Java：`mvn compile` / `gradle build`
- Go：`go build`
- Python：语法校验 `python -m py_compile`
- 前端：`npm run build`

> CI 必须跑，一旦构建失败直接告警。

### 3. 单元测试 Unit Test

测试独立方法、工具类，**Mock 掉数据库、外部接口等依赖**。

- Java：JUnit5
- Go：testing
- Python：pytest
- 前端：Vitest / Jest

> ✅个人项目策略：**核心业务逻辑写单元测试，工具类、核心算法覆盖；简单 CRUD 可以少写**，不强制高覆盖率。

### 4. 接口集成测试

测试对外接口，验证入参、返回、异常场景。

- Java：SpringBoot Test + MockMvc
- Go：httptest
- Python：pytest‑requests

> 覆盖场景：正常请求、参数非法、异常报错、权限校验。

### 5. E2E 端到端测试

模拟真实用户浏览器 / 客户端完整操作。

- 工具：Playwright、Cypress

> 缺点：维护成本高；**个人项目前期可以用手动自测代替**。

### 6. 依赖安全扫描

检查第三方依赖是否存在漏洞。

- 工具：`dependency‑check`、npm audit、gosec

> CI 自动扫描高危漏洞，提醒升级依赖。

### 7. 数据库迁移测试

如果项目有数据库，验证迁移脚本是否可以正常执行。

### 8. 压力测试

- 性能压测（jmter k6、wrk）：有真实用户流量后再做
- 渗透安全测试：简单注意即可，不用全套
- 完整覆盖率报告、mutation 测试
- 混沌测试

## Checklist

> 提 PR 前过一遍，确保不漏项。

### 1 通用检查

-  代码能正常编译 / 构建，无报错
-  Lint / 静态检查全部通过，无 warning
-  单元测试通过，核心逻辑有覆盖
-  没有硬编码的敏感信息（密钥、密码、token）
-  配置文件 / 环境变量示例已更新
-  README / 相关文档已同步更新
-  没有 console.log / println 等调试代码残留

### 2 前端专项

-  页面在不同分辨率下展示正常（至少 1920 / 1440 / 移动端）
-  加载状态 / 空状态 / 错误状态都有处理
-  表单校验：必填项、格式校验、错误提示清晰
-  列表分页、搜索、排序功能正常
-  路由跳转正常，浏览器前进后退无异常
-  刷新页面状态不丢失（或有合理降级）
-  图片懒加载、资源加载无 404
-  TypeScript 类型完整，无 `any` 滥用
-  接口错误有统一提示，不白屏

### 3 后端专项

-  所有接口入参校验完整（类型、长度、格式、必填）
-  接口返回格式统一，错误码规范
-  SQL 查询无注入风险，关键查询走索引
-  事务边界正确，异常时数据一致
-  接口有幂等性保障（支付、下单等关键操作）
-  并发场景下无竞态条件
-  外部依赖调用（第三方 API、消息队列）有超时和重试
-  日志输出合理，异常有完整堆栈，不打印敏感信息
-  权限校验到位，无越权风险（水平越权 + 垂直越权）
-  限流 / 熔断机制（高并发接口）

### 4 数据库专项

-  迁移脚本正向执行成功
-  迁移脚本回滚（down）验证过
-  新增字段有默认值，不影响存量数据
-  大表加字段考虑了锁表问题
-  索引设计合理，SQL 已 explain 验证
-  没有删除字段 / 表的破坏性变更（除非确认）

### 5 部署 & 配置专项

-  Dockerfile 能正常构建镜像
-  docker-compose 能一键启动完整环境
-  环境变量区分 dev / test / prod，无硬编码
-  配置文件有示例（`.env.example`）
-  健康检查接口正常

## 自测数据准备策略

### 1 测试数据原则

- **独立**：每个开发者本地有独立的测试数据库，互不影响
- **可重复**：同一套数据跑多次结果一致
- **覆盖边界**：包含正常数据、边界数据、异常数据

### 2 数据准备方式

| 方式                   | 适用场景           | 工具                             |
| :--------------------- | :----------------- | :------------------------------- |
| 数据库迁移 + seed 脚本 | 基础数据、字典表   | Flyway / Liquibase + 自定义 seed |
| Mock 数据生成          | 大量随机测试数据   | Faker.js / Java Faker / mimesis  |
| Fixture 文件           | 固定的测试用例数据 | JSON / YAML 文件加载             |
| 测试工厂函数           | 单元测试中动态生成 | FactoryBot / 自定义 factory      |

### 3 推荐本地环境

用 `docker-compose` 一键拉起全部依赖：

YAML

```yaml
# 示例
services:
  mysql:
    image: mysql:8.0
    ports: ["3306:3306"]
  redis:
    image: redis:7
    ports: ["6379:6379"]
  minio:
    image: minio/minio
    ports: ["9000:9000"]
```

> 好处：新人上手零配置，环境一致性有保障。

## 前后端联调自测流程

### 1 联调前各自确认

- **后端**：接口开发完成，Postman / Swagger 自测通过，返回格式符合约定
- **前端**：页面静态结构完成，用 Mock 数据验证过渲染逻辑

### 2 联调步骤

1. **后端先部署到测试环境**（或本地起服务）
2. **前端连接测试环境接口**，逐页验证
3. **发现问题即时沟通**，后端修接口 / 前端调调用，小步快跑
4. **联调完成后跑一遍完整业务流程**（从登录到核心功能闭环）

### 3 联调常见坑

- 接口字段名前后端约定不一致 → 提前定好 API 文档（Swagger / OpenAPI）
- 时间格式、金额单位不统一 → 约定统一标准
- 异常情况前端没处理 → 后端错误码 + 前端统一错误处理中间件
- 分页参数不一致 → 约定 page/pageSize 或 offset/limit

## 自测通过标准（什么时候可以提 PR）

满足以下全部条件即可提 PR：

1. ✅ **编译通过**：代码能正常 build，无报错
2. ✅ **Lint 通过**：静态检查 0 error，尽量 0 warning
3. ✅ **测试通过**：已有单元测试全绿，新增核心逻辑有测试
4. ✅ **核心流程跑通**：手动验证了主要用户路径
5. ✅ **边界场景覆盖**：空输入、非法参数、网络异常、权限不足
6. ✅ **无明显性能问题**：列表不卡顿、接口响应时间合理
7. ✅ **文档同步**：README、API 文档、变更说明已更新
8. ✅ **数据库变更有迁移脚本**：不手动改表结构

## 常见自测遗漏点（踩坑集锦）

> 这些是最容易被忽略但上线后容易出问题的地方：

| 遗漏点            | 后果                     | 自测方法                       |
| :---------------- | :----------------------- | :----------------------------- |
| 空值 / null 处理  | 前端白屏、后端 NPE       | 故意传空值、删必填字段测试     |
| 长文本 / 大数字   | 展示溢出、精度丢失       | 输入超长字符串、大数测试       |
| 并发 / 重复提交   | 数据重复、超卖           | 快速连续点击 / 并发请求        |
| 权限越权          | 用户能看别人的数据       | 用普通用户 token 调管理员接口  |
| 时间 / 时区       | 时间显示不对、统计偏差   | 跨时区场景、夏令时、零点边界   |
| 文件上传下载      | 格式不对、大小超限、乱码 | 不同格式、大文件、中文文件名   |
| 中文 / 特殊字符   | 乱码、截断、正则匹配失败 | 中文、emoji、特殊符号全测一遍  |
| 浏览器后退 / 刷新 | 状态丢失、表单清空       | 频繁前进后退、刷新页面         |
| 配置缺失          | 启动失败、运行时报错     | 删掉配置文件看错误提示是否友好 |
| 慢接口 / 大数据量 | 页面卡顿、超时           | 构造万级数据量测试列表性能     |

## 自测效率提升技巧

1. **写 Makefile / npm scripts**：把常用命令封装起来，比如 `make test`、`make lint`、`make dev`，减少记忆成本
2. **Git hooks 自动检查**：pre-commit 跑 lint，pre-push 跑单元测试，不通过不让提交
3. **本地一键启动环境**：`docker-compose up` 就能跑完整前后端 + 数据库 + 中间件
4. **测试数据固化**：常用测试账号、测试数据写在 seed 脚本里，不用每次手动造
5. **快捷键 + 别名**：常用 git 命令、测试命令设别名，减少重复输入
6. **自测脚本化**：把重复的手动验证步骤写成脚本，一条命令跑完

## Bug 复现与回归验证流程

###  修 Bug 前

1. **先复现**：在本地 / 测试环境复现 bug，确认问题存在
2. **定位根因**：不要只修表面现象，找到根本原因
3. **写测试用例**：先写一个能复现 bug 的测试（测试会红）

###  修 Bug 后

1. 运行刚写的测试，确认变绿
2. 跑全量相关测试，确认没有引入新问题（回归）
3. 手动验证修复效果
4. 检查边界情况：类似的场景会不会有同样问题

###  回归测试清单（每次发版前过一遍）

-  登录 / 注册流程
-  核心业务主流程（根据项目定）
-  数据增删改查
-  权限控制（普通用户 / 管理员 / 未登录）
-  异常场景（网络错误、超时、参数错误）
-  上一版本修复的 Bug 验证
