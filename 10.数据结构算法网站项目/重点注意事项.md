# OJ 系统数据压测（构造批量测试数据）设计原则 + 后期清理修改方案

> 场景：你现在给 `oj_problem_comment` 批量生成评论，扩展到用户、提交记录、做题记录等压测场景。 核心目标：压测验证接口性能、数据库索引、分页、查询逻辑；**不能污染真实业务数据，方便事后清理**。

## 一、压测数据设计原则

### 1. 数据隔离原则（最重要）

1. 所有压测生成记录必须增加标记字段，例如 `is_test TINYINT DEFAULT 0`
   - `is_test=1`：压测脚本生成的测试脏数据
   - `is_test=0`：真实业务用户产生的数据
2. 所有表只要会被压测插入，都加上该字段：评论表、提交记录表、做题记录表等。

> ❌禁止：直接无标记往业务表灌数据，后期无法区分哪些是测试，哪些是真实，只能 truncate 全表。

### 2. 外键合法性原则

压测插入的数据外键必须真实存在：

- `oj_problem_comment` 的 `user_id`，必须取自真实`user`表存在的 id；
- `problem_id` 取自真实题目表`oj_problem`存在 id；

> 禁止随机乱填数字 id，造成大量数据库外键错误、脏外键。

**实现方式：** 脚本启动时一次性加载全部合法`user_id`、`problem_id`到内存 List，内存随机选取，不要循环数据库查询。

### 3. 数据真实性原则（模拟线上分布）

1. 字段模拟真实业务分布：
   - 创建时间：不要全部同一时间，生成一段时间内随机时间；
   - 点赞数：随机 0‑200，不要全部是 0；
   - 评论文本长度：10‑120 字符，模拟真实用户长短评论；
2. 不要全部记录一模一样，避免测试不出分页、索引、字符串查询真实性能。
3. 文本内容：必须经过**敏感词过滤校验**，防止压测入库一堆违规内容。

### 4. 性能友好原则（压测脚本本身）

1. 禁止循环单条 insert，大量数据使用**批量插入 batch insert**，一次插入几百条；
2. ID 集合预加载到内存，避免循环执行 `select ... order by rand()`（mysql order by rand 性能极差）；
3. 控制插入速率，不要瞬间几万条狂轰数据库，防止开发库直接打崩。

### 5. 不破坏真实业务数据

1. 压测脚本**只做 INSERT，不做 UPDATE、DELETE 真实业务数据**；
2. 不要修改真实用户、真实题目记录；
3. 测试环境优先做压测，**尽量不在生产环境执行数据构造脚本**。

### 6. 可观测原则

- 脚本输出日志：一共生成多少条，耗时多少；
- 数据库可以快速统计测试数据数量：

```
SELECT is_test,count(*) FROM oj_problem_comment GROUP BY is_test;
```

## 二、表结构改动示例（给你的评论表）

```
ALTER TABLE `oj_problem_comment` ADD COLUMN `is_test` TINYINT DEFAULT 0 COMMENT '1=压测测试数据，0真实数据';
```

> 所有压测脚本插入数据的时候，强制设置 `is_test = 1`。

## 三、压测完成之后，如何清理数据（两种方案）

### 方案 A：只删除压测脏数据，保留真实业务数据【日常开发首选】

```
-- 删除评论表全部压测数据
DELETE FROM `oj_problem_comment` WHERE is_test = 1;

-- 如果多张表都有is_test，依次执行
-- DELETE FROM oj_submit WHERE is_test=1;
-- DELETE FROM oj_user_record WHERE is_test=1;
```

✅优点：真实用户数据完全保留；支持事务，可以回滚； ❌缺点：如果千万级大表，delete 会比较慢，可以分批次删除。

> 大表分批删除示例，避免锁表：

```
DELETE FROM `oj_problem_comment` WHERE is_test=1 LIMIT 1000;
-- 循环执行，直到影响行数为0
```

### 方案 B：整张表全部清空（仅完全测试环境，无真实数据）

```
TRUNCATE TABLE `oj_problem_comment`;
```

⚠️风险：全部数据清空，真实数据一并消失。

## 四、压测后额外的数据库修改维护点

1. **删除完大量数据之后，MySQL 会产生碎片**，大表建议执行优化（开发环境）

```
OPTIMIZE TABLE `oj_problem_comment`;
```

1. 核对索引是否生效：压测可以帮你发现缺失索引，例如按 problem_id 分页查询评论慢，就需要建立索引。

```
CREATE INDEX idx_problem_id ON oj_problem_comment(problem_id);
```

1. 验证业务接口：清理完脏数据后，跑一遍接口，确认分页、查询逻辑不受影响。

## 五、踩坑清单

1. ❌没有`is_test`标记，压测数据和真实数据混在一起，后期无法清理；
2. ❌压测脚本随机生成不存在的 user_id/problem_id，产生非法外键；
3. ❌单条循环 insert，插入速度极慢；
4. ❌压测文本不经过敏感词校验，数据库存入违规文本；
5. ❌生产环境直接 truncate 业务表，数据丢失；
6. ❌大批量 delete 之后不处理碎片，查询性能下降。

## 简短总结流程

1. 给需要压测的业务表增加 `is_test` 标记字段；
2. 压测脚本插入时强制设置`is_test=1`；
3. 脚本预加载合法 id 集合，批量插入，模拟真实业务分布，内容过敏感词；
4. 压测完毕，使用 `DELETE FROM xxx WHERE is_test=1` 清理脏数据；
5. 大表可执行 optimize 优化表碎片，校验索引与业务接口。
