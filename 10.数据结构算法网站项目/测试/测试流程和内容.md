## 测试流程

```
开发提交代码（PR 到 main 分支）
    ↓
CI 自动构建 + 跑单元测试（不通过则拒绝合并，自动通知）
    ↓
构建通过 → 产出带版本号的制品（app-1.2.3.jar 或镜像 xxx:1.2.3）
    ↓
推入免费制品库（GitHub Packages / Docker Hub / 阿里云个人版 ACR）
    ↓
自动部署到测试环境（拉取的就是这份制品，不重新编译）
    ↓
测试人员手动验证（冒烟 + 本次改动点，半天内完成）
    ↓
验证通过 → 打 tag（如 v1.2.3）触发发布
    ↓
同一个制品部署到生产环境
```

```
开发自己：
  写代码时 → 单元测试覆盖核心逻辑（这是唯一必须自动化的）
  提测前   → 自己先跑通主流程

测试阶段：
  1. 部署到测试环境后 → 冒烟（10 分钟手动）
  2. 交叉验证新功能   → 按需求对照着点（半天）
  3. 发版前          → 核心清单过一遍（30 分钟）
持续进行：
  CI 里挂着 → 单元测试 + 依赖漏洞扫描（全自动，零维护）
```

## 配套工具选择（全免费，零服务器维护）

| 环节           | 推荐工具                                          | 说明                           |
| :------------- | :------------------------------------------------ | :----------------------------- |
| CI 构建 + 测试 | GitHub Actions / GitLab CI                        | 提交即触发，免费额度够小团队用 |
| 制品库         | GitHub Packages / Docker Hub / 阿里云 ACR 个人版  | 不用自建 Nexus/Harbor          |
| 部署           | docker compose + 一条 `docker pull && up -d` 脚本 | 不需要 K8s                     |

## 只保留 3 条铁律

1. **测过什么就发什么**：测试环境和生产环境用同一个版本号的制品，禁止重新打包
2. **单元测试卡 CI**：测试不通过代码进不了 main，这是唯一的自动化门禁
3. **发布靠 tag**：测试通过后打个 tag 就发布，不需要额外审批流程

## 按你列的逐项裁剪

| 测试类型           | 小团队要不要     | 怎么做                                                       |
| :----------------- | :--------------- | :----------------------------------------------------------- |
| 单元测试           | ✅ **要**         | 开发-代码逻辑、分支、边界，本地 / CI 跑                      |
| 冒烟测试           | ✅ **要**         | 部署后花 10 分钟手动点一遍核心流程，或写 3-5 个 curl 脚本调健康检查接口 |
| 功能测试（新功能） | ✅ **要，最重要** | 测业务功能本身，面向需求，验证 “功能是不是按需求干活”，测业务功能本身，面向需求，验证 “功能是不是按需求干活” |
| 回归测试           | ⚠️ **极简版**     | 自动化回归框架，维护一个 20 条以内的「核心功能清单」，每次发版前快速过一遍（30 分钟内） |
| 接口测试           | ⚠️ **按需**       | 用 Postman 建个集合存起来手动跑即可；只有接口多、改动频繁时才考虑脚本化 |
| 集成测试（联调）   | ✅ **非必须**     | 开发-前端-接口联调，模块交互，测试环境                       |
| UI 自动化          | ❌ **不要**       | 维护成本远超收益，小团队做这个是自杀行为                     |
| 性能/压力测试      | ❌ **日常不要**   | 除非产品明确有并发要求（如秒杀），否则上线前用 JMeter 跑一次摸底就够了 |
| 安全扫描           | ⚠️ **只留免费的** | CI 里加依赖漏洞扫描（GitHub Dependabot / OWASP 插件，零成本全自动）；人工渗透测试完全不需要 |

## 判断标准一句话

> **人力能覆盖的就手动做，人力覆盖不了的（重复执行几百次、千级并发）才自动化**。

3-5 人团队，测试投入控制在开发时间的 **15% 以内**，把精力留给功能正确性本身——你们最大的质量风险不是没做性能测试，而是新功能没验就上线。

# 数据结构算法项目测试流程

**单元测试**  写完代码 ，maven编译 测试 debug流程过一遍，内部逻辑，外部依赖 Mock

**冒烟测试**  极小，只跑**核心主干 Happy Path 正常流程**；不测异常、边界、分支，手动+批量

**集成测试**   范围大，模块间接口、RPC、数据库、缓存、第三方调用；包含正常 + 异常场景

**功能测试**  业务需求是否全部实现，站在用户的视角

**回归测试** 当代码发生变更（新增功能、修复 bug、改表结构、升级依赖、重构）之后，**重新执行原有测试用例，验证老的业务功能没有被本次改**

```
代码编译构建
↓
单元测试（JUnit）
↓
部署测试环境
↓
冒烟测试【准入，失败直接终止】
↓
集成测试（模块、接口、中间件交互）
↓
功能测试（完整业务、权限、边界、UI）
↓
回归测试（校验旧功能不受本次变更影响）
↓
提交代码
↓
CI
↓
PR
↓
全部CI
↓
tag
↓
CD
↓
部署
```
