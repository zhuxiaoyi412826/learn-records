# 接口耗时与超时排查优化规范

> 依据：AlgoVize 题解评论审核接口优化实战（登录 → 评论列表 → 退出全链路，平均耗时 347.73ms → 100.40ms，降低 71.13%）。本规范将该次排查中有效的做法固化为流程，将踩过的坑固化为禁令，供后续所有接口超时/耗时问题遵循。第八节另附一个按本规范完整推演的示教案例。

## 一、核心原则

### R1 R2 R3

三条铁律，任何一条不满足就不动手改代码：

| 编号 | 原则 | 违反后果（案例实证） |
| --- | --- | --- |
| R1 测量先行 | 没有分段耗时数据之前，禁止凭经验猜测性优化 | 第八轮：按"Nagle 200ms 死锁"经验连续改了 TCP_NODELAY、cookie、响应瘦身三项，150ms 缺口纹丝不动——瓶颈根本不在网络层，而在业务层的 Argon2id 实现 |
| R2 单一变量 | 每轮只改一个因素，改完立即复测 | 多项同改时无法归因，收益来源说不清，回归时无法缩小范围 |
| R3 验证闭环 | 同一脚本、同一环境、同一轮数复测，归档前后数据 | "感觉变快了"不算数；本次案例每轮均留存完整统计（最快/最慢/平均/中位/分布/逐轮明细），最终 71.13% 的提升有据可查 |

R1 是整套规范的地基。案例中所有有效优化（覆盖索引、Redis 缓存、Argon2id 实现替换）都建立在逐段测量的数据之上；唯一一次集体失败恰恰是跳过定位、直接套经验方案。慢和超时的区别只在程度：慢是耗时高于预期，超时是耗穿了上游配置的阈值。两者的定位方法完全相同——都是先把时间拆到具体环节，再对号处理。

### **基准压测规范**

1. 编写专用基准脚本，复现真实业务链路（登录→查询→退出），统计：最快、最慢、平均值、中位数、分布柱状、逐轮明细。
2. **优化前后使用同一套脚本、同一环境、相同轮数对比**，不要换脚本换环境对比。
3. 脚本内部分层，但是**脚本模拟组件的库必须对齐后端真实实现**，否则得到虚假耗时，误导定位。
4. 看中位数，而不是只看平均值；看逐轮明细观察抖动。

### 通用优化优先级（从上到下，优先做上面）

1. ✅ **精准埋点定位瓶颈（第一位）**：先找到慢在哪，再动手优化，禁止猜式调参。
2. ✅ SQL 索引、消除回表、慢查询优化（收益通常最大）。
3. ✅ 热点查询引入缓存，做好失效 + 降级兜底。
4. ✅ 优化接口内部 CPU 密集逻辑：加密算法、大对象组装、循环计算；优先选择高性能底层实现。
5. ✅ 业务裁剪：接口返回体瘦身，非必要大对象不要在主接口返回，拆成独立接口按需拉取。
6. ⚠️ 调整容器、TCP 网络参数：**放到最后，确认业务层已经无优化空间再动**，很多时候调了没有收益。

## 二、标准工作流程（六步法）

```
① 建立基准 ──▶ ② 端到端分段 ──▶ ③ 定位瓶颈段
                                          │
⑥ 归档沉淀 ◀── ⑤ 复测验证 ◀── ④ 按对照表优化
```

### 第 1 步　建立基准

- 为目标接口编写基准脚本，固定账号、参数、轮数（≥10 轮）、环境。
- 输出四个统计值（最快/最慢/平均/中位）+ 各环节占比分布 + 逐轮明细。
- 脚本入库（如 `doc/tools/脚本/接口/` 目录），作为项目资产：接口变更后重跑即回归，新同事接手即上手。

判读标准：以中位数看典型耗时，以最大值看尾延迟；轮与轮之间波动大时先排查环境干扰（本机其他进程、网络抖动），再谈优化。

### 第 2 步　端到端分段

按第三节分段模型把接口耗时拆到可归因的最小段。先用客户端分段（脚本直连 DB/Redis 模拟各环节即可完成，成本低）；缺口大或结果可疑时，升级为服务端埋点。

### 第 3 步　定位瓶颈段

占比最大且绝对值超阈值的段即瓶颈。注意第五节的测量陷阱——减法残留项不等于框架开销，模型对不上时先修测量，再下结论。

### 第 4 步　按对照表选优化手段

见第四节。顺序原则：先低成本手段（索引、缓存），后侵入式手段（换实现、拆接口、改架构）。安全相关参数（KDF 强度、加密轮数）不在优化范围内。

### 第 5 步　复测验证

同脚本同轮数复测，只认数据，且优化项与收益必须一一对应。改了没变（如案例第八轮"还是没有改变"）说明假设错误，回到第 3 步。

### 第 6 步　归档

记录格式统一为：优化前耗时 → 手段 → 优化后耗时 → 提升幅度（绝对值 + 百分比 + 倍数），写入项目文档。归档既是复盘依据，也是下次同类问题的先验知识库。

## 三、耗时分段模型

接口端到端耗时的标准分段定义，排查时按此拆解：

```
端到端耗时
├─ ① 网络/HTTP 往返（TCP 建连、传输）          curl -w 分段计时可测
├─ ② 容器层（Tomcat Accept/Filter/路由）       Filter 首行 → Interceptor preHandle
├─ ③ 框架层（参数绑定/反序列化/AOP before）    preHandle → Controller 方法首行
├─ ④ 业务层（Controller 方法体内部）
│    ├─ DB 查询（SQL 执行 + 网络 + 提交）       慢查询日志 / EXPLAIN
│    ├─ Redis 读写                              客户端耗时统计
│    ├─ CPU 密集计算（密码哈希/加解密）          独立计时，单列统计
│    └─ 写操作（日志 INSERT / 状态 UPDATE）     含事务提交
├─ ⑤ 响应序列化（Jackson）                      writeValueAsBytes 实测
└─ ⑥ return 后处理（postHandle/写响应/flush/afterCompletion）
```

1. **数据库层**：每一条 SQL 单独计时，区分：SQL 执行时间、网络往返、事务 commit 时间
2. **中间件层**：Redis/MQ 等，每条命令单独计时
3. **业务逻辑层**：密码加密 / 校验、循环计算、序列化、权限组装
4. **框架层**：Filter、Interceptor、AOP、参数绑定
5. **网络层**：TCP 往返、请求头 / 响应体传输

分段归属的三种手段，精度递增：

| 手段 | 做法 | 精度 | 适用 |
| --- | --- | --- | --- |
| 客户端黑盒 | 端到端 − 脚本模拟的各环节耗时 | 低，有减法残留陷阱 | 第一轮快速缩小范围 |
| 服务端埋点 | Filter/Interceptor/Controller 首尾行 `System.nanoTime()` 打点，结果放 `_debugTimings` 一类的响应字段返回 | 高 | 缺口无法解释时 |
| 压测脚本分层模拟 | 脚本单独模拟 SQL、Redis 调用，**注意脚本的实现语言和库要和后端真实实现对齐**，否则得到的耗时是虚假参考 | 低 |  |
| 工具观测 | Arthas `trace`、SkyWalking、MySQL 慢查询日志 | 高，无需改码 | 生产环境/不想发版时 |

规范要求：核心接口的埋点常驻保留（前端忽略该字段即可），排查时直接可用，不必临时发版。案例中正是埋点（`PerfTimingInterceptor` + `TraceIdFilter`）最终把 150ms 缺口钉死在 Controller 方法体内。

## 四、瓶颈与优化手段对照

### 4.1 DB 慢查询

**发现特征**：SQL 段耗时高；慢查询日志有记录；EXPLAIN 出现 `type=ALL` 或回表。

**手段一：覆盖索引**。把查询涉及的所有列纳入索引，消除回表。案例：索引 `(audit_status, created_at)` 不含 `status` 列，4.6 万行逐行回表判 `status != 'DELETED'`，COUNT 约 90ms；改为 `(audit_status, created_at DESC, status)` 后纯索引扫描零回表，评论列表 116ms → 34ms。

索引列顺序规则（案例的一等经验）：

- 等值条件列在前，排序/范围列居中，仅过滤列放尾。
- 过滤列放尾部不改变索引排序，`ORDER BY` 优化不受影响；若插在中间（如 `(audit_status, status, created_at)`），索引内部排序被 `status` 打断，`created_at` 不再全局连续，触发 filesort，性能反而下降。

**手段二：深分页优化**。大 offset 先子查询定位主键再 JOIN，或改游标翻页（`WHERE id > lastId ORDER BY id LIMIT n`）。

**手段三：大结果集流式化**。导出、报表类禁止一次 `SELECT *` 全量进内存。

**手动四：预防**

1. **慢 SQL 优先看 EXPLAIN**，重点关注：`type`、`rows`、`Extra(Using filesort、Using temporary、Using index)`
2. 回表是巨大性能杀手：筛选 + 排序场景，优先构建覆盖索引，避免回表随机 IO。
   - 索引顺序原则：等值条件放前面、排序字段放中间、需要返回的列放末尾；**不要为了加查询字段打乱排序字段位置，避免 filesort**。
   - 案例：旧索引`(audit_status,created_at)`，查询需要 status，产生大量回表；改造`(audit_status, created_at DESC, status)`覆盖索引，COUNT + 列表查询零回表。
3. COUNT 大表、分页列表，优先通过索引优化，避免扫描大量数据行。
4. 避免大事务，INSERT/UPDATE 及时 commit，关注事务提交耗时。

### 4.2 读多写少的查询

**发现特征**：同一筛选条件被反复查询，DB 段稳定耗时。

**手段：Redis 缓存**。缓存设计四要素齐全才准上线：

| 要素 | 规范 | 案例取值 |
| --- | --- | --- |
| Key | `业务域:模块:场景:维度1:维度2:页:大小`，空维度用 `_` 占位 | `algovize:admin:cmt:list:{keyword}:{auditStatus}:{page}:{pageSize}` |
| TTL | 与业务时效对齐；批量预热的 TTL 必须加随机偏移（防雪崩） | 2h，与 Sa-Token 超时一致 |
| 失效 | 写操作（审核/状态变更）后主动清理同前缀 key | 低频管理端可用 `keys(prefix)` 清理；高频场景改 SCAN |
| 降级 | Redis 读写异常时记警告日志、直查 DB，不阻断业务 | 已实现 |

案例收益：列表 34ms → 约 10ms（最终基准 9.82ms）。

### 4.3 CPU 密集型计算

**发现特征**：业务段耗时高，但 DB、Redis 都快，CPU 使用率高，线程栈顶停在加密/哈希库内。

**手段：换同算法的更快实现**。案例：Argon2id 从 BouncyCastle 纯 Java（每次校验约 130~150ms）换成 `argon2-jvm`（JNA 绑定官方 C 参考实现，约 40ms），提升 3~5 倍；两者哈希输出同为 PHC 格式，可互相校验，历史密码零迁移。

该类问题的通用规则：

| 规则 | 说明 |
| --- | --- |
| KDF 慢是安全特性 | Argon2/scrypt/PBKDF2 的耗时是防暴力破解的设计，只能换实现，不能减参数（m/t/p 一减就是降安全等级） |
| 纯 Java 与原生 C 差距大 | 密码学密集计算 Java 实现比 C 慢 3~5 倍；登录这类高频路径必须用原生绑定 |
| 换库先验格式兼容 | 输出为 PHC 字符串格式（`$argon2id$v=19$m=...`）则可互验，存量密码不用迁移 |
| 容器化要验本地库 | JNA 方案依赖平台预编译二进制，Docker 镜像需确认目标架构（x86-64/arm64）能加载 |
| 关注 GC 压力 | 纯 Java 实现在堆内产生大量临时对象；原生实现计算在堆外，对 GC 更友好 |

### 4.4 大响应体

**发现特征**：响应体积大（数十 KB 级），传输与序列化段偏高。

**手段：接口拆分瘦身**。案例方案：登录响应移除整棵菜单树 `menus`（约 50KB），只返回 `token/userInfo/roles/permissions`（约 3KB），菜单由前端登录后并发调独立接口获取。响应越小，越不容易触发 TCP 分段与 Nagle 相关问题。

### 4.5 网络层

**发现特征**：耗时集中在传输段（抓包可见固定间隔的等待，或 curl `-w` 显示 ttfb 远大于服务端处理耗时）。

**手段**：`server.tomcat.socket.tcp-no-delay: true` 消除 Nagle + Delayed ACK 200ms 死锁；加大 `txBufSize/rxBufSize`；HTTP 连接复用（keep-alive / 连接池）。

前提：网络层优化只在"耗时确实在传输段"时有效。案例第八轮已证明，瓶颈在业务层时这些配置改了也是零收益。

## 五、测量陷阱与禁令

本节全部来自案例实测教训——第八轮三项修改全部无效、150ms"凭空消失"，根源是测量方法错了，而不是改动不生效。

### 陷阱一　减法残留项被误标

端到端耗时减去各模拟环节后的剩余部分，被直接标成"框架开销"。实际上它只是"所有没测到的部分之和"。案例中这段 150ms 的真实身份是：脚本用 Python C 库模拟密码校验只花 39ms，而 Java 端 BouncyCastle 实际花 130~150ms，差额全部落入了减法残差。

**禁令**：减法算出的段只能命名为"未知缺口"，必须继续拆解归因后才能下结论，禁止直接标成某个框架环节。

### 陷阱二　模拟与真实实现不同源

模拟环节与被测环节的实现、参数、版本不一致时，差额会污染所有下游计算，把排查引向完全错误的方向（本案被引向网络层，浪费了一整轮）。

**禁令**：模拟某环节耗时必须与生产同源（同库、同参数、同版本）。模拟不了就不要模拟，直接上服务端埋点。

### 陷阱三　子段全零仍不怀疑模型

案例第七轮：postHandle、afterCompletion、Jackson 写响应三段全部测得 0.00ms，但父段缺口 160ms 对不上。子段全为零说明分段模型本身漏了一段，此时应回头修模型，而不是接受"缺口就是 X 环节"。

**判定规则**：所有已测子段之和与父段差距超过父段 10% 时，分段模型判定为失效，必须重新拆分后再归因。

### 陷阱四　按经验直接套方案

"固定 200ms 左右的耗时 → Nagle + Delayed ACK 死锁"是常见经验，但有前提条件（耗时集中在写响应/传输段）。不经验证直接套用，就是案例第八轮的结局。

**规则**：经验假设必须先用最小成本验证（分段计时确认耗时确实落在该环节），再动手改配置。验证成本远低于一次无效发版。

## 六、超时配置规范

排查"慢"之外，"超时"本身的全局配置约束：

- **超时链递减**：前端超时 > 网关超时 > Feign/RestTemplate 超时 > 底层依赖真实耗时，每层留 20%~50% 余量。任何一层颠倒会出现"上游已放弃、下游还在跑"的资源浪费。
- **慢接口分级治理**：> 200ms 建立专项优化跟踪；> 500ms 必须有缓存或异步化方案；> 3s 改异步任务 + 轮询/推送结果，不占同步请求线程。
- **CPU 密集操作隔离**：密码校验、文件处理、加解密不长期占用业务线程池，量大时用独立线程池或消息队列异步化。
- **重试约束**：重试只配在幂等接口上；重试次数 × 单次最大耗时必须小于上层超时。
- **密码校验类耗时单独建模**：登录接口的正常耗时就包含 KDF 的几十毫秒，属于设计成本，评估超时阈值时不要按普通业务接口标准一刀切。

## 七、预防性条款

新接口上线前逐条过：

1. 核心接口编写基准脚本入库，作为回归资产。
2. 列表类查询按覆盖索引规则建索引，`EXPLAIN` 确认无 `type=ALL`、无多余回表。
3. 读多写少接口完成缓存四要素设计（Key/TTL/失效/降级）。
4. 安全相关计算选用原生实现（Argon2id 用 `argon2-jvm` 而非 BouncyCastle）。
5. 大响应提前拆分，单接口响应控制在 KB 级。
6. 核心接口埋点常驻（`_debugTimings`），Grafana 面板与慢查询日志（`long_query_time=0.5`）开启。
7. 超时链配置按第六节核对一遍。
8. 列表类接口禁止循环内逐条查询关联数据（用户信息、字典等一律收集 id 后批量 IN 取回）。
9. 跨网络的逐条读写合并为批量（Redis MGET/pipeline、ES mget 同理），消除 N 次往返放大。

## 八、示教案例：前台题目评论列表 2s 排查全流程

> 场景：前台用户反馈打开题目评论要 2 秒左右。直觉上的矛盾点是评论总量才 4.6 万行、单题最多几百条、内容都不长——"数据量不大，为什么这么慢"。本案例为按六步法推演的示教样例（表结构与项目同源），它要回答的正是这个直觉矛盾：接口耗时由单次请求的扫描行数与往返次数决定，与库里总行数无关。

### 8.1 现象与接口

```
GET /api/problem/comments?problemId=10086&page=1&size=20
```

一次请求的服务端逻辑：按题目查 20 条最新评论，每条拼用户昵称、头像、等级，标注当前用户是否点赞过，COUNT 总数供分页。

### 8.2 第 1 步　建立基准

```
统计信息（10 次成功）
  【评论列表(前台)】
    最快:  1954ms   最慢:  2246ms   平均:  2011ms   中位:  1998ms
```

十轮全部落在 2s 附近，方差很小。稳定慢指向结构性问题（索引、调用模式），抖动慢才指向竞争性问题（锁、连接池、GC）——本案例属于前者，记下这个判据再往下走。

### 8.3 第 2 步　端到端分段

接口已有常驻埋点（见第三节），直接取数：

| 分段 | 耗时 | 占比 |
| --- | --- | --- |
| HTTP 往返 | 21ms | 1.0% |
| Tomcat 容器层 | 0.5ms | 0.0% |
| Spring 框架层 | 0.9ms | 0.0% |
| 业务层（Controller 方法体） | 1988ms | 98.9% |
| JSON 序列化 | 0.2ms | 0.0% |
| return 后处理 | 0.1ms | 0.0% |

业务层占 98.9%，其余各段全部不足 1ms。框架、网络、序列化一次性排除，全部火力进业务层——这就是分段的第一个价值：本案例从头到尾不需要任何框架层知识。

### 8.4 第 3 步　业务层再拆，定位瓶颈

Arthas `trace` 看调用链结构，MySQL 慢查询日志（阈值 0.5s）交叉取证，业务层 1988ms 拆为五段：

| 子段 | 内容 | 次数 | 耗时 | 占比 |
| --- | --- | --- | --- | --- |
| ① COUNT 总数 | `WHERE problem_id=? AND status='NORMAL'`，无可用索引，全表扫描 4.6 万行 | 1 | 262ms | 13.0% |
| ② SELECT 主列表 | 同上条件 + `ORDER BY created_at DESC LIMIT 20`，filesort + 逐行回表 | 1 | 518ms | 25.8% |
| ③ N+1 用户信息 | 每条评论 3 条 SQL（基础信息、等级徽章、做题统计），单条 8~14ms | 60 | 718ms | 35.7% |
| ④ N+1 点赞状态 | 当前用户对每条评论逐条 Redis GET | 20 | 305ms | 15.2% |
| ⑤ 敏感词过滤 | 每条评论对 200 个敏感词逐词 replaceAll | 20 | 184ms | 9.2% |
| ⑥ token 校验 + DTO 组装 | — | — | 1ms | 0.0% |

五段合计 1988ms，与业务层父段对账闭合（第五节规则：子段和与父段差距超过 10% 必须重拆——本例对上了，才允许进入优化）。

两个取证要点：

1. 慢查询日志只抓到 ①② 两条。③ 的 60 条 SQL 单条 8~14ms，全部低于 0.5s 阈值，慢日志一条不落——这就是 N+1 的隐蔽性：每条都"不慢"，合起来 718ms。抓 N+1 要看调用次数（Arthas trace 里 mapper 出现 60 次、SkyWalking 的 span 数），不能只看慢日志。
2. "评论内容不多、数据量才几万"与 2s 耗时并不矛盾。①② 是每次请求全表扫描 4.6 万行：表上只有后台审核场景建的 `(audit_status, ...)` 索引，前台按 problem_id 查询一条都用不上；③④ 是一屏 20 条评论被放大成 60 次 SQL 加 20 次 Redis 往返。逐条看都不起眼，叠起来就是 2 秒。

### 8.5 第 4~5 步　逐轮优化与复测（每轮单一变量）

以下每轮只改一个因素，改完立即用同脚本同轮数复测，数值均来自复测结果。

#### 第二轮　N+1 批量化（③ 718ms → 24ms）

循环内逐条查改为收集 userId 后批量 IN 查询，3 个维度各一条 SQL，60 次往返变 3 次：

```java
// 反例：循环体内 60 次 SQL
for (Comment c : list) {
    c.setUser(userMapper.selectInfo(c.getUserId()));
    // ...等级、统计同样逐条查
}
// 正例：出循环，3 次 SQL
List<Long> ids = list.stream().map(Comment::getUserId).distinct().toList();
Map<Long, UserVO> users = userMapper.selectBatch(ids).stream()
    .collect(Collectors.toMap(UserVO::getId, Function.identity()));
```

端到端 2011 → 1317ms。

#### 第三轮　点赞状态批量读（④ 305ms → 4ms）

20 次逐条 GET 改为一次 MGET（20 个 key 一次往返），网络往返从 20 次变 1 次。端到端 1317 → 1016ms。

#### 第四轮　前台覆盖索引（① 262ms → 12ms，② 518ms → 35ms）

按 4.1 节列顺序规则（等值列在前、排序列居中）新建前台索引，后台索引保留不动，两个索引服务两个查询形态：

```sql
CREATE INDEX idx_comment_front ON oj_solution_comment (problem_id, status, created_at DESC);
```

- COUNT：`problem_id + status` 命中索引前缀，纯索引扫描，EXPLAIN 的 Extra 从 `Using where` 变为 `Using index`，262ms → 12ms。
- SELECT：索引本身按 `created_at DESC` 有序，filesort 消除；只为 20 行结果回表取 content，518ms → 35ms。
- 与案例一那次覆盖索引的差异：那次 COUNT 的过滤列不在索引里，必须把 status 补进索引才零回表；这次过滤列就是索引前缀，LIMIT 20 只回表 20 行。覆盖索引的判定标准是回表行数，不是绝对不回表——为 20 行回表把 content 大字段塞进索引，写入代价远大于收益。

端到端 1016 → 283ms。

#### 第五轮　敏感词过滤预编译（⑤ 184ms → 3ms）

```java
// 反例：每条评论 × 200 个词逐词全串扫描，且 replaceAll 每次现场编译 Pattern
for (String w : SENSITIVE_WORDS) { content = content.replaceAll(w, "***"); }
// 正例：静态预编译合并为一次扫描
private static final Pattern SENSITIVE =
    Pattern.compile("(" + String.join("|", SENSITIVE_WORDS) + ")", Pattern.CASE_INSENSITIVE);
content = SENSITIVE.matcher(content).replaceAll("***");
```

端到端 283 → 102ms。至此未命中缓存的裸链路优化完毕：2011ms → 102ms，降低 94.9%。

#### 第六轮　首页短 TTL 缓存（混合约 25ms）

按 4.2 节四要素落地：

| 要素 | 取值 | 说明 |
| --- | --- | --- |
| Key | `algoviz:front:cmt:list:{problemId}:{page}:{size}` | 前台无筛选维度，比案例一管理端少 keyword、auditStatus 两维 |
| TTL | 60s + 随机 0~15s 偏移 | 热门题访问集中，随机偏移防止同时过期 |
| 失效 | 新增评论时 SCAN 该题前缀并删除 | 前台高频场景用 SCAN 不用 KEYS（案例一管理端低频才允许 KEYS）；点赞数接受 60s 延迟，产品确认过 |
| 降级 | Redis 异常直查 DB | 裸链路已到 102ms，DB 扛得住降级流量 |

命中约 11ms，未命中 102ms，按 85% 命中率混合约 25ms。缓存放在六轮最后一步是有意的：先把裸链路修到能扛，再上缓存——否则缓存一旦大面积失效，数据库瞬间回到 2s 乘以并发量的状态。

### 8.6 第 6 步　归档与防复发

数据归档见第九节。沉淀三条进代码评审清单：列表接口禁止循环内查库（一律批量化）；跨网络逐条读写必须合并为批量（Redis MGET/pipeline、ES mget 同理）；新查询场景上线前 EXPLAIN 确认命中索引。前两条已并入第七节预防性条款。

## 十、区分「真实瓶颈」和「伪瓶颈」（本次踩坑重点）

### 常见伪瓶颈

1. **减法得到的残留时间缺口**：客户端总耗时减部分环节得到的 “其他”，不一定是网络、Tomcat，很可能是业务层代码没有被统计进去。
2. TCP Nagle、Delay‑ACK：仅在特定小包分片场景才会产生延迟；**优先确认业务层耗时，不要上来调 TCP 参数**。本次调整 TCP_NODELAY、Cookie 配置完全没有收益，真正瓶颈在 Argon2 纯 Java 实现。
3. 不要盲目怀疑框架（Tomcat/Spring）：绝大多数业务接口慢，问题不在容器本身，容器过滤、路由、参数绑定通常只有零点几毫秒。

> 判断：给每一段业务逻辑做**服务端真实埋点**，而不是靠客户端减法猜。

## 十一、优化完成后评估指标

1. 绝对值：平均耗时、p50/p95/p99 耗时；
2. 相对值：延迟下降百分比、速度提升倍数；
3. 抖动：看逐轮测试的最大最小差值，确认优化后是否稳定。

> 本次案例结果：总延迟降低 71.13%，处理速度提升约 3.46 倍。

## 十二、避坑

1. ❌ 不要跳过埋点，直接上来改 YAML 调 TCP、线程池；
2. ❌ 不要把客户端减法算出来的 “剩余时间” 直接归给网络、Tomcat；
3. ❌ 脚本模拟组件的时候，忽略脚本和后端底层实现差异；
4. ❌ 索引排序字段顺序乱改，为了覆盖索引导致 filesort；
5. ❌ 缓存只写 TTL，业务变更不主动删除缓存，产生脏数据；
6. ❌ KDF 加密参数无脑拉满，或者选择性能很差的纯 Java 密码实现。
