# 索引优化

分析得知  评论列表耗时 110ms 明显过长

## 优化过程

```
-- ============================================================================
-- 迁移说明：题解/评论审核管理列表查询索引优化
--
-- 背景：
--   后台管理员按 audit_status 筛选评论/题解列表时，COUNT 查询耗时 ~90ms
--   根因：现有索引 (audit_status, created_at) 不含 status 列，
--   MySQL 判定 status != 'DELETED' 时必须回表（随机 I/O），4.6 万行 = 36K 次回表
--
-- 优化：
--   将 status 作为索引尾列加入，变为覆盖索引 (audit_status, created_at, status)
--   - COUNT: 纯索引扫描，零回表
--   - SELECT + ORDER BY created_at DESC + LIMIT: 索引正序读 → created_at DESC，
--     status 从索引取 → 零回表，LIMIT 20 只读 20 条
--   - status 放在末尾不改变索引排序，不影响 ORDER BY 优化
--
-- 幂等：先 DROP IF EXISTS 再 CREATE
-- ============================================================================

-- USE algoviz;  -- 按实际库名修改，或命令行 -D 指定

-- ① oj_solution_comment：评论审核列表覆盖索引
DROP INDEX idx_comment_audit ON oj_solution_comment;
CREATE INDEX idx_comment_audit ON oj_solution_comment (audit_status, created_at DESC, status);

-- ② oj_solution：题解审核列表覆盖索引
DROP INDEX idx_solution_audit ON oj_solution;
CREATE INDEX idx_solution_audit ON oj_solution (audit_status, created_at DESC, status);

```

**问题背景**

后台管理员按 `audit_status` 筛选的查询 SQL：

```
WHERE audit_status = 'pending' AND status != 'DELETED' ORDER BY created_at DESC
```

现有旧索引：`(audit_status, created_at)`，**不包含 `status` 列**。 执行流程：MySQL 通过索引定位到 `audit_status='pending'` 的 36000 行后，**需要回表**（通过主键索引读取完整行数据）才能判断 `status != 'DELETED'`，36000 次随机 IO，耗时约 90ms。

**优化方案**

将 `status` 添加到索引，调整为**覆盖索引**，MySQL 直接从索引中读取 `status` 字段，**无需回表**，`EXPLAIN` 可看到 `Using index`。

> ✅ 最终索引：`(audit_status, created_at, status)`

**为什么 `status` 放在第 3 列，不放在第 2 列？**

- ✅ `(audit_status, created_at, status)`：索引排序顺序为 `audit_status → created_at`，原生匹配 `ORDER BY created_at DESC`，排序优化不受影响。
- ❌ 如果设置为 `(audit_status, status, created_at)`：索引内部排序变成 `audit_status → status → created_at`，不同`status`分组下`created_at`不连续，`ORDER BY created_at DESC` **会触发 filesort 文件排序**，性能反而变差。

**优化效果**

- 评论列表接口：116ms → 34ms，性能提升 70.5%
- COUNT 统计查询：90ms → 32ms

# Redis缓存

能不能加上redis缓存

## 优化过程

两个 Service 统一新增 3 项改动：

1. 注入依赖：`StringRedisTemplate redis` + `ObjectMapper objectMapper`
2. `adminList()` 方法：优先查询 Redis，缓存命中直接返回；未命中查询数据库，查询成功后写入缓存
3. 审核 / 状态变更操作：操作完成后主动清理对应列表缓存
   - `adminPassAudit` / `adminRejectAudit`：审核操作后清理缓存
   - `adminUpdateStatus`（题解上下架）：状态变更后清理缓存

**缓存设计**

| 项目       | 说明                                                         |
| ---------- | ------------------------------------------------------------ |
| 缓存 Key   | 评论列表：`algovize:admin:cmt:list:{keyword}:{auditStatus}:{page}:{pageSize}`题解列表：`algovize:admin:sol:list:{keyword}:{auditStatus}:{page}:{pageSize}`👉 `keyword`/`auditStatus` 为空时使用 `_` 占位 |
| TTL        | 2 小时（和 Sa-Token token 超时时间保持一致）                 |
| 读缓存逻辑 | `redis.opsForValue().get(key)` → JSON 反序列化为 `PageResult` |
| 写缓存逻辑 | `redis.opsForValue().set(key, JSON字符串, 2, HOURS)`         |
| 清缓存逻辑 | 通过 `redis.keys(prefix + ":*")` 匹配同前缀所有 key，批量删除✅ 说明：管理员审核属于低频手动操作，`keys()` 扫描无性能风险 |
| 降级策略   | Redis 读写异常时，打印警告日志，自动降级直查数据库，不阻断业务 |

**缓存失效时机**

1. 管理员审核通过某条评论 / 题解 → 清除该类型全部列表缓存
2. 管理员审核驳回某条评论 / 题解 → 清除该类型全部列表缓存
3. 管理员上下架题解 → 清除该类型全部列表缓存
4. 缓存自然过期（2 小时）

**预期效果**

1. 首次查询（缓存未命中）：走数据库查询（约 34ms）+ 写入缓存（约 1ms）
2. 后续查询（缓存命中）：Redis GET + JSON 反序列化，耗时约 1~2ms
3. 管理员翻页、相同筛选条件重复查询时，接口耗时由 34ms 降低至个位数毫秒

**验证方式**

重启后端服务使新代码生效，使用基准脚本压测验证；缓存命中后，评论列表接口耗时应下降至个位数 ms。

## 分析

**上述结论：200ms 的大头不是 DB 查询（才 3.8ms），也不是 Redis（0.73ms）。** 占 98.2% 的「其它」就是 `API 登录端到端 − 4 步纯 SQL/Redis`，主要由这几件事构成：

- `LoginLockService.checkLock` + `recordFailure` 两次锁检查 + Redis 读写
- `loginLogMapper.insert(successLog)` 写登录日志表（INSERT + 事务提交）
- `sysUserMapper.updateLastLogin` UPDATE 语句提交
- Java 框架 JSON 序列化 / Servlet 线程调度 / HTTP 往返

**BCrypt 输出固定：60 个字符**（定长，不会变化) 

Argon2输出**可变长度**，取决于配置的内存 m、迭代 t、并行 p、盐长度、hash 输出字节数一般96字符

## 修改

**9 步拆解（你要求的序号 1~9）**

| #    | 名称                               | 测什么                                                       |
| :--- | :--------------------------------- | :----------------------------------------------------------- |
| ①    | SQL 查用户(sys_user)               | `SELECT ... WHERE username=? LIMIT 1` 纯 SQL                 |
| ②    | SQL 查角色(sys_user_role/sys_role) | 角色 JOIN 纯 SQL                                             |
| ③    | SQL 权限 UNION（6 表）             | sys_permission 支 UNION sys_menu 支，对应 `findPermissionCodesByUserId` |
| ④    | Sa-Token 生成 token + Redis        | uuid4 + 2 条 SET EX + 2 条 DELETE，模拟 StpUtil.login/logout |
| ⑤    | 密码校验 Argon2id / BCrypt         | id=1 或 `algovize` → Argon2id（m=16384KB, t=2, p=1）；否则 → BCrypt（严格对齐后端逻辑） |
| ⑥    | LoginLock 两次 checkLock + reset   | 2 次 Redis GET（按 identifier 和真实 username） + 1 次 Redis DEL（成功路径 reset 清理失败计数+锁标记），对应 `LoginLockService.checkLock ×2 + reset` |
| ⑦    | login_log 登录日志 INSERT          | 插入 1 行 `login_log(status='success')` + commit；**提交后 DELETE** 避免脚本污染登录日志表 |
| ⑧    | UPDATE sys_user.last_login_time    | `UPDATE sys_user SET last_login_time=NOW(), last_login_ip=? WHERE id=?` + commit；**提交后写回原值**，避免修改真实用户的 last_login_time |
| ⑨    | JSON/Servlet/Tomcat/HTTP 往返      | = API 登录端到端 − (①+②+③+④+⑤+⑥+⑦+⑧)                         |

- **9 字段独立统计**：最快 / 最慢 / 平均 / 中位 + 分布条 + 占 API 百分比（①~⑨都显示）
- **平均耗时分布百分比柱**：9 行 + 百分比 + 实心条
- **逐轮明细表**：9 列（API登录 + ①~⑧ + ①~⑧合计 + ⑨其它）

## 修改

**✅ ① 直接开关：`application.yml` 开 `TCP_NODELAY`（必改，干掉 160ms 的 90%）**

**✅ ② Sa-Token cookie 别写双份 `Secure`（减少 Set-Cookie 头 = 减少 TCP 分段触发）**

YAML

```yaml
sa-token:
  token-name: satoken
  timeout: 7200
  active-timeout: -1
  is-concurrent: true
  is-share: false
  token-style: random-uuid
  is-log: false
  is-read-header: false
  is-read-body: false
  is-read-cookie: true
  cookie:
    http-only: true
    same-site: lax       # 不要用 none（本地 http 环境尤其不要）
    secure: false        # 本地开发必须 false；线上 https 再 true
    path: /
```

# 第九轮测试

## deepseekv4-fash 分析得知

**根因：Argon2id 密码校验在 Java 端太慢**

- 登录接口对超级管理员（algovize）走 [PasswordEncoderUtil.java](file:///D:/daima/XiangMu/算法数据结构可视化/AlgoVize/houduan/src/main/java/com/algoviz/common/util/PasswordEncoderUtil.java) 的 `argon2Matches`，参数 m=16MB / t=2 / p=1
- 旧实现用的是 **BouncyCastle 纯 Java** Argon2 → 同样的参数比 C 参考实现慢 **3~5 倍**，实测每次校验 **~130-150ms**
- 这是 Argon2 的设计特性（内存困难 KDF 本来就慢），但纯 Java 实现放大了它

**次因：基准脚本把耗时标错位置（误导排查方向）**

- 脚本里 `⑨-5 = ⑨合计 − (HTTP+Tomcat+Servlet+JSON)` 是个**减法残留项**
- 脚本⑤测密码用的是 **Python C 库**（几十 ms），比真实 Java 端快得多，所以「Java 比 C 慢的那段差额」全部落进 ⑨-5，并错误标成「Spring return 后」
- 于是 9-5a/5b/5c 全是 0、5 张卡加起来 <1ms，而 150ms「凭空消失」——实际它一直都在 Controller 方法体里

**之前 TCP_NODELAY / menus / cookie 三项没压掉 150ms，是因为它们根本不在这条路径上**（它们压的是网络层，而 150ms 在业务层）。

# 区别

<a id="diff"></a>

**BouncyCastle 实现   argon2‑jvm实现区别**

| 对比项                                 | BouncyCastle bcpkix‑jdk18on（纯 Java 实现）                  | argon2‑jvm:2.11（JNA 调用官方 C 库）                         |
| -------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 底层实现                               | 完整**纯 Java**实现 Argon2id 算法，不依赖任何本地 so/dll 库GitHub | JNA 绑定调用**Argon2 官方 C 参考实现**，jar 内置各平台预编译本地二进制库GitHub |
| 运行依赖                               | 只依赖 JDK，跨平台零本地库，全平台直接运行                   | 运行时加载 C 原生库；支持 Windows/Linux/macOS；小众架构（BSD 等）缺少预编译二进制会报错GitHub |
| 你的实测耗时（同参数 m=16384,t=2,p=1） | 密码校验约 **150ms**                                         | 密码校验约 **30‑41ms**，**速度提升 3‑5 倍**                  |
| 性能瓶颈                               | Argon2 是内存硬算法，大量内存块拷贝、异或运算，Java 堆对象 + GC 开销大；JIT 很难把内存密集循环优化到 C 同等水平GitHub | C 直接操作堆外内存，SIMD 指令优化，内存拷贝开销极低；仅 JNA 调用层有极小的 Java‑C 边界开销 |
| 哈希输出格式                           | 标准 PHC 格式 `$argon2id$v=19$m=...`                         | **完全一样的 PHC 格式**，可互相校验对方生成的哈希，历史密码不用迁移 |
| GC 压力                                | 大量 Java 堆内临时对象，产生不少短期 GC 对象                 | 核心计算全部在 C 堆外内存；Java 堆几乎不产生临时对象，降低 GC 压力 |
| 安全强度                               | ✅Argon2id 算法本身安全强度相同；安全等价                     | ✅算法完全一致，安全强度等价，是 PHC 官方参考实现             |
| 生产风险点                             | 性能差，高并发登录场景 CPU 压力大                            | 需要关注容器环境：Docker 镜像下确认本地库能正常加载；阿里云 / 华为云标准 x86‑64、arm64 服务器都支持 |
| SpringSecurity 关系                    | SpringSecurity 内置`Argon2PasswordEncoder`底层就是 BouncyCastle 纯 Java 实现GitHub | 不属于 SpringSecurity 内置，需要自己封装工具类               |
