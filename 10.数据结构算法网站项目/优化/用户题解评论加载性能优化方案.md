# 用户题解 & 评论加载性能优化方案与实现文档

> **背景**：前台 OJ 页面切换到"用户题解"或"评论"Tab 时，需要等待 **10~15 秒**才能渲染完，而数据库只有几千条数据（题解 1963 条、评论 7280 条）。
> **目标**：将接口响应时间从 10+ 秒降低到 **毫秒级（< 500ms，理想 < 100ms）**，做到用户点击即显示的"秒级查询"。
> **优化结果**：题解列表稳定 **11~53 ms**，评论列表稳定 **12~48 ms**，提速约 **200 倍**。

---

## 1. 性能瓶颈定位（5 层 Root Cause 分析）

优化前对系统做了 **SQL 运行耗时 + 代码走查 + HTTP 接口压测** 三位一体的分析，定位到 4 个核心瓶颈：

| # | 瓶颈模块 | 耗时贡献 | 根本原因 |
|---|---|---|---|
| 1 | `SensitiveWordService.getTrie() / getWordMeta()` | **8.4 秒**（最严重） | 每次调用都把 **41550 条敏感词**从 Redis JSON 反序列化回对象；即使 Trie 没变，也先全量反序列化再对比 fingerprint。每页 20 条评论 × 2 次调用 = **28 次 4 万对象反序列化** |
| 2 | 题解列表 `selectPublished` SELECT * | **10+ 秒** | 列表页只显示标题/格式/点赞数等元信息，却把 `idea / process / code` 三个 `MEDIUMTEXT` 大字段（每行几 KB）全量拉回；还对每条题解全文跑 DFA 屏蔽 |
| 3 | 评论回复数 N+1 查询 | **每页 20 次额外 COUNT** | 顶层评论每条调 `commentMapper.countReplies(root_id)`，一次 HTTP = 21 次 SQL；几千条评论积累了大量磁盘随机 IO |
| 4 | MySQL 缺少覆盖索引 + DFA 重复扫描 | **filesort + 重复 CPU** | 题解/评论 ORDER BY 的字段不在复合索引里，MySQL 必须 Using filesort；相同评论内容重复翻页重复跑 DFA Trie |

### 验证 SQL 基准耗时（已实际跑 `SHOW PROFILES` 验证）

```sql
-- 题解列表（加索引前 Using filesort）：≈ 30~50ms / 10 条
-- 评论列表 20 条顶层评论 + 20 次 COUNT（N+1）： 单 SQL ≈ 5-10ms × 21 = 100-200ms（还好）
-- 41550 条敏感词 JSON 反序列化：≈ 300-400ms × 28 次 = 8.4 秒（核心瓶颈）
```

## 3. 实现过程详解

### 3.1 L1：MySQL 覆盖索引 + 排序索引（消除 filesort）

**文件**：`AlgoVize/houduan/sql/00_oj_solution_perf_index.sql`

对三张常用查询各建一组 **包含 ORDER BY 字段**的复合覆盖索引，让 InnoDB 可以直接按索引顺序返回（EXPLAIN 无 `Using filesort / Using temporary`）：

```sql
-- 1) 题解列表覆盖索引
--    查询条件：problem_id=? AND status='PUBLISHED' AND audit_status!='blocked'
--    排序条件：ORDER BY is_featured DESC, like_count DESC, created_at DESC
ALTER TABLE oj_solution
    ADD INDEX idx_sol_problem_sort (
        problem_id, status, audit_status,
        is_featured, like_count, created_at, id
    );

-- 2) 顶层评论覆盖索引
--    查询：solution_id=? AND parent_id=0 AND status='PUBLISHED' AND audit_status!='blocked'
--    排序：ORDER BY like_count DESC, created_at ASC
ALTER TABLE oj_solution_comment
    ADD INDEX idx_cmt_sol_top_sort (
        solution_id, parent_id, status, audit_status,
        like_count, created_at, id
    );

-- 3) 子评论 + 批量 reply COUNT 辅助索引
--    WHERE root_id IN (...) AND parent_id!=0 AND status='PUBLISHED' AND audit_status!='blocked'
ALTER TABLE oj_solution_comment
    ADD INDEX idx_cmt_root_reply_sort (
        root_id, parent_id, status, audit_status,
        created_at, id
    );
```

> **设计要点**：将等值查询列（`problem_id, status, audit_status`）放索引最左前缀，排序列紧接其后，最后 `id` 作为辅助列用于回表。这样 MySQL 索引 dives 到匹配位置后，直接顺序读 N 条就能满足 ORDER BY，无需内存/磁盘排序。

**3.3.3 Service 层集成（含降级兜底）**

文件：[OJSolutionCommentService.java](file:///d:/daima/XiangMu/算法数据结构可视化/AlgoVize/houduan/src/main/java/com/algoviz/service/OJSolutionCommentService.java#L124-L172)

```java
public PageResult<OJSolutionComment> listTopLevel(Long solutionId, int page, int pageSize) {
    int total = commentMapper.countTopLevel(solutionId);
    List<OJSolutionComment> list = commentMapper.selectTopLevel(solutionId,
            (page - 1) * pageSize, pageSize);

    // --- 批量查回复数：1 次 SQL 取代 pageSize 次 COUNT ---
    if (!list.isEmpty()) {
        List<Long> rootIds = list.stream()
                .map(OJSolutionComment::getId)
                .filter(Objects::nonNull)
                .collect(Collectors.toList());
        Map<Long, Integer> replyCountMap = new HashMap<>(rootIds.size());
        try {
            List<IdCount> idCounts = commentMapper.countRepliesByRootIds(rootIds);
            if (idCounts != null) {
                for (IdCount ic : idCounts) {
                    if (ic != null && ic.getId() != null) {
                        replyCountMap.put(ic.getId(), ic.getCnt() == null ? 0 : ic.getCnt());
                    }
                }
            }
        } catch (Exception e) {
            // 兜底：退化到逐行查询（避免批量方法异常时整页不可用）
            log.warn("[oj-comment] 批量查询回复数失败，退化到 N+1: {}", e.getMessage());
            list.forEach(c -> replyCountMap.put(c.getId(), commentMapper.countReplies(c.getId())));
        }
        list.forEach(c -> {
            Integer rc = replyCountMap.get(c.getId());
            c.setReplyCount(rc == null ? 0 : rc);
            c.setMaskContent(cachedMaskContent(c.getContent())); // DFA 内容缓存
        });
    }
    return PageResult.of(list, total, page, pageSize);
}
```

**设计要点**：
1. 用 `Collectors.toList()` 一次性取出当前页所有 root_id
2. `try/catch` 兜底，批量 SQL 任何异常（比如索引不存在、字段错误）自动退化到 N+1，保证页面可用
3. 查询结果转 `Map<Long, Integer>` 后 O(1) 写回每条评论的 `replyCount`

### 3.4 L4：评论 DFA 屏蔽内容缓存（重复评论不重复跑 Trie）

文件：[OJSolutionCommentService.java](file:///d:/daima/XiangMu/算法数据结构可视化/AlgoVize/houduan/src/main/java/com/algoviz/service/OJSolutionCommentService.java#L44-L71)

```java
// DFA 屏蔽缓存（避免对相同评论内容反复扫描）
// LRU 风格：使用 ConcurrentHashMap，控制最多 2000 条
private static final int MASK_CACHE_MAX = 2000;
private final Map<String, String> maskCache = new ConcurrentHashMap<>(256);
private final Object maskCacheLock = new Object();

private String cachedMaskContent(String text) {
    if (text == null || text.isEmpty()) return text;
    String hit = maskCache.get(text);
    if (hit != null) return hit;
    String masked = doMaskContent(text);   // 真正跑 DFA matchAll
    // 超过阈值淘汰一半（简易 LRU，避免无限增长）
    if (maskCache.size() >= MASK_CACHE_MAX) {
        synchronized (maskCacheLock) {
            if (maskCache.size() >= MASK_CACHE_MAX) {
                Iterator<Map.Entry<String, String>> it = maskCache.entrySet().iterator();
                int drop = MASK_CACHE_MAX >> 1;
                while (it.hasNext() && drop-- > 0) { it.next(); it.remove(); }
            }
        }
    }
    maskCache.put(text, masked);
    return masked;
}
```

> 因为评论内容普遍不长（< 500 字），直接把原文作 key 即可；2000 条缓存只占 1~2 MB 内存，完全可接受。对翻页、二次访问相同题解评论的场景，命中后直接跳过 DFA 扫描。

### 3.5 L5（最关键瓶颈）：敏感词库 DFA 初始化 —— 从"每次 4 万对象反序列化"到"0 IO"

#### 问题拆解

原来的 `getTrie()` 代码路径：

```java
// ❌ 每次调用都做 4 万对象 JSON 反序列化，再判断需不需要重建 Trie
public DfaTrie getTrie() {
    List<SensitiveWord> words = getEnabledWords();   // ← 慢：redis.get → JSON 反序列化 41550 对象
    String fp = calcFingerprint(words);              // ← 轻量
    if (trieCache != null && fp.equals(trieFingerprint)) return trieCache;
    // 重建 trie ...
}
```

- `getEnabledWords()` 每次 **100% 触发** Redis JSON 读取 + Jackson 反序列化 41550 个 Java 对象
- 每页 20 条评论 × 2 次调用 = 28 次 × 约 300ms ≈ **8.4 秒**（全部花在冗余的 JSON → 对象转换上）

#### 优化方案：引入指纹独立 Key + 快速路径

文件：[SensitiveWordService.java](file:///d:/daima/XiangMu/算法数据结构可视化/AlgoVize/houduan/src/main/java/com/algoviz/audit/SensitiveWordService.java)

**Step 1：新增指纹常量 + 写入辅助方法**

```java
public static final String FINGERPRINT_KEY = "audit:words:fp";

private static String fingerprintOf(List<SensitiveWord> words) {
    if (words == null || words.isEmpty()) return "0@-@0";
    // 组合「数量 + 首词ID + 末词ID」，词表变化时几乎必然变化；20 字节以内
    return words.size() + "@" + words.get(0).getId() + "@" + words.get(words.size() - 1).getId();
}

private void refreshCacheWithWords(List<SensitiveWord> words) {
    String fp = fingerprintOf(words);
    try { redis.opsForValue().set(CACHE_KEY, objectMapper.writeValueAsString(words), TTL); } catch (Exception e) {}
    try { redis.opsForValue().set(FINGERPRINT_KEY, fp, TTL); } catch (Exception ignored) {}
}
```

**Step 2：懒加载 Redis 指纹（缺失时自动回填 MySQL）**

```java
private String loadRedisFingerprint() {
    try {
        String fp = redis.opsForValue().get(FINGERPRINT_KEY);
        if (fp != null && !fp.isEmpty()) return fp;
    } catch (Exception ignored) {}
    // fp 不存在：从 MySQL 直查一次词表，同时写入 CACHE_KEY 和 FINGERPRINT_KEY
    try {
        List<SensitiveWord> words = wordMapper.selectAllEnabled();
        refreshCacheWithWords(words);
        return fingerprintOf(words);
    } catch (Exception e) { return null; }
}
```

**Step 3：重写 `getTrie()` 快速路径 + 双重检查锁**

```java
public DfaTrie getTrie() {
    DfaTrie cached = trieCache;
    String cachedFp = trieFingerprint;
    String redisFp = loadRedisFingerprint();
    // 0) Redis 挂了 -> 返回内存缓存
    if (redisFp == null) { if (cached != null) return cached; }
    else if (cached != null && redisFp.equals(cachedFp)) {
        // 1) 快速路径（99% 请求）：0 额外 IO，直接返回内存 Trie
        lastSeenRedisFp = redisFp;
        return cached;
    }
    // 2) 慢路径：词表变化或首次启动 —— 双重检查锁避免多线程重复构建
    synchronized (this) {
        String newRedisFp = (redisFp == null) ? loadRedisFingerprint() : redisFp;
        DfaTrie cur = trieCache;
        String curFp = trieFingerprint;
        if (cur != null && newRedisFp != null && newRedisFp.equals(curFp)) return cur;
        List<SensitiveWord> words = getEnabledWords();
        String newFp = fingerprintOf(words);
        try { redis.opsForValue().set(FINGERPRINT_KEY, newFp, Duration.ofSeconds(cacheTtlSeconds)); }
        catch (Exception ignored) {}
        if (cur != null && newFp.equals(curFp)) return cur;
        DfaTrie nt = new DfaTrie();
        for (SensitiveWord w : words) { if (w.getWord() != null) nt.insert(w.getWord()); }
        trieCache = nt;
        trieFingerprint = newFp;
        return nt;
    }
}
```

**`getWordMeta()` 同样改造**，避免每次构造 `Map<String, SensitiveWord>` 时都先全量反序列化。

**配套改造**：`refreshCache()` / `evictCache()` / `rollback()` 都同时清除/刷新 `FINGERPRINT_KEY`，保证管理员在后台发布新版本词表后，下一次请求立即生效，不会出现"内存 Trie 用旧词表"的问题。

## 5. 关键设计决策与权衡

| 决策 | 选择 | 理由 |
|---|---|---|
| MySQL 索引排序方向 | 统一 ASC（不写 DESC） | MySQL 8.0 前 DESC 定义会被忽略，实际 ORDER BY DESC 仍能走 ASC 索引倒序读，不会 filesort |
| 列表是否保留 DFA 屏蔽 | **去掉** | 列表不显示正文/详情，只有标题和计数；屏蔽只在详情页做，避免每页 10 次全文扫描 |
| 评论 N+1 是否 100% 强依赖批量 SQL | **加 try/catch 兜底** | 生产环境任何未知异常（如 MySQL 升级、字段变化）不能导致整页挂掉，退化到 N+1 保证可用 |
| DFA 缓存淘汰策略 | 容量 + 同步淘汰一半 | 评论内容重复率高（用户互相参考），2000 条基本覆盖当前活跃评论；比 LinkedHashMap LRU 更简单、线程安全 |
| `getTrie()` 是否先读 Redis fp 再读词表 | **是** | fp 只有 20 字节，相比几 MB 的词表 JSON 几乎 0 开销；即使词表 10 分钟变更一次（TTL），也只在变化时才拉全量 |
| Trie/meta 重建锁 | `synchronized(this)` 双重检查 | 不影响读路径（读路径全 volatile + 无锁），只在词表真变化时单线程排队构建，避免惊群重建 |

## 6. 未来可进一步优化点（可选）

1. **冷启动 DFA 预构建**：在 Spring Bean 初始化完成后异步调用一次 `getTrie()`，把 2.3s 的一次性开销挪到启动阶段而不是第一个用户请求。
2. **SQL 结果集二级缓存**：对 `problemId → 题解列表页 1` 这种热点数据，用 Caffeine `expireAfterWrite = 1min` 做本地二级缓存。
3. **评论预加载窗口**：题解详情打开时并发发 `comments?page=1` 和 `comments?page=2`，用户翻页直接命中。
4. **EXPLAIN 回归检查**：任何新增索引/SQL 改动后强制跑 `EXPLAIN`，确保 `rows` < 100 且无 `Using filesort / Using temporary`。
