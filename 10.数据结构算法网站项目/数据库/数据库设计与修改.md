# 整体设计说明

数据库设计规范总结

本项目数据库采用标准化、高性能、可扩展、可迭代的统一设计规范，整体遵循**高性能写入、防遍历泄露、易扩展、可分表、规范统一**的设计原则，具体规范总结如下：

**1.** **主键ID设计规范**

区分业务场景差异化选型：用户、核心流水等核心业务表采用 **BIGINT 自增****主键**，保障高写入性能；日志、关联类非核心表采用 **32位压缩**UUID**字符串主键，避免ID自增规律泄露，防止爬虫遍历爬取数据。所有数据表必须设置主键，统一无例外。

**2. 索引设计规范**

遵循“够用不冗余”原则，通过唯一索引保障业务数据唯一性，普通索引覆盖高频查询场景，严格控制索引数量，避免索引过多降低数据库写入性能；同时统一索引命名规范，唯一索引以 **uk_** 前缀、普通索引以 **idx_** 前缀命名，规范化、易维护。

**3. 字段类型统一规范**

全库统一字段类型标准，规避精度与兼容问题：金额字段使用整型（分）或 DECIMAL(10,2)，禁止浮点类型丢失精度；布尔状态统一使用 TINYINT(1) 存储 0/1；业务状态字段采用 VARCHAR(20)，摒弃ENUM类型，避免后续业务变更需修改表结构；所有数据表强制预留 **created_at、updated_at** 时间字段，统一自动维护数据创建与更新时间。

**4. 表结构扩展性设计**

所有业务表预留扩展字段，关联表采用解耦设计，支持后续业务迭代、功能拓展，无需大幅修改原有表结构；针对日志、流水类大数据量表，预留时间、用户维度分表方案，支撑千万级数据量级的性能稳定，保障长期查询与写入效率。

**5. 数据库基础约束与脚本规范**

全局统一使用 InnoDB 引擎、utf8mb4 字符集，兼容所有字符与表情存储；摒弃物理外键，通过业务代码+唯一索引保障数据完整性，提升数据库并发性能；所有建表脚本以 **DROP TABLE IF EXISTS** 开头，支持脚本可重复执行；所有数据表、字段必须配备详细注释，提升可读性与可维护性。

## **增加索引**

```
-- ============================================================================
-- 迁移说明：题解/评论审核管理列表查询索引优化
--
-- 背景：
--   后台管理员按 audit_status 筛选评论/题解列表时，COUNT 查询耗时 ~90ms
--   根因：现有索引 (audit_status, created_at) 不含 status 列，
--   MySQL 判定 status != 'DELETED' 时必须回表（随机 I/O），4.6 万行 = 36K 次回表
--
-- 优化：
--   将 status 作为索引尾列加入，变为覆盖索引 (audit_status, created_at, status)
--   - COUNT: 纯索引扫描，零回表
--   - SELECT + ORDER BY created_at DESC + LIMIT: 索引正序读 → created_at DESC，
--     status 从索引取 → 零回表，LIMIT 20 只读 20 条
--   - status 放在末尾不改变索引排序，不影响 ORDER BY 优化
--
-- 幂等：先 DROP IF EXISTS 再 CREATE
-- ============================================================================

-- USE algoviz;  -- 按实际库名修改，或命令行 -D 指定

-- ① oj_solution_comment：评论审核列表覆盖索引
DROP INDEX idx_comment_audit ON oj_solution_comment;
CREATE INDEX idx_comment_audit ON oj_solution_comment (audit_status, created_at DESC, status);

-- ② oj_solution：题解审核列表覆盖索引
DROP INDEX idx_solution_audit ON oj_solution;
CREATE INDEX idx_solution_audit ON oj_solution (audit_status, created_at DESC, status);
```

> **行数上限计算逻辑**（InnoDB 16KB 页 + 4GB Buffer Pool 假设）：
>
> | 因素                            | 影响                                                         |
> | ------------------------------- | ------------------------------------------------------------ |
> | **主键 bigint 自增**            | 顺序写入，B+Tree 紧凑无碎片，Buffer Pool 利用率高            |
> | **主键 UUID**                   | 随机写入导致页分裂碎片化，有效页密度降至 50-70%，上限降低 30-50% |
> | **索引数量**                    | 每个二级索引在 INSERT/UPDATE 时额外维护一棵 B+Tree，写放大约等于索引数 |
> | **行宽 (text/mediumtext/blob)** | 大字段存溢出页，每行占多个页，Buffer Pool 可缓存行数骤降     |
> | **append-only 日志表**          | 无 UPDATE/DELETE 碎片，bigint 自增顺序写，上限可达 5000万级  |
> | **无分区表**                    | 超过上限后 B+Tree 层级从 3 层升至 4 层，点查回表 IO 增加     |
>
> **降速临界点**：当 **活跃数据 + 全部索引总大小 > Buffer Pool 容量** 时，磁盘随机 IO 成为主要瓶颈，查询响应时间从 ms 级恶化至 10-100ms 级。
