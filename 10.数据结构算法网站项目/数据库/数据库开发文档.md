### 1. `user` — C 端用户主表

#### 用途说明

C 端用户主表，存储账号基础信息（用户名、邮箱、密码、昵称、头像）、金币余额、各模块访问统计（AI 对话次数、数据结构/算法/OJ 访问次数）、登录状态与时间。是整个 algoviz 平台的核心实体表，被 `login_log`、`coin_purchase`、`submission`、`oj_solution`、`interview_favorite` 等十余张表通过 `user_id` 外键关联。

#### 完整建表 SQL

```sql
DROP TABLE IF EXISTS `user`;

CREATE TABLE `user` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `username` varchar(50) COLLATE utf8mb4_unicode_ci NOT NULL,
  `email` varchar(100) COLLATE utf8mb4_unicode_ci NOT NULL,
  `password` varchar(255) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `age` int DEFAULT NULL,
  `gender` varchar(10) COLLATE utf8mb4_unicode_ci DEFAULT '未知',
  `nickname` varchar(100) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `avatar_url` varchar(500) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `login_status` varchar(20) COLLATE utf8mb4_unicode_ci DEFAULT 'offline',
  `status` tinyint DEFAULT '1' COMMENT '1:正常 0:封禁',
  `coins` int NOT NULL DEFAULT '1000' COMMENT '用户金额',
  `created_at` datetime DEFAULT CURRENT_TIMESTAMP,
  `updated_at` datetime DEFAULT CURRENT_TIMESTAMP,
  `last_login_at` datetime DEFAULT CURRENT_TIMESTAMP,
  `ai_dialogues` int DEFAULT '0' COMMENT 'AI对话次数',
  `ds_visits` int DEFAULT '0' COMMENT '数据结构访问次数',
  `algo_visits` int DEFAULT '0' COMMENT '算法访问次数',
  `oj_visits` int DEFAULT '0' COMMENT 'OJ访问次数',
  `last_visit_time` datetime DEFAULT NULL COMMENT '最后访问时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_username` (`username`),
  UNIQUE KEY `uk_user_email` (`email`),
  KEY `idx_user_nickname` (`nickname`),
  KEY `idx_user_created_at` (`created_at`),
  KEY `idx_user_status_created` (`status`,`created_at`),
  KEY `idx_user_gender_created` (`gender`,`created_at`),
  KEY `idx_user_login_created` (`login_status`,`created_at`)
) ENGINE=InnoDB AUTO_INCREMENT=942009 DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='用户表';
--修改SQL 增加冗余字段
ALTER TABLE `user` 
ADD COLUMN `is_deleted` TINYINT(1) NOT NULL DEFAULT 0 COMMENT '逻辑删除 0=正常 1=已删除';
```

#### 索引设计理由

| 索引名                    | 类型 | 字段                         | 理由                                  |
| ------------------------- | ---- | ---------------------------- | ------------------------------------- |
| PRIMARY                   | 主键 | `id`                         | 自增主键，聚簇索引                    |
| `uk_user_username`        | 唯一 | `username`                   | 用户名登录去重，保证唯一性            |
| `uk_user_email`           | 唯一 | `email`                      | 邮箱注册/找回密码去重                 |
| `idx_user_nickname`       | 普通 | `nickname`                   | 按昵称搜索用户（模糊查询）            |
| `idx_user_created_at`     | 普通 | `created_at`                 | 按注册时间排序/筛选新用户             |
| `idx_user_status_created` | 复合 | `(status, created_at)`       | 管理后台筛选正常/封禁用户并按时间排序 |
| `idx_user_gender_created` | 复合 | `(gender, created_at)`       | 按性别统计用户分布，配合时间范围      |
| `idx_user_login_created`  | 复合 | `(login_status, created_at)` | 筛选在线/离线用户并按注册时间排序     |

#### 不足之处

1. `login_status` 用 varchar 存储 online/offline，应改为 tinyint 或 enum 减少存储空间。

   已修改

   ```
   -- ============ ① 存量值迁移：online→0(在线)、其余→1(离线) ============
   UPDATE `user`
   SET `login_status` = CASE
       WHEN `login_status` IN ('online', '0') THEN 0
       ELSE 1
   END;
   
   -- ============ ② 改类型：varchar(20) -> tinyint(1) ============
   -- 语义：0 = 在线（已登录），1 = 离线（默认值，新注册用户离线）
   ALTER TABLE `user`
       MODIFY COLUMN `login_status` TINYINT(1) NOT NULL DEFAULT 1
       COMMENT '登录状态: 0=在线 1=离线';
   
   -- 索引 idx_user_login_created（含 login_status, created_at）类型变更后自动适配，无需重建
   ```

2. `gender` 同样用 varchar，存储效率低。

3. 缺少手机号字段（`phone`），无法支持手机号注册/登录。

4. 密码字段长度 255 偏大，若使用 BCrypt(60) 可缩短，但若考虑 Argon2id 则合理。

5. 各模块访问统计字段（`ai_dialogues`、`ds_visits` 等）直接放在用户主表，高频更新会导致行锁竞争。

6. 缺少逻辑删除字段（`is_deleted`）。

7. 没有第三方登录关联（OAuth/OpenID）

```
-- 18============ user 表结构升级：gender 整型化 / 手机号预留 / 逻辑删除 / 注销状态
-- 语义约定：
--   gender       TINYINT(1)  : 1=男 0=女，NULL=未知（原 '男'/'女'/'未知' 字符串迁移）
--   phone        VARCHAR(20) : 手机号，预留字段，暂不启用（先不加唯一索引）
--   is_deleted   TINYINT(1)  : 0=正常 1=已逻辑删除；所有业务 SQL 必须带 is_deleted=0
--   status       TINYINT(1)  : 1=正常 0=封禁 -1=注销
-- 唯一索引策略（重要）：
--   uk_user_username / uk_user_email 保持不变 —— 逻辑删除/注销后用户名与邮箱
--   永久占用，新用户注册不可复用（防止冒名注册）。应用层注册查重使用
--   "不过滤 is_deleted" 的查询提前拦截，唯一索引作为并发兜底。
-- ============================================================================

-- ① gender: varchar(10) -> tinyint(1)，'男'->1，'女'->0，'未知'/其他->NULL
UPDATE `user`
SET `gender` = CASE `gender`
    WHEN '男'   THEN '1'
    WHEN '女'   THEN '0'
    ELSE NULL
END;

ALTER TABLE `user`
    MODIFY COLUMN `gender` TINYINT(1) DEFAULT NULL
    COMMENT '性别: 1=男 0=女';

-- ② 新增手机号（预留字段，暂不启用，不建唯一索引）
ALTER TABLE `user`
    ADD COLUMN `phone` VARCHAR(20) DEFAULT NULL
    COMMENT '手机号（预留，暂不启用）' AFTER `email`;

-- ③ 新增逻辑删除字段：0=正常 1=已删除
ALTER TABLE `user`
    ADD COLUMN `is_deleted` TINYINT(1) NOT NULL DEFAULT 0
    COMMENT '逻辑删除: 0=正常 1=已删除' AFTER `status`;

-- ④ status 语义升级：1=正常 0=封禁 -1=注销（先兜底 NULL 数据，再收紧 NOT NULL）
UPDATE `user` SET `status` = 1 WHERE `status` IS NULL;
ALTER TABLE `user`
    MODIFY COLUMN `status` TINYINT(1) NOT NULL DEFAULT 1
    COMMENT '账号状态: 1=正常 0=封禁 -1=注销';

-- ⑤ 索引重建：is_deleted 作为前导等值列，保证所有业务 SQL 带 is_deleted=0 后
--    筛选 + ORDER BY created_at 全部走索引（is_deleted=1 行极少，过滤成本极低）
DROP INDEX `idx_user_created_at`   ON `user`;
CREATE INDEX `idx_user_deleted_created`       ON `user` (`is_deleted`, `created_at`);

DROP INDEX `idx_user_status_created` ON `user`;
CREATE INDEX `idx_user_deleted_status_created` ON `user` (`is_deleted`, `status`, `created_at`);

DROP INDEX `idx_user_gender_created` ON `user`;
CREATE INDEX `idx_user_deleted_gender_created` ON `user` (`is_deleted`, `gender`, `created_at`);

DROP INDEX `idx_user_login_created` ON `user`;
CREATE INDEX `idx_user_deleted_login_created`  ON `user` (`is_deleted`, `login_status`, `created_at`);

-- ⑥ 唯一索引无需改动：uk_user_username / uk_user_email 天然覆盖"含已删除行"的
--    全局唯一性，逻辑删除/注销账号的用户名与邮箱永久不可再注册。
```

### 2.user_oauth 第三方账号

#### 用途说明

user_oauth 表用于存储用户各个第三方 OAuth 账号绑定信息，实现一个用户可绑定多个第三方账号，解耦第三方数据与 user 主表。

#### 完整建表SQL

```
CREATE TABLE `user_oauth` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '自增主键',
  `user_id` BIGINT UNSIGNED NOT NULL COMMENT '关联user表主键ID',
  `oauth_type` TINYINT NOT NULL COMMENT '第三方平台类型枚举 1=Gitee 2=GitHub 3=GitLab',
  `openid` VARCHAR(128) NOT NULL COMMENT '第三方平台用户唯一标识',
  `unionid` VARCHAR(128) NULL DEFAULT NULL COMMENT '同一厂商跨应用统一ID，无则null',
  `client_id` VARCHAR(128) NULL DEFAULT NULL COMMENT '第三方应用clientId，区分不同客户端',
  `bind_scene` TINYINT NOT NULL DEFAULT 1 COMMENT '绑定场景：1注册自动绑定 2用户手动账号绑定',
  `bind_status` TINYINT NOT NULL DEFAULT 0 COMMENT '绑定状态：0正常 1授权已撤销 2授权过期',
  `nickname` VARCHAR(64) NULL DEFAULT NULL COMMENT '第三方返回昵称，仅展示，以user主表为准',
  `avatar` VARCHAR(512) NULL DEFAULT NULL COMMENT '第三方头像地址',
  `access_token` VARCHAR(1024) NULL DEFAULT NULL COMMENT '加密存储access_token，不存明文，不需要可删除字段',
  `refresh_token` VARCHAR(1024) NULL DEFAULT NULL COMMENT '加密存储刷新令牌',
  `token_encrypted` TINYINT(1) NOT NULL DEFAULT 1 COMMENT '0未加密 1已加密，标识token字段是否AES加密',
  `expires_at` DATETIME NULL DEFAULT NULL COMMENT 'token过期时间',
  `last_token_refresh_time` DATETIME NULL DEFAULT NULL COMMENT 'token最后刷新时间',
  `raw_profile` TEXT NULL DEFAULT NULL COMMENT 'OAuth原始返回JSON快照，用于调试扩展',
  `is_deleted` TINYINT(1) NOT NULL DEFAULT 0 COMMENT '逻辑删除：0正常 1解绑删除',
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',

  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_type_openid` (`oauth_type`, `openid`, `is_deleted`) COMMENT '同一个平台openid只能绑定一个有效用户，解绑后允许重新绑定',
  KEY `idx_user_id` (`user_id`) COMMENT '快速查询某个用户全部第三方绑定',
  KEY `idx_oauth_type` (`oauth_type`) COMMENT '按平台检索'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户第三方OAuth绑定表(优化版)';

```

| idx_oauth_type | oauth_type                   | 按第三方平台筛选数据                                         |

#### 不足之处

| 序号 | 不足点                             | 说明                                                         |
| ---- | ---------------------------------- | ------------------------------------------------------------ |
| 1    | 缺少绑定时间、解绑时间             | 只有通用 create_time/update_time；无法精确知道**什么时候绑定、什么时候解绑授权**，审计排查不方便。update_time 会被 token 刷新、状态变更乱覆盖，不能代表解绑时刻。 |
| 2    | 没有失败记录能力                   | OAuth 流程报错、授权拒绝、token 刷新失败，本表只存成功绑定的数据；失败流程无法留存记录，排查第三方对接故障困难。 |
| 3    | raw_profile 无大小控制             | TEXT 无长度限制，如果第三方返回超大 JSON，会造成行膨胀，拖慢查询。 |
| 4    | 不支持 OAuth1.0 协议               | 当前全部按照 OAuth2 / OpenID Connect 设计；如果以后要对接老平台 OAuth1.0，字段不兼容。 |
| 5    | client_id 仅做记录，未加入唯一索引 | `uk_type_openid(oauth_type,openid,is_deleted)`没有带上 client_id。同一 openid、不同 clientId（不同第三方应用）会被判定为同一个账号；如果对接同一厂商多个不同 clientId 应用会冲突。 |
| 6    | 没有账号冲突操作记录               | 第三方登录遇到「openid 已经绑定其它用户」冲突场景，没有记录冲突事件，无法追溯是谁、什么时候发生账号冲突。 |
| 7    | token 过期仅靠业务代码判断         | 数据库层面没有定时机制；需要业务代码轮询 / 捕获第三方接口报错更新 bind_status，数据库本身不会自动变更状态。 |
| 8    | 缺少外部用户头像昵称同步标记       | 无法标记：第三方头像昵称是否需要自动同步到系统；每次登录要不要覆盖本地 user 昵称头像没有字段控制。 |
| 9    | 无版本标记                         | 第三方平台接口、字段变更，没有存储协议版本 (OAuth2.0/OIDC)，后期对接 OIDC 拿 id_token 时缺少记录位置。 |

#### 扩展点

| 字段                     | 类型                          | 说明                                       | 适用场景                                                  |
| ------------------------ | ----------------------------- | ------------------------------------------ | --------------------------------------------------------- |
| `bind_at`                | DATETIME                      | **绑定时间**                               | 记录该第三方账号成功绑定的精确时间，不受 update_time 干扰 |
| `unbind_at`              | DATETIME                      | 解绑时间                                   | 用户解绑 / 授权撤销时写入，用于审计统计                   |
| `oidc_id_token`          | VARCHAR(2048)                 | OIDC 的 id_token                           | 对接 OpenID Connect 时存储，建议加密保存                  |
| `oauth_protocol`         | TINYINT                       | 协议版本：1=OAuth2 2=OIDC 3=OAuth1.0       | 区分协议类型，方便多协议兼容                              |
| `sync_profile_switch`    | TINYINT(1) NOT NULL DEFAULT 0 | 0 不自动同步第三方头像昵称，1 登录自动同步 | 控制是否覆盖 user 主表昵称头像                            |
| `last_sync_profile_time` | DATETIME NULL                 | 最后一次同步第三方资料时间                 | 避免每次登录无意义重复更新                                |

### 3. `algorithm` — 算法配置表

#### 用途说明

存储算法可视化模块的算法元数据，包括算法名称、分类、描述、时间/空间复杂度、伪代码等。供前端动态渲染算法演示页面。

#### 完整建表 SQL

```sql
DROP TABLE IF EXISTS `algorithm`;

CREATE TABLE `algorithm` (
  `id` varchar(40) COLLATE utf8mb4_unicode_ci NOT NULL,
  `name` varchar(100) COLLATE utf8mb4_unicode_ci NOT NULL,
  `category` varchar(50) COLLATE utf8mb4_unicode_ci NOT NULL,
  `description` text COLLATE utf8mb4_unicode_ci,
  `time_complexity` varchar(50) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `space_complexity` varchar(50) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `pseudocode` mediumtext COLLATE utf8mb4_unicode_ci,
  `status` varchar(20) COLLATE utf8mb4_unicode_ci DEFAULT 'enabled',
  `created_at` datetime DEFAULT CURRENT_TIMESTAMP,
  `updated_at` datetime DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_algorithm_category` (`category`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='算法配置表';
```

#### 字段详解

| 字段               | 类型                  | 默认值            | 说明                        |
| ------------------ | --------------------- | ----------------- | --------------------------- |
| `id`               | varchar(40) NOT NULL  | —                 | 主键，UUID                  |
| `name`             | varchar(100) NOT NULL | —                 | 算法名称                    |
| `category`         | varchar(50) NOT NULL  | —                 | 分类（排序/搜索/图论等）    |
| `description`      | text                  | NULL              | 算法描述                    |
| `time_complexity`  | varchar(50)           | NULL              | 时间复杂度（如 O(n log n)） |
| `space_complexity` | varchar(50)           | NULL              | 空间复杂度                  |
| `pseudocode`       | mediumtext            | NULL              | 伪代码                      |
| `status`           | varchar(20)           | 'enabled'         | 状态（enabled/disabled）    |
| `created_at`       | datetime              | CURRENT_TIMESTAMP | 创建时间                    |
| `updated_at`       | datetime              | CURRENT_TIMESTAMP | 更新时间（无 ON UPDATE）    |

#### 索引设计理由

| 索引名                   | 类型 | 字段       | 理由               |
| ------------------------ | ---- | ---------- | ------------------ |
| PRIMARY                  | 主键 | `id`       | UUID 主键          |
| `idx_algorithm_category` | 普通 | `category` | 按分类筛选算法列表 |

#### 不足之处

1. `id` 使用 UUID，插入性能差。
2. `updated_at` 缺少 `ON UPDATE CURRENT_TIMESTAMP`。
3. `status` 用 varchar，存储效率低。
4. 缺少排序字段（`sort_order`），无法控制算法在前端的展示顺序。
5. 缺少浏览次数字段，无法统计算法热度。
6. `category` 未加唯一约束，无法防止重复分类名。

#### 扩展点

1. 将 `id` 改为 `bigint AUTO_INCREMENT`。
2. 增加 `sort_order int DEFAULT 0` 控制展示顺序。
3. 增加 `view_count int DEFAULT 0` 统计浏览次数。
4. 增加 `tags varchar(500)` 存储标签。
5. 增加 `difficulty varchar(20)` 标记算法难度等级。
6. `updated_at` 加 `ON UPDATE CURRENT_TIMESTAMP`。

| `status`        | varchar(20)           | 'PENDING' | 状态（PENDING/JUDGING/DONE）       |
| `runtime`       | int                   | NULL      | 运行时间（ms）                     |
| `memory`        | int                   | NULL      | 内存消耗（KB）                     |
| `error_message` | text                  | NULL      | 错误信息                           |
| `judge_log`     | text                  | NULL      | 判题日志                           |
| `create_time`   | datetime              | NULL      | 创建时间                           |
| `submit_time`   | datetime              | NULL      | 提交时间                           |
| `judge_time`    | datetime              | NULL      | 判题完成时间                       |
| `update_time`   | datetime              | NULL      | 更新时间                           |

#### 索引设计理由

| 索引名                        | 类型 | 字段            | 理由                   |
| ----------------------------- | ---- | --------------- | ---------------------- |
| PRIMARY                       | 主键 | `id`            | 自增主键               |
| `uk_submission_submission_id` | 唯一 | `submission_id` | 业务提交 ID 唯一       |
| `idx_submission_problem_id`   | 普通 | `problem_id`    | 按题目查提交记录       |
| `idx_submission_user_id`      | 普通 | `user_id`       | 按用户查提交记录       |
| `idx_submission_status`       | 普通 | `status`        | 按状态筛选（查待判题） |
| `idx_submission_submit_time`  | 普通 | `submit_time`   | 按时间排序提交列表     |

#### 不足之处

1. `create_time` 和 `update_time` 无默认值（NULL），应设 `CURRENT_TIMESTAMP`。
2. `update_time` 缺少 `ON UPDATE CURRENT_TIMESTAMP`。
3. 缺少复合索引 `(user_id, submit_time DESC)` 和 `(problem_id, submit_time DESC)`，按用户/题目查询提交列表时需要回表排序。
4. `judge_log` 用 text 类型，可能不够存储详细判题信息。
5. 缺少编译输出（compile_error）独立字段。
6. `status` 和 `result` 职责重叠，容易混淆。
7. 无分区策略，提交量大后查询性能下降。

#### 扩展点

1. `create_time` 设 `DEFAULT CURRENT_TIMESTAMP`，`update_time` 设 `ON UPDATE CURRENT_TIMESTAMP`。
2. 增加复合索引 `(user_id, submit_time DESC)` 和 `(problem_id, submit_time DESC)`。
3. 按月分区表，配合冷热数据分离。
4. 增加 `compile_error mediumtext` 独立存储编译错误。
5. 将 `judge_log` 改为 `mediumtext`。
6. 增加 `ip varchar(64)` 记录提交来源。

5. 减少冗余字段，改为 JOIN 查询或缓存。

| `problem_no`    | varchar(32) NOT NULL  | —                           | 题目编号（如 MS001） |
| `title`         | varchar(255) NOT NULL | —                           | 题目标题             |

| 索引名                      | 类型 | 字段                                         | 理由                                                  |
| --------------------------- | ---- | -------------------------------------------- | ----------------------------------------------------- |
| PRIMARY                     | 主键 | `id`                                         | 自增主键                                              |
| `uk_interview_problem_no`   | 唯一 | `problem_no`                                 | 题目编号唯一                                          |
| `idx_interview_filter`      | 复合 | `(status, category, difficulty, is_deleted)` | 列表页综合筛选：状态+分类+难度+未删除，覆盖最常见查询 |

| `idx_interview_is_frequent` | 普通 | `is_frequent`                                | 高频题推荐                                            |

1. 将 `tags` 关联到 `interview_tag` 表，建立 `interview_problem_tag` 多对多关联表。
2. 将计数迁移到 Redis 或独立统计表。

4. 增加 `source varchar(100)` 标记题目来源（字节、腾讯等）。

```sql
  `updated_at` datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '记录更新时间',
```


#### 字段详解

| 字段         | 类型                  | 默认值                      | 说明                 |
| ------------ | --------------------- | --------------------------- | -------------------- |
| `id`         | bigint AUTO_INCREMENT | —                           | 主键                 |
| `user_id`    | bigint NOT NULL       | —                           | 用户 ID              |
| `problem_id` | bigint NOT NULL       | —                           | 题目 ID              |
| `type`       | varchar(10) NOT NULL  | —                           | 类型（like/dislike） |
| `created_at` | datetime              | CURRENT_TIMESTAMP           | 创建时间             |
| `updated_at` | datetime              | CURRENT_TIMESTAMP ON UPDATE | 更新时间             |

#### 索引设计理由

| 索引名                | 类型 | 字段                    | 理由                      |
| --------------------- | ---- | ----------------------- | ------------------------- |
| PRIMARY               | 主键 | `id`                    | 自增主键                  |
| `uk_user_problem`     | 唯一 | `(user_id, problem_id)` | 防止同一用户重复点赞/点踩 |
| `idx_like_problem_id` | 普通 | `problem_id`            | 按题目统计点赞数          |
| `idx_like_user_type`  | 复合 | `(user_id, type)`       | 按用户查看点赞/点踩列表   |

4. `updated_at` 对于仅插入的记录意义不大。

#### 扩展点

1. 将 `type` 改为 `tinyint`（1=like 2=dislike）。
2. 增加 `is_active tinyint DEFAULT 1` 支持软删除。
3. 如果允许同时 like 和 dislike，将唯一约束改为 `(user_id, problem_id, type)`。
4. 移除不必要的 `updated_at`（纯插入表不需要）。

### 22. `sensitive_word` — 敏感词词库表

#### 用途说明

存储平台敏感词词库，支持按分类（辱骂/政治/广告/色情/其他）和风险级别（高/中/低）管理。支持精确匹配和模糊匹配两种模式。数据量较大（AUTO_INCREMENT 已到 41857）。

> **注**: 原 SQL 中 COMMENT 因编码乱码，以下为根据字段名推断的中文注释。

#### 完整建表 SQL

```sql
DROP TABLE IF EXISTS `sensitive_word`;

CREATE TABLE `sensitive_word` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `word` varchar(128) NOT NULL COMMENT '敏感词',
  `category` varchar(32) NOT NULL DEFAULT 'ABUSE' COMMENT '分类: ABUSE(辱骂)/POLITICS(政治)/ADVERTISING(广告)/PORN(色情)/OTHER(其他)',
  `level` varchar(16) NOT NULL DEFAULT 'MEDIUM' COMMENT '级别: HIGH(高风险)/MEDIUM(中风险)/LOW(低风险)',
  `match_mode` varchar(16) NOT NULL DEFAULT 'EXACT' COMMENT '匹配模式: EXACT/FUZZY',
  `enabled` tinyint NOT NULL DEFAULT '1' COMMENT '是否启用',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_word` (`word`)
) ENGINE=InnoDB AUTO_INCREMENT=41857 DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='敏感词词库表';
```

#### 字段详解

| 字段          | 类型                  | 默认值                      | 说明         |
| ------------- | --------------------- | --------------------------- | ------------ |
| `id`          | bigint AUTO_INCREMENT | —                           | 主键         |
| `word`        | varchar(128) NOT NULL | —                           | 敏感词，唯一 |
| `category`    | varchar(32) NOT NULL  | 'ABUSE'                     | 分类         |
| `level`       | varchar(16) NOT NULL  | 'MEDIUM'                    | 级别         |
| `match_mode`  | varchar(16) NOT NULL  | 'EXACT'                     | 匹配模式     |
| `enabled`     | tinyint NOT NULL      | 1                           | 是否启用     |
| `create_time` | datetime              | CURRENT_TIMESTAMP           | 创建时间     |
| `update_time` | datetime              | CURRENT_TIMESTAMP ON UPDATE | 更新时间     |

#### 索引设计理由

| 索引名    | 类型 | 字段   | 理由                     |
| --------- | ---- | ------ | ------------------------ |
| PRIMARY   | 主键 | `id`   | 自增主键                 |
| `uk_word` | 唯一 | `word` | 敏感词唯一，防止重复录入 |

#### 不足之处

1. 缺少 `(category, enabled)` 复合索引，按分类查询启用词时全表扫描。
2. `category`、`level`、`match_mode` 用 varchar，存储效率低。
3. 敏感词直接存 MySQL，加载到内存做 DFA/AC 自动机匹配时需要全表加载。
4. 缺少批量导入/导出支持。
5. 无词库版本管理（虽有 `sensitive_word_version` 表但与本表无直接关联）。

#### 扩展点

1. 增加 `KEY idx_category_enabled (category, enabled)` 索引。
2. 将 `category`、`level`、`match_mode` 改为 `tinyint`。
3. 增加 `word_hash bigint` 字段存储词的 hash 值，加速精确匹配。
4. 增加 `source varchar(50)` 标记词库来源（人工录入/第三方导入）。
5. 考虑用 Redis + DFA 算法替代全表加载。

### 1. `login_log` — C 端登录日志表

#### 用途说明

记录 C 端用户每次登录的详细信息，包括 IP、设备信息、地理位置、登录状态和失败原因。用于安全审计、异地登录检测和登录历史展示。与 `user` 表通过 `user_id` 做一对多关联。

#### 完整建表 SQL

```sql
DROP TABLE IF EXISTS `login_log`;

CREATE TABLE `login_log` (
  `id` varchar(40) COLLATE utf8mb4_unicode_ci NOT NULL,
  `user_id` varchar(40) COLLATE utf8mb4_unicode_ci NOT NULL,
  `username` varchar(50) COLLATE utf8mb4_unicode_ci NOT NULL,
  `ip` varchar(64) COLLATE utf8mb4_unicode_ci NOT NULL,
  `device` varchar(200) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `location` varchar(200) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `login_time` datetime DEFAULT CURRENT_TIMESTAMP,
  `status` varchar(20) COLLATE utf8mb4_unicode_ci DEFAULT 'success',
  `fail_reason` varchar(255) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  PRIMARY KEY (`id`),
  KEY `idx_login_log_user_id` (`user_id`),
  KEY `idx_login_log_login_time` (`login_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='登录日志表';
```

#### 字段详解

| 字段          | 类型                 | 默认值            | 说明                                  |
| ------------- | -------------------- | ----------------- | ------------------------------------- |
| `id`          | varchar(40) NOT NULL | —                 | 主键，UUID                            |
| `user_id`     | varchar(40) NOT NULL | —                 | 用户 ID（关联 user.id，但类型不匹配） |
| `username`    | varchar(50) NOT NULL | —                 | 用户名（冗余字段）                    |
| `ip`          | varchar(64) NOT NULL | —                 | 登录 IP 地址                          |
| `device`      | varchar(200)         | NULL              | 设备信息（User-Agent）                |
| `location`    | varchar(200)         | NULL              | 地理位置                              |
| `login_time`  | datetime             | CURRENT_TIMESTAMP | 登录时间                              |
| `status`      | varchar(20)          | 'success'         | 登录状态（success/fail）              |
| `fail_reason` | varchar(255)         | NULL              | 失败原因                              |

#### 索引设计理由

| 索引名                     | 类型 | 字段         | 理由               |
| -------------------------- | ---- | ------------ | ------------------ |
| PRIMARY                    | 主键 | `id`         | UUID 主键          |
| `idx_login_log_user_id`    | 普通 | `user_id`    | 按用户查询登录历史 |
| `idx_login_log_login_time` | 普通 | `login_time` | 按时间范围查询日志 |

#### 不足之处

1. `user_id` 类型为 varchar(40)，但 `user.id` 为 bigint，类型不匹配导致 JOIN 时隐式转换，性能差。
2. `id` 使用 UUID(varchar(40))，插入时随机 IO，对 InnoDB 聚簇索引不友好。
3. 缺少复合索引 `(user_id, login_time)`，按用户查询登录历史时需要回表排序。
4. `status` 用 varchar 存储，效率低。
5. 缺少登录类型字段（区分密码登录、第三方登录等）。
6. 无分区/归档策略，日志数据量大后会拖慢查询。

#### 扩展点

1. 将 `user_id` 改为 `bigint`，与 `user.id` 类型一致。
2. 将 `id` 改为 `bigint AUTO_INCREMENT`，或使用雪花 ID。
3. 增加复合索引 `(user_id, login_time DESC)`。
4. 增加 `login_type` 字段区分登录方式。
5. 按月分区，配合归档策略定期清理历史数据。
6. 将 `status` 改为 `tinyint`（0=失败 1=成功）。

### 2.`api_log` — API 日志表

#### 用途说明

记录所有 API 请求的详细日志，包括请求路径、HTTP 方法、状态码、响应时间、请求/响应体、客户端 IP、用户 ID 等。用于性能监控和问题排查。数据量大，高频写入。

**但是用户量太大不建议入库输出到日志文件用ELK 需要进行改造为后台管理系统人员**

**前端改造为EFK日志系统，因为用户量大**

#### 完整建表 SQL

```sql
DROP TABLE IF EXISTS `api_log`;

CREATE TABLE `api_log` (
  `id` varchar(40) COLLATE utf8mb4_unicode_ci NOT NULL,
  `api_path` varchar(255) COLLATE utf8mb4_unicode_ci NOT NULL,
  `http_method` varchar(10) COLLATE utf8mb4_unicode_ci NOT NULL,
  `status_code` int DEFAULT '200',
  `response_time` int DEFAULT '0' COMMENT '单位 ms',
  `client_ip` varchar(64) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `request_body` mediumtext COLLATE utf8mb4_unicode_ci,
  `response_body` mediumtext COLLATE utf8mb4_unicode_ci,
  `error_message` text COLLATE utf8mb4_unicode_ci,
  `user_id` varchar(32) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `create_time` datetime DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_api_log_path` (`api_path`),
  KEY `idx_api_log_create_time` (`create_time`),
  KEY `idx_userid_createtime` (`user_id`,`create_time` DESC),
  KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='API日志表';
```

#### 字段详解

| 字段            | 类型                  | 默认值            | 说明           |
| --------------- | --------------------- | ----------------- | -------------- |
| `id`            | varchar(40) NOT NULL  | —                 | 主键，UUID     |
| `api_path`      | varchar(255) NOT NULL | —                 | API 路径       |
| `http_method`   | varchar(10) NOT NULL  | —                 | HTTP 方法      |
| `status_code`   | int                   | 200               | 状态码         |
| `response_time` | int                   | 0                 | 响应时间（ms） |
| `client_ip`     | varchar(64)           | NULL              | 客户端 IP      |
| `request_body`  | mediumtext            | NULL              | 请求体         |
| `response_body` | mediumtext            | NULL              | 响应体         |
| `error_message` | text                  | NULL              | 错误信息       |
| `user_id`       | varchar(32)           | NULL              | 用户 ID        |
| `create_time`   | datetime              | CURRENT_TIMESTAMP | 创建时间       |

#### 索引设计理由

| 索引名                    | 类型 | 字段                          | 理由                              |
| ------------------------- | ---- | ----------------------------- | --------------------------------- |
| PRIMARY                   | 主键 | `id`                          | UUID 主键                         |
| `idx_api_log_path`        | 普通 | `api_path`                    | 按 API 路径查询                   |
| `idx_api_log_create_time` | 普通 | `create_time`                 | 按时间范围查询                    |
| `idx_userid_createtime`   | 复合 | `(user_id, create_time DESC)` | 按用户查询请求历史，按时间倒序    |
| `idx_create_time`         | 普通 | `create_time`                 | 与 `idx_api_log_create_time` 重复 |

#### 不足之处

1. `idx_create_time` 与 `idx_api_log_create_time` 完全重复，冗余索引。
2. `id` 使用 UUID，高频写入时随机 IO 严重影响性能。
3. `user_id` 类型为 varchar(32)，与 `user.id` (bigint) 不匹配。
4. `request_body` 和 `response_body` 用 mediumtext，大请求体会导致行膨胀。
5. 无分区/归档策略，日志表数据量增长后严重影响性能。
6. `http_method` 用 varchar，效率低。

#### 扩展点

1. 移除冗余的 `idx_create_time` 索引。
2. 将 `id` 改为 `bigint AUTO_INCREMENT` 或使用雪花 ID。
3. 将 `user_id` 改为 `bigint`。
4. 按天/周分区表，定期归档历史数据。
5. 将 `request_body`/`response_body` 改为存储到 ES 或对象存储，数据库只存摘要。
6. 将 `http_method` 改为 `varchar(6)` 或 `enum`。

### 2.user_visit_stat

#### 用途说明

> 模块访问统计拆分至独立的 `user_visit_stat` 表，把模块访问次数、最后访问时间这类高频更新的额外业务信息从用户主统计表剥离出去，避免高频 Update 冲击主表，实现读写隔离，降低主表行锁、页分裂风险、与用户核心数据解耦

#### 为什么这么设计

- 保留用户核心聚合指标（刷题数量、金币、评论数、总在线时长等）。
- `user_visit_stat`：独立存储**用户 + 模块**维度的访问聚合数据，访问计数做数据库原子自增，不侵入用户主表。
- 优势：新增 / 调整统计模块时仅操作本表，无需对用户主表执行 DDL 变更。

#### 完整建表SQL

```
CREATE TABLE IF NOT EXISTS `user_visit_stat` (
    `user_id`         BIGINT   NOT NULL COMMENT '用户ID（user.id，1:1）',
    `ai_dialogues`    INT      NOT NULL DEFAULT 0 COMMENT 'AI对话次数',
    `ds_visits`       INT      NOT NULL DEFAULT 0 COMMENT '数据结构访问次数',
    `algo_visits`     INT      NOT NULL DEFAULT 0 COMMENT '算法访问次数',
    `oj_visits`       INT      NOT NULL DEFAULT 0 COMMENT 'OJ访问次数',
    `last_login_at`   DATETIME DEFAULT NULL COMMENT '最后登录时间',
    `last_visit_time` DATETIME DEFAULT NULL COMMENT '最后访问时间（任一模块上报时刷新）',
    `updated_at`      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (`user_id`),
    KEY `idx_uvs_last_visit` (`last_visit_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

#### 字段详解

| 字段            | 说明             | 拆分理由                                     |
| --------------- | ---------------- | -------------------------------------------- |
| ai_dialogues    | AI 对话次数      | 业务统计计数器，频繁更新，不参与用户基础查询 |
| ds_visits       | 数据结构访问次数 | 访问计数，高频 update                        |
| algo_visits     | 算法访问次数     | 访问计数                                     |
| oj_visits       | OJ 访问次数      | OJ 模块访问计数                              |
| last_login_at   | 最后登录时间     | 登录行为统计                                 |
| last_visit_time | 最后访问时间     | 用户页面访问时间，频繁更新                   |

#### 不足之处

- **"免 DDL"目标未完全达成**：宽表仍是"一模块一列"，新增统计模块（如课程、竞赛）时依旧需要 `ALTER TABLE ADD COLUMN`；拆表只是把 DDL 影响面从 `user` 主表缩小到本表，并非真正的零 DDL 扩展。
- **只有累计值、无时间切片**：表内仅存累计计数 + 最后访问时间，无法回溯任意一天的真实访问量。Dashboard 的 today/yesterdayAIDialogues 实际是用 `last_visit_time` 推导的**近似口径**（最近 24h 活跃用户的累计对话总和，数值偏大），也无法生成历史趋势曲线。
- **无防刷 / 去重机制**：上报接口不做频控，PV 语义下脚本连发即累加（并发 20 次 = 恰好 +20），计数可被刷高；缺少 UV（同用户同模块每日至多计 1 次）口径。
- **前端埋点未接入**：后端上报 / 查询 / Dashboard 聚合链路已闭环，但前台 ds/algo/oj/ai 四个页面尚未调用 `POST /api/visit/{module}`，当前计数几乎全部来自脚本与 curl 触发，真实用户行为数据缺失。
- **单用户行级写热点未消除**：upsert 每次都命中同一 `user_id` 行，重度用户高频上报时仍在本表内竞争行锁（只是不再波及 `user` 主表），写放大依旧存在。
- **职责混搭**：表名为"访问统计"，却同时承载 `last_login_at`（登录行为）与各模块访问计数；只能记录最后一次登录，无法支撑登录历史类需求。
- **行数只增不减**：注销 / 逻辑删除用户的 stat 行按口径永久保留（审计需要），又无归档机制，表体积随历史注册用户量线性增长。

#### 未来扩展

- **日汇总表（精确趋势与活跃口径）**：新增 `user_visit_daily`（唯一键 `user_id + module_code + visit_date`，字段 `visit_count`），上报时与宽表同步 upsert；Dashboard 今日 / 昨日、趋势图、日活 / 周活、模块访问占比、留存分析全部改查此表，彻底消除近似口径。
- **Redis 写缓冲**：上报先走 Redis `INCR`，定时任务（如每分钟）批量回写 MySQL，消除行锁竞争与写放大；Redis 持久化 + 定时对账任务兜底，防止缓冲数据丢失。
- **行式改造（真正的零 DDL）**：宽表转为行式结构 `user_visit_stat(user_id, module_code, visit_count)`，新增模块仅需注册一个 module_code 枚举值，无需任何 DDL；一次性迁移脚本转换存量数据。
- **防刷与 UV 口径**：上报接口增加"同用户同模块 N 秒去重"（Redis SETNX）或"每日每模块至多计 1 次"的 UV 语义，保证计数抗刷。
- **登录日志独立**：需要多端登录记录 / 异地登录提醒时，新增追加式 `user_login_log` 表；本表 `last_login_at` 维持"最后一次登录"语义不变。
- **归档与预聚合**：注销用户 stat 行超过 N 年后迁移至归档表；用户量上来后将 Dashboard 聚合改为定时预聚合 + 缓存，替代每次请求的实时 `SUM ... JOIN user`。

```
CREATE TABLE IF NOT EXISTS `user_visit_stat` (
    `user_id`         BIGINT   NOT NULL COMMENT '用户ID（user.id，1:1）',
    `ai_dialogues`    INT      NOT NULL DEFAULT 0 COMMENT 'AI对话次数',
    `ds_visits`       INT      NOT NULL DEFAULT 0 COMMENT '数据结构访问次数',
    `algo_visits`     INT      NOT NULL DEFAULT 0 COMMENT '算法访问次数',
    `oj_visits`       INT      NOT NULL DEFAULT 0 COMMENT 'OJ访问次数',

    `last_visit_time` DATETIME DEFAULT NULL COMMENT '最后访问时间（任一模块上报时刷新）',

    PRIMARY KEY (`user_id`),
    KEY `idx_uvs_last_visit` (`last_visit_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- ② 存量迁移（INSERT IGNORE 幂等，含已删除用户一并保留审计）
INSERT IGNORE INTO `user_visit_stat`
    (`user_id`,`ai_dialogues`,`ds_visits`,`algo_visits`,`oj_visits`,`last_login_at`,`last_visit_time`)
SELECT `id`,`ai_dialogues`,`ds_visits`,`algo_visits`,`oj_visits`,`last_login_at`,`last_visit_time` FROM `user`;

-- ③ 核验关卡（只读）：stat 行数=user 行数；四项 SUM 逐列相等

-- ④ 删除 user 表 6 列（③ 通过后再执行，不可逆）
ALTER TABLE `user`
    DROP COLUMN `ai_dialogues`,`ds_visits`,`algo_visits`,`oj_visits`,
    DROP COLUMN `last_visit_time`,`last_login_at`;

-- ⑤ 兜底补 stat 行（幂等）
```
