# 编程题库关键词屏蔽与审核系统开发文档

## 一、项目概述

### 1.1 项目背景

编程题库系统已引入 EFK（Elasticsearch + Fluentd + Kibana）7.12.1 日志栈，现需在此基础上构建内容安全审核体系，对用户提交的代码、问题描述等内容进行敏感词检测与危害代码识别，实现违规内容的自动发现、日志归集、人工审核与最终入库的全流程闭环管理。

### 1.2 建设目标

- **自动检测**：对用户提交的代码内容、问题描述进行实时敏感词扫描与危害代码识别
- **日志归集**：命中规则的内容自动写入 Elasticsearch 专项索引，便于汇总分析
- **定时同步**：定期将 ES 中待审核数据同步至业务数据库
- **人工审核**：提供审核后台，支持人工判定违规类型与处理结果
- **闭环管理**：审核结果回写入库，形成检测 - 审核 - 处置的完整链路

### 1.3 检测范围

表格

| 检测类别   | 检测对象                             | 检测内容                                                     |
| ---------- | ------------------------------------ | ------------------------------------------------------------ |
| 辱骂类内容 | 问题标题、问题描述、代码注释、用户名 | 脏话、人身攻击、歧视性语言、恶意调侃                         |
| 危害代码   | 提交的源代码                         | 系统命令执行、文件删除、端口扫描、挖矿代码、后门程序、无限循环攻击 |

### 2.2 数据流向说明

1. **提交检测**：用户提交代码或问题时，敏感检测服务同步扫描内容，命中规则则标记违规等级与命中详情
2. **日志输出**：业务系统将提交内容 + 检测结果以结构化日志形式输出到日志文件
3. **Fluentd 采集**：Fluentd 实时采集日志文件，解析为结构化数据后写入 Elasticsearch 对应索引
4. **定时同步**：调度任务每 30 分钟从 ES 拉取新增待审核记录，同步至 MySQL 审核表
5. **人工审核**：运营人员通过审核后台查看待审记录，判定通过 / 驳回 / 封禁
6. **结果入库**：审核结果更新至业务库，同步触发对应业务处置（如内容下架、用户封禁）

## 四、核心模块详细设计

### 4.1 敏感内容检测模块

#### 4.1.1 检测层级设计

采用**三层检测架构**，兼顾性能与准确率：

**第一层：AC 自动机快速匹配（毫秒级）**

- 基于敏感词库构建前缀树，实现多模式快速匹配
- 覆盖辱骂词、政治敏感词、违规广告等确定型词汇
- 支持全匹配、模糊匹配、拼音变体检测

**第二层：正则规则匹配（十毫秒级）**

- 针对危害代码编写专用正则规则
- 检测危险函数调用、系统命令、文件操作等模式
- 支持按编程语言分类规则

**第三层：语义加权评分（可配置开启）**

- 对上下文进行语义分析，降低误报率
- 结合命中位置、频次、上下文进行风险评分
- 高分自动标记为高危，低分进入人工复核

#### 4.1.2 辱骂词检测规则

```
检测维度：
- 基础脏词库：约 2000+ 条常用辱骂词汇
- 变体识别：谐音、拼音、拆字、符号插入等变体
- 上下文判定：单独出现的疑似词不触发，结合语境评分
- 分级机制：
  - 严重：直接辱骂、人身攻击 → 自动拦截 + 高危标记
  - 一般：低俗用语、不文明表达 → 待人工审核
  - 轻微：疑似词、边缘词汇 → 记录日志，不拦截
```

#### 4.1.3 危害代码检测规则

按编程语言分类建立规则库，核心检测项：

表格

| 风险类别 | 典型检测模式                                                | 风险等级 |
| -------- | ----------------------------------------------------------- | -------- |
| 命令执行 | `Runtime.exec()`、`os.system()`、`eval()`、`ProcessBuilder` | 高危     |
| 文件操作 | `rm -rf`、`File.delete()`、格式化磁盘相关 API               | 高危     |
| 网络攻击 | 端口扫描代码、Socket 批量连接、发包循环                     | 高危     |
| 恶意循环 | 死循环占用 CPU、内存爆炸代码                                | 中危     |
| 信息窃取 | 读取环境变量、读取系统文件、收集用户信息                    | 中危     |
| 挖矿特征 | 特定加密算法循环、矿池地址、挖矿关键词                      | 高危     |
| 后门特征 | 反向 Shell、远程代码执行模板                                | 高危     |

> 检测说明：代码检测以静态规则匹配为主，避免误判正常教学代码。对注释中的内容单独检测，代码逻辑区与注释区分开评分。

### 4.3 定时同步模块

#### 4.3.1 同步机制

采用**增量时间窗口同步**方案：

- 调度频率：每 30 分钟执行一次
- 时间窗口：查询上一个同步时间点至当前时间前 1 分钟的数据（留出写入缓冲）
- 去重策略：以 `submit_id` 为唯一键，MySQL 端唯一索引防重
- 同步范围：仅同步 `hit=true` 且 `sync_flag=false` 的记录
- 状态回写：同步成功后更新 ES 中 `sync_flag` 为 true

#### 4.3.2 同步流程

1. 读取 Redis 中记录的上次同步时间戳 `last_sync_time`
2. 构造 ES 查询：`submit_time > last_sync_time AND submit_time <= now - 60s AND hit=true AND sync_flag=false`
3. 分页滚动查询（scroll API），批量拉取数据
4. 批量写入 MySQL 审核表，冲突则跳过
5. 批量更新 ES 文档的 `sync_flag` 为 true
6. 更新 Redis 中的 `last_sync_time`
7. 记录同步日志：本次同步条数、成功数、失败数

#### 4.3.3 核心代码逻辑示意

```
// ES 查询构造
SearchSourceBuilder sourceBuilder = new SearchSourceBuilder();
BoolQueryBuilder query = QueryBuilders.boolQuery()
    .must(QueryBuilders.rangeQuery("submit_time").gt(lastSyncTime).lte(endTime))
    .must(QueryBuilders.termQuery("hit", true))
    .mustNot(QueryBuilders.termQuery("sync_flag", true));

// 滚动查询
SearchScrollRequest scrollRequest = new SearchScrollRequest(scrollId);
scrollRequest.scroll(TimeValue.timeValueMinutes(1));

// 批量写入 MySQL
auditRecordService.batchInsert(auditRecords);

// 批量更新 ES sync_flag
bulkProcessor.add(new UpdateRequest(index, docId)
    .doc(XContentFactory.jsonBuilder()
        .startObject()
        .field("sync_flag", true)
        .endObject()));
```

## 六、部署与配置方案

### 6.1 Elasticsearch 配置优化

**索引生命周期管理（ILM）**：

- 热阶段：0-7 天，主分片 3，副本 1
- 温阶段：7-30 天，分片收缩，只读
- 冷阶段：30-180 天，冻结存储
- 删除阶段：180 天后自动删除

**性能优化**：

- 审核日志索引设置 `refresh_interval: 30s`，提升写入性能
- `code_snippet` 字段设置 `index: false`，不建立倒排索引
- 开启 `_source` 压缩，节省存储空间

### 6.2 Fluentd 部署

- 采用 Sidecar 或 DaemonSet 方式部署，与业务服务同节点
- 配置缓冲队列：`buffer_chunk_limit 2M`、`buffer_queue_limit 64`

# 方案 1：预处理清洗文本（最常用，业务首选，配合 DFA）

> 
> **检测前，先把所有干扰符号全部删掉，再跑敏感词匹配**

### 需要过滤的干扰字符集合

​```
// 全部替换为空，去掉干扰
// 中英文逗号、顿号、空格、点、竖线、星号、横线、@ # $ % 等
String text = userInput
    .replaceAll("[,，、.\\|*\\-@#$%_ ]", "")
    .trim();
​```

示例：

- `微信,QQ` →清洗后→ `微信QQ`，DFA 即可命中`微信`和`QQ`
- `微,信` →清洗后→`微信`，命中敏感词

✅优点：实现简单，DFA 不需要改源码；
⚠️缺点：不能过滤**汉字、字母变形**（比如 “薇信” 这种谐音，这部分只能扩充词库）。

> 
> 注意：**原始文本不要修改保存到数据库！只做检测用，只传给敏感词检测器的临时副本做清洗，入库保留用户原始内容。**

---

# 方案 2：DFA 扩展：跳过干扰字符（高级方案）

标准 DFA 是必须连续匹配字符；
增强版 DFA：遍历文本时，如果遇到干扰符号，直接跳过，继续走状态机，**不重置状态**。

举例文本：`微 , 信`

1. 读到`微`，进入 DFA 节点【微】
2. 读到`,`，属于干扰字符，跳过，**状态不清零**
3. 读到`信`，接续上一个状态，匹配成功【微信】

> 
> houbb/sensitive‑word 开源库已经内置这个能力：支持忽略干扰符号配置，不用自己手写 DFA。

## houbb/sensitive‑word 开启跳过符号示例

​```
// 构建敏感词检测器，设置忽略的符号集合
IWordContext context = WordContext.newInstance()
        .ignoreChar(',')
        .ignoreChar('，')
        .ignoreChar('、')
        .ignoreChar(' ')
        .ignoreChar('|');
​```

# 方案 3：不要把输入文本按符号切割！（避坑重点）

❌错误做法（很多人踩坑）：

​```
// 千万不要！！
String[] parts = content.split("[,， ]");
for(String part : parts){
    匹配敏感词(part);
}
​```

> 
> 如果用户输入`微信,QQ`，split 后得到`["微信","QQ"]`好像没问题；
> 但是用户输入`我想微信,QQ聊天`，split 分割后破坏上下文，逻辑极易出错。

✅正确思路：**不要分割原文，对完整全文做扫描匹配，预处理仅删除干扰字符**。

# 区分两个业务场景（交友系统非常关键）

## 场景①：多个独立敏感词拼接 `微信,QQ`

> 
> 真实含义：同时出现 2 个敏感词。
> 预处理去掉逗号得到`微信QQ`，DFA 扫描，能同时命中 2 个词。

## 场景②：敏感词中间插干扰绕过检测 `微,信`

> 
> 黑产绕过滤手段，清洗掉中间符号还原出完整敏感词。

## 边界问题：误杀风险

> 
> 全部符号删除会带来少量误判，例如正常句子：`你好,信不信我找你`
> 清洗后变成`你好信不信我找你`，如果词库有`好信`就会误命中。

### 折中策略（推荐交友项目）

1. **第一层（快速）：原始文本直接 DFA 检测，不清洗，处理绝大多数正常情况；**
2. **第二层：如果第一层没有命中，再执行清洗干扰字符后的二次检测；**
3. 如果二次检测命中，标记为高嫌疑，**不直接拦截，可以人工审核 / 交给云内容安全 API 复核，不要直接拒绝**。

> 
> 逻辑：
> 原始文本命中 → 直接拦截；
> 原始未命中，清洗后命中 → 标记嫌疑，送人工 / 云 API，降低误杀。

| 代码区（其余）              | 同上                 | 只跑危险代码正则（DC 规则），不跑 “赌博” 类文本词 → 消除变量名误伤 |

   }
   ```

   ## 3、两种扩展模式

   ### 模式 A：静态文件扩展（你现在的 json 文件方案）

   1. 在 json 数组里追加新词条
   2. **预处理生成变体**（重点，对应截图表格）

   > 不要只存原始词，要基于基准词生成各类变体，有两种实现思路

   - 方案 1：

     入库预生成变体

     （Trie/DFA 加载时把变体全部塞进去）

     - 基准词：`赌博`
     - 自动生成：繁體`賭博`、拼音首字母`db`、l33t、去符号版本
     - 全部存入 trie 树，检测直接匹配，检测速度快；词库体积会膨胀

   - 方案 2：

     运行时预处理

     （推荐，你的架构图方案）

     > 输入文本先做归一化，再跑 DFA，**词库只存标准基准词**，不存变体 输入文本预处理流水线：

     1. 移除特殊符号
     2. 全角转半角
     3. 繁体转简体
     4. l33t 数字字母还原（`1→i`，`4→a`）
     5. 再送入 DFA 树做匹配

   > ✅优势：词库维护简单，只维护标准词，不需要维护一堆变体词条；缺点：每一条待检测文本都要跑预处理，消耗一点 CPU。

   > 拼音首字母这种，运行时很难实时计算，适合**预生成变体存入词库**。

   ### 模式 B：后台 API 动态扩展（生产环境）

   做新增敏感词 http 接口，运营页面调用接口新增，持久化到数据库，再刷新词库。

   > 注意：DFA/Trie 是内存结构。新增词后，不能只写数据库，**需要重新构建 Trie/DFA 内存树**

   - 方案 1：全量重载：新增词后，重新读取全部词库，重建 DFA，热加载，不重启服务
   - 方案 2：增量更新 Trie：难度更高，适合词库巨大场景，一般业务风控优先全量热重载。

   ## 4、扩展词完整流程（标准上线流程）

   1. **收集候选敏感词**

   2. **人工审核**：标注 category 分类、level 风险等级，排除容易误杀的词

   3. **写入存储**：json 文件 / MySQL 数据库

   4. 词库加载 & 变体处理

      - 如果是运行时归一化：只保存基准词；检测时对用户文本做预处理
      - 如果是预生成变体：生成繁简、缩写、l33t 变体，一并加载进 DFA

   5. **热更新内存 DFA，不重启服务**

   6. 单元测试验证

      ：必须写测试用例，验证原始词 + 各种变体都能命中

      ```
      基准词：赌博
      测试case：赌*博、賭博、db、g4mbl1ng，全部应该命中
      ```

   7. **灰度上线，观察误杀漏杀日志**

   ## 5、踩坑点（重点）

   1. ❌不要直接把变体全部丢进词库，词库爆炸，误杀暴涨。优先选择**输入文本运行时归一化**。
   2. ❌新增词之后忘记刷新内存 DFA，接口还是旧词库，新增词不生效（高频坑）。
   3. ❌外部词库直接导入，大量宽泛词，正常内容被拦截。
   4. ❌繁简转换、全半角处理遗漏，导致变种绕过检测。
