# 编译器

## 🔹基础概念

**编译器：把高级语言源码，完整翻译成机器语言（汇编 / 机器码），生成可执行文件。**

> 对比解释器：
>
> - ✅编译器：**整体翻译 → 生成程序文件 → 之后运行程序**；翻译和运行是两个阶段。C/C++、Rust、Go
> - ✅解释器：**读一句，翻译一句，立刻执行；不生成独立 exe**；Python (原生解释)、JS 早期浏览器解释执行
> - ✅JIT（即时编译）：混合模式；Java HotSpot，先解释执行字节码，热点代码动态编译成本地机器码。

### 编译整体四大阶段（经典流程）

1. 预处理（Pre‑process）
   - C 语言：#include 头文件展开、#define 宏替换、删除注释、条件编译
   - `.c` → 预处理后的`.i`文件
2. **编译（Compile）【狭义编译：高级语言 → 汇编】** 做词法分析、语法分析、语义分析、中间代码生成、优化；输出汇编代码 `.s`
3. **汇编（Assemble）汇编器 as** 汇编指令翻译成机器指令，生成目标文件（`.obj` Windows / `.o` Linux），**目标文件还不能直接运行，存在未解析符号**
4. 链接（Link）链接器 ld
   - 静态链接：把库的机器代码直接合并进 exe；体积大；更新库要重新编译
   - 动态链接（共享库 `.so` / `.dll`）：运行的时候加载库；程序体积更小

> 完整流程示例 GCC： `main.c` →预处理→`main.i`→编译→`main.s`→汇编→`main.o`→链接→`a.out`可执行程序

## 🧩编译器内部前端、中端、后端

### 🔹前端（Front‑end）：语言相关

1. **词法分析 (Lexer)**：拆源码字符串，得到 Token（关键字、标识符、数字、运算符）

> ```
> int a = 10 + b;` →拆成 token 序列：`int` `a` `=` `10` `+` `b` `;
> ```

1. **语法分析 (Parser)**：基于 token 生成**抽象语法树 AST**；检查语法错误（少分号、括号不匹配）
2. **语义分析**：类型检查；变量是否定义；函数参数是否匹配；类型不兼容直接报错。
3. 生成**IR 中间表示 (中间代码)**。

### 🔹中端 (Middle)：平台无关优化（重点！跨平台）

> IR（中间表示）脱离 CPU 架构；做独立于硬件的优化；常量折叠、死代码删除、循环优化。 LLVM‑IR 就是非常出名的中间码。

### 🔹后端 (Back‑end)：硬件架构相关

IR → 针对特定 CPU 架构（x86‑64 / ARM / RISC‑V）做机器相关优化；寄存器分配；生成汇编 / 机器码。

> LLVM 架构特点： 多种语言（C/C++ Rust Swift）前端生成统一 LLVM‑IR；中端优化；后端针对不同 CPU 输出机器码。 Clang 就是基于 LLVM 的 C/C++ 编译器。

## 💡面试常考区分点

1. 编译器 vs 解释器 vs JIT
   - 编译器：一次性完整翻译，运行速度快；修改源码必须重编译
   - 解释器：边翻译边跑；启动快；运行慢；脚本语言
   - JIT：先解释；运行期把频繁执行热点字节码编译成本地机器码；Java HotSpot、V8 引擎 (JS)
2. 静态语言 vs 动态语言
   - 静态语言（C++ Java）：**编译期做类型检查**
   - 动态语言（Python JS）：运行的时候才做类型检查
3. 链接：静态链接、动态链接的优缺点
   - 静态链接：exe 大；不需要依赖外部库；升级库要全部重新编译；
   - 动态链接：程序体积小；共享库可以单独升级；运行环境必须存在对应 dll/so。

### 📎补充概念：交叉编译

**在 A 架构机器上编译生成另一种架构的可执行程序。** 例：x86 PC 编译 ARM 平台程序，用于嵌入式开发。

# 解释器（Interpreter）

## 📖一句话定义

**解释器：一边读取源程序代码，一边分析、一边执行；不需要提前把整个程序全部翻译成机器码。**

> 和编译器做对比：
>
> - **编译器 (Compiler)：完整翻译。源码 → 全部翻译成目标机器代码（二进制可执行程序），之后再运行。先翻译，后执行。**
> - **解释器 (Interpreter)：边解释边跑。读一句，分析一句，执行一句；没有生成完整独立的 exe。**

## 🧩简单类比

- 编译器：**书面翻译。把整篇文章一次性全部翻译完，之后拿着译文阅读。**
- 解释器：**同声传译。一边听一句，立刻翻译一句，当场输出。**

## 两种执行模式

### 1、纯解释执行（原生解释）

直接读源码文本，边解析边跑。 早期版本 Python、Shell、JavaScript 最早版本。 缺点：每次运行都要重新做词法语法分析；速度慢。

### 2、基于字节码的解释器（虚拟机，混合模式⭐重点）

现在很多语言不是直接解释源码。 源码先编译成**中间字节码**；**然后由虚拟机里面的解释器解释字节码。**

👉 **Java 就是这种！**

```
Java源代码(.java)
→ javac编译 → 字节码(.class)
→ JVM里面的解释器解释执行字节码
```

> Java 不是纯粹编译语言，也不是纯粹解释语言；属于**先编译到字节码，再在虚拟机上解释执行；同时附带 JIT 即时编译器。**

## ✨JVM 里面：解释器 + JIT 即时编译器（热点代码编译）

JVM 有两套执行引擎：

1. **解释器：逐条解释字节码；启动快。一开始运行的时候用解释器，不用等待编译。**
2. **JIT 即时编译器 (Just‑In‑Time)：运行过程监控，发现热点代码（反复频繁执行的循环、方法）；把这一部分字节码编译成本地机器码；之后直接跑机器码，速度变快。**

> 这就是 JVM 的**混合执行模式（解释 + 即时编译）**
>
> - 刚启动：解释器快速跑；不用等编译。
> - 跑一段时间之后，热点代码交给 JIT 编译为本地机器指令；之后执行更快。

# 📌编译器、解释器、JIT 区别

表格

| 角色           | 行为                         | 产物            | 特点                           |
| -------------- | ---------------------------- | --------------- | ------------------------------ |
| 静态编译器     | 事前全部翻译源码             | 机器码 / 字节码 | 运行前完成翻译                 |
| 解释器         | 边读边执行指令               | 无输出文件      | 启动快；反复执行同段代码性能差 |
| JIT 即时编译器 | 运行的时候动态编译（运行期） | 本地机器码      | 热点代码加速；有编译耗时开销   |

AOT（提前编译）：运行前，构建阶段完成字节码→本地机器码。

|              | AOT 提前编译                                     | JIT 即时编译                             |
| ------------ | ------------------------------------------------ | ---------------------------------------- |
| 编译时机     | **运行之前（构建阶段）**                         | **程序运行期间**                         |
| 启动性能     | ✅启动快，无预热                                  | ❌启动慢，需要预热 (warm‑up)              |
| 峰值性能     | 一般；缺少运行时信息，激进优化受限               | ✅更好；依靠运行时 profiling 做投机优化   |
| 适用场景     | Serverless、命令行工具、轻量微服务（短生命周期） | 后台长运行 Java 服务（传统 Spring 业务） |
| 动态特性支持 | 麻烦，反射、动态代理需要额外配置                 | 原生完整支持 Java 全部动态能力           |

## 🗣面试口述答案

> AOT 也就是提前编译，是在程序运行之前就将字节码编译为本地机器码，把编译工作前移到构建阶段。 
>
> Java 有两种 AOT 实现：早期 JDK9 的 jaotc，依然依赖 JVM 虚拟机；现在主流是 GraalVM Native Image，可以编译出独立原生可执行程序，不需要 JVM 就可以直接运行，启动速度很快，适合 serverless 和云原生场景。
>
>  AOT 的优势就是启动快，省去运行时编译开销；但是缺点也很明显：编译的时候拿不到运行时的统计信息，很多 JIT 那种基于运行时的激进优化做不了，长期运行峰值性能往往不如 JIT；同时 Java 的反射、动态代理这类动态特性会给静态 AOT 带来很大麻烦，需要额外配置。
>
>  JIT 适合长时间运行后台业务服务；AOT 更看重冷启动速度。
>
> 补充：Project Leyden 就是 OpenJDK 的项目，目标改善 Java 启动慢的痛点，探索 AOT、镜像缓存优化

## 📝面试口述回答

> 解释器是程序执行引擎。它不需要预先把全部源代码完整翻译成机器指令；边解析代码边执行。 
>
> 早期解释器直接解释源代码；现在很多虚拟机解释的是中间字节码。
>
> 比如 JVM 的解释器执行 class 字节码。 JVM 采用混合模式：一开始由解释器执行字节码，启动速度快；对于反复执行的热点方法和循环，
>
> JIT 即时编译器会在运行期间把字节码编译成本地机器码，后续直接执行机器码以此提升性能。
>
>  和静态编译器对比：静态编译器是在运行之前就完成全部翻译工作，生成可执行文件。
