## 一、调优前置：监控体系（没有监控不要调）

### 1. 四大黄金指标（Google SRE）

任何系统先看这四个数，调优前后的对比也用这四个数衡量：

| 指标 | 含义 | 典型信号 |
| --- | --- | --- |
| 延迟 Latency | 请求耗时，分位数 | P99 RT 突增 → GC / 锁 / 慢 SQL |
| 流量 Traffic | QPS / TPS / 消息速率 | 流量翻倍 → 容量问题 |
| 错误 Errors | 错误率、异常数 | 错误率突增 → 下游故障 / 熔断 |
| 饱和度 Saturation | 资源拥挤程度 | CPU、连接池、线程池、队列水位 |

### 2. 分层监控清单

| 层面 | 必看指标 | 工具 |
| --- | --- | --- |
| 系统 | CPU、内存、磁盘 IO、网络 IO、负载、Swap、fd 数 | node_exporter + Grafana / top、vmstat |
| 应用 | QPS、RT（P50/P95/P99）、错误率、线程池活跃数、GC 次数与耗时 | Micrometer + Prometheus、SkyWalking |
| 数据库 | 慢 SQL、连接数、锁等待、buffer pool 命中率 | mysqld_exporter、慢查询日志 |
| 缓存 | 命中率、大 key、热 key、内存碎片率 | redis_exporter、--bigkeys |
| 消息 | 堆积量、消费 TPS、消费延迟 | RocketMQ Dashboard、kafka_exporter |
| 链路 | 全链路 trace、各段耗时占比 | SkyWalking（Java Agent 无侵入） |

### 3. 告警阈值参考

| 指标 | 建议阈值（P1 电话 / P2 消息） |
| --- | --- |
| CPU 使用率 | 持续 5 分钟 > 80% 报警 |
| Full GC | 1 小时 > 3 次报警；单次 > 3s 报警 |
| 接口 P99 RT | 超过基线 2 倍报警 |
| 错误率 | 5 分钟窗口 > 1% 报警 |
| 线程池队列 | 水位 > 80% 报警 |
| 磁盘 | 使用率 > 80%，inode 也要监控 |
| MQ 堆积 | 消费延迟 > 5 分钟报警 |

> 优先抓：**高 RT、高 CPU、频繁 FullGC、慢 SQL、磁盘 IO 打满、连接池耗尽**。
> 生产禁止直接在生产改，优先在测试 / 压测环境复现问题。

## 二、JVM 调优

### 1. 先定目标再动参数

延迟（P99 GC 停顿）、吞吐（GC 时间占比）、内存占用，三者最多同时优化两个。调优前必须有基线：GC 日志 + 监控至少跑一周，没有数据的调参是玄学。

### 2. 堆内存

- `-Xms` = `-Xmx`，避免运行时堆伸缩带来抖动；不要无脑给很大堆。
- 经验值：堆不超过机器/容器内存的 50~70%，剩余留给元空间、线程栈、直接内存、GC 数据结构和 page cache。
- 服务器内存 8G：堆给到 4-5G；剩余给系统、数据库、其他进程。

### 3. GC 收集器选型

| 收集器 | 版本 | 典型停顿 | 适用场景 |
| --- | --- | --- | --- |
| Parallel | JDK 8 默认 | Full GC 秒级 | 离线批处理、吞吐优先 |
| G1 | JDK 9+ 默认 | 可设目标，几十毫秒 | 在线服务通用，4G~32G 堆，**JDK17 首选** |
| ZGC | JDK 15+ 正式 | < 1ms | 高并发大堆、低延迟（交易、网关、8G+） |

G1 关键参数：

```
-XX:MaxGCPauseMillis=200               # 软目标，驱动 region 回收调度
-XX:InitiatingHeapOccupancyPercent=45  # 并发标记触发阈值
-XX:G1HeapRegionSize=8m                # 大对象多时调大
```

> G1 下**不要**手动设置 `-Xmn`、`SurvivorRatio`，交给自适应。

### 4. GC 日志必开（开销 < 1%）

```
# JDK 9+
-Xlog:gc*:file=/data/logs/gc-%t.log:time,uptime:filecount=5,filesize=50m
# JDK 8
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/data/logs/gc.log
```

拿到日志丢 [GCeasy](https://gceasy.io) 自动出报告：停顿分布、吞吐率、回收效率、内存趋势。

### 5. 频繁 FullGC 根因速查

| 现象 | 根因 | 处理 |
| --- | --- | --- |
| 老年代持续上涨至打满 | 内存泄漏或堆不足 | dump + MAT 分析 |
| 元空间打满 | 动态类泄漏（Groovy、CGLib、热部署） | 设 MaxMetaspaceSize 兜底 |
| 每小时固定时刻一次 | RMI 定时 System.gc() | 加大 gcInterval 或禁显式 GC |
| to-space exhausted | 混合回收跟不上晋升 | 扩堆、降分配速率 |
| humongous 频繁 | 大数组/大报文 | region 调大或业务分片 |

### 6. 容器环境（K8s）

```
-XX:InitialRAMPercentage=50.0 -XX:MaxRAMPercentage=75.0
-XX:ActiveProcessorCount=4          # CPU limit < 1 核时修正 GC 并行度
-XX:+ExitOnOutOfMemoryError         # OOM 立即退出交给 K8s 重启
```

容器 OOMKilled（退出码 137）的元凶通常是堆外：JVM 实际内存 = 堆 + 元空间 + 代码缓存 + 线程栈×线程数 + 直接内存，用 NMT + pmap 核对。

### 7. 生产参数模板（JDK 17 + G1）

```bash
-Xms4g -Xmx4g
-XX:MaxMetaspaceSize=512m
-XX:MaxDirectMemorySize=1g
-XX:+UseG1GC -XX:MaxGCPauseMillis=200
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump
-XX:+ExitOnOutOfMemoryError
-Xlog:gc*:file=/data/logs/gc-%t.log:time,uptime:filecount=5,filesize=50m
```

### 8. 常见坑

- 堆设置过大：GC STW 时间变长，OOM 风险。
- 没有开启 GC 日志，完全不知道 GC 状态。
- 新生代过大，老年代过小，频繁 FullGC。
- ❗不要上来就改一堆 JVM 参数，**优先定位是内存泄漏还是堆太小**。

诊断工具的完整用法见姊妹篇《JDK 生产环境检测与分析工具》。

## 三、应用层调优

### 1. Web 容器（Tomcat / Undertow）

默认 Tomcat 200 工作线程，多数场景够用；线程不是越大越好，CPU 核数才是天花板：

```yaml
# 内嵌 Tomcat
server:
  tomcat:
    threads:
      max: 200          # 工作线程，CPU 密集型给小，IO 密集型给大
      min-spare: 20
    max-connections: 8192   # 最大连接数
    accept-count: 100       # 满载后等待队列
```

高并发长连接场景可换 Undertow（NIO，IO 线程 + 工作线程分离，内存占用更低）：

```yaml
server:
  undertow:
    threads:
      io: 8        # 默认 CPU 核数，处理 IO 事件
      worker: 256  # 业务工作线程
```

### 2. 线程池（手动创建，不用 Executors）

`Executors.newFixedThreadPool` 队列无界，堆积会 OOM；`newCachedThreadPool` 线程数无上限。必须手动：

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    16,                                     // 核心：IO密集 ≈ 2×CPU核
    32,                                     // 最大
    60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),         // 有界队列，满了走拒绝策略
    new ThreadFactoryBuilder().setNameFormat("biz-pool-%d").build(), // 命名便于排查
    new ThreadPoolExecutor.CallerRunsPolicy() // 拒绝策略：让提交线程自己跑，天然限流
);
```

参数经验：

| 类型 | 线程数 |
| --- | --- |
| CPU 密集 | 核数 + 1 |
| IO 密集 | 核数 × 2 起步，按压测调 |
| 混合 | 拆成两个池分别配 |

关键配套：暴露 `getActiveCount`、`getQueue().size()` 到监控；拒绝策略触发要有日志和告警。

### 3. 数据库连接池（HikariCP）

官方公式：**连接数 = CPU 核数 × 2 + 有效磁盘数**。实践上单实例 10~20 几乎总是最优，**不是越大越好**——连接多了只会把 MySQL 打得更慢（上下文切换 + 锁竞争）。

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      minimum-idle: 20            # 与最大相等，避免伸缩抖动
      connection-timeout: 3000    # 获取连接超时
      max-lifetime: 1800000       # 必须 < MySQL wait_timeout
      leak-detection-threshold: 60000  # 连接泄漏检测（超时未归还报警）
```

> **全局约束**：所有服务的连接池总和 ≤ MySQL `max_connections` × 75%。微服务 50 个实例 × 每实例 20 连接 = 1000 连接，MySQL 默认 151 直接打满，这正是"连接池耗尽"事故的头号来源。

### 4. 缓存三大经典问题

| 问题 | 现象 | 方案 |
| --- | --- | --- |
| 穿透 | 查不存在的 key，每次打到 DB | 布隆过滤器；空值缓存（短 TTL 60s） |
| 击穿 | 热 key 过期瞬间打爆 DB | 互斥锁重建（setnx）；热点逻辑过期不删 |
| 雪崩 | 大批 key 同时过期 / Redis 挂 | TTL 加随机偏移；多级缓存（Caffeine 本地 + Redis）；集群高可用 |

缓存一致性优先用 **Canal 订阅 binlog 异步更新**，业务代码双删容易漏；用延迟双删时第二次删除走异步。

### 5. IO、序列化与代码

- 大对象、大集合避免频繁创建，复用对象（ThreadLocal 缓存 SimpleDateFormat 等）。
- 避免 N+1 查询：循环里查库一次一个，改 join 或批量 `IN` 查询后内存组装。
- 批量操作代替循环单条：`insert ... values (),(),()`、MyBatis 批量执行器。
- 序列化：对外 API 用 Jackson 手动注册模块；内部 RPC 优先 Hessian/Protobuf（Dubbo 默认）。

### 6. 日志（被忽视的 IO 杀手）

- 生产关闭 debug 级别；异步 Appender 隔离磁盘抖动：

```xml
<appender name="ASYNC" class="ch.qos.logback.classic.AsyncAppender">
    <queueSize>1024</queueSize>
    <discardingThreshold>0</discardingThreshold>
    <neverBlock>true</neverBlock>
    <appender-ref ref="FILE"/>
</appender>
```

- `neverBlock=true` 队列满丢日志不阻塞业务——日志永远不能拖垮主流程。

## 四、数据库 MySQL 调优

### 1. SQL 层面（收益最大，优先做）

1. 开启慢查询日志，抓取慢 SQL：

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;    -- 记录超过1秒的
```

2. 每条慢 SQL 必过 `EXPLAIN`，看三处：

| 列 | 健康值 | 危险信号 |
| --- | --- | --- |
| type | ref / range 以上 | ALL（全表扫描）、index |
| key | 命中索引 | NULL |
| rows | 扫描行数小 | 大数字（几十万级） |
| Extra | Using index（覆盖索引） | Using filesort、Using temporary |

3. **避免索引失效**：函数包裹列、隐式类型转换（字符串列传数字）、`like '%xx'` 前导模糊、or 连接非索引列。
4. 避免 `select *`，只查需要字段，有机会走覆盖索引。
5. 避免大事务：事务不要包含外部 IO（RPC、发消息），事务尽量短——长事务是主从延迟和锁等待的头号来源。
6. 分页优化：`limit 100000, 20` 要扫 10 万行，改主键游标：`WHERE id > ? LIMIT 20`。

### 2. 索引设计规范

- 最左前缀：联合索引 (a,b,c) 支持 a / a,b / a,b,c，不支持 b 或 b,c。
- 区分度高的列在前；等值查询列在前，范围查询列在后。
- 单表索引建议 ≤ 5 个：每个索引都拖慢写入。
- 唯一索引交给业务层时注意幂等兜底。

### 3. MySQL 参数调优

| 参数 | 建议值 | 说明 |
| --- | --- | --- |
| innodb_buffer_pool_size | 物理内存 50-70%（独占机器） | **最重要参数**，热数据全在内存 |
| innodb_log_file_size | 1-4G | redo 日志，太小频繁刷盘 |
| max_connections | 500~2000，按业务 | 与上游连接池总和联动 |
| innodb_flush_log_at_trx_commit | 1（默认） | 1=每次提交刷盘最安全；2=每秒，宕机丢 1 秒数据，性能提升明显 |
| sync_binlog | 1（默认） | 与上条合称"双1"，金融必须双1，可容忍丢失的日志类业务可放宽 |

> 注意：**SQL 优化收益 >> 参数调优**，不要上来改 my.cnf。

### 4. 架构层优化

- 读写分离：读多写少，主写从读；注意主从延迟对"写后立读"的影响（强制走主或延迟容忍）。
- 分库分表：单表数据量超过千万或单库写入达到瓶颈时再上，按业务键分片（ShardingSphere）。
- 热点数据缓存到 Redis，减少 DB 压力。

## 五、中间件调优（Redis / MQ）

### Redis

**1. 先发现再治理：**

```bash
redis-cli --bigkeys                    # 扫描大 key（低峰跑）
redis-cli --hotkeys                    # 热 key（需 LFU 淘汰策略）
MEMORY USAGE <key>                     # 单个 key 精确内存
SLOWLOG GET 10                         # 慢命令
redis-cli --latency                    # 网络延迟基线
INFO memory                            # mem_fragmentation_ratio > 1.5 需关注
```

**2. 运行期规范：**

- 大 key 拆分：单个 String < 10KB，Hash 元素 < 5000，用 `hscan` 分批。
- 禁用生产危险命令：`keys *`、`flushall`、大集合全量 `smembers`（rename-command 屏蔽）。
- 批量代替循环：`mget`、`pipeline`（注意单批 ≤ 1000 条，分批发送）。

**3. 配置权衡：**

```
maxmemory 6gb
maxmemory-policy allkeys-lru     # 缓存场景；作存储时用 noeviction
io-threads 4                     # Redis 6+，网络 IO 多线程（命令执行仍单线程）
```

- 持久化：纯缓存可关 RDB/AOF；重要数据用混合持久化（RDB 做基线 + AOF 增量）。
- 集群：避免多 key 操作跨 slot（hash tag `{}` 控制）；主从复制风暴时逐个重启从库。

### MQ（RocketMQ / Kafka）

**RocketMQ：**

```properties
# 消费端提速
rocketmq.consumer.consume-thread-min=20
rocketmq.consumer.consume-thread-max=64
rocketmq.consumer.pull-batch-size=32
```

- 堆积治理三板斧：先扩消费者实例（注意消费者数 ≤ 队列数，超出的空转）、再临时跳过堆积（控制台 resetOffset 到最新）、最后补数据。
- 重试风暴：消费失败进重试队列（%RETRY%），默认重试 16 次每次间隔递增，死信队列（%DLQ%）要有监控和人工处理流程。
- 生产端批量发送 + 适当增大 `maxMessageSize` 提吞吐。

**Kafka：**

| 参数 | 建议 | 说明 |
| --- | --- | --- |
| linger.ms | 5 | 攒批时间，吞吐 vs 延迟权衡 |
| batch.size | 64KB | 单批大小 |
| compression.type | lz4/zstd | CPU 换网络与磁盘 |
| acks | 1（默认）/ all | all 最安全，吞吐降；金融场景必须 all + min.insync.replicas=2 |
| 分区数 | = 消费并行度上限 | 消费者数 > 分区数无意义；rebalance 风暴用 static membership 缓解 |

## 六、操作系统 OS 调优（Linux）

```bash
# 1. 文件句柄（默认1024，生产必调）
# /etc/security/limits.conf
* soft nofile 65535
* hard nofile 65535

# 2. 内核参数 /etc/sysctl.conf
net.core.somaxconn = 2048              # 监听队列，配合 Tomcat accept-count
net.ipv4.tcp_max_syn_backlog = 2048
net.ipv4.ip_local_port_range = 1024 65000   # 出方向端口范围，高并发调用下游必备
net.ipv4.tcp_tw_reuse = 1              # TIME_WAIT 复用（仅出方向）
net.ipv4.tcp_keepalive_time = 600
vm.swappiness = 1                      # 尽量不用 swap

# 3. 立即生效
sysctl -p
```

- Swap：生产尽量关闭 swap，防止内存被交换到磁盘，GC 停顿性能暴跌（数据库、JVM 机器 `swappiness=1` 起步）。
- 磁盘：数据库、日志盘优先 SSD/NVMe；机械盘做数据库必拖垮。
- 排障必备：`top -Hp <pid>`（线程级 CPU）、`vmstat 1`（si/so 看 swap、cs 看切换）、`iostat -x 1`（磁盘 await）、`dmesg -T | grep -i oom`（进程是否被杀）。

## 七、Spring Cloud Alibaba 微服务调优

微服务调优与单体的本质区别：**瓶颈从"计算"转移到"调用链"**。一条请求穿过后 网关 → 服务 A → Feign → 服务 B → DB，任何一环的超时、重试、线程配置不当都会级联放大。总纲一句话：**超时有预算、重试有上限、线程有隔离、依赖有熔断**。

### 0. 全链路超时预算（微服务调优第一件事）

自外向内层层收紧，**上游超时 > 下游处理时间总和**，否则上游已放弃、下游还在白跑占用资源：

```
网关 response-timeout 10s
  ≥ Feign 调用 readTimeout 5s
      ≥ 下游业务处理时间（Tomcat 200线程 × DB 慢查询场景需实测）
          ≥ DB statement timeout 2s
```

示例配置（网关层）：

```yaml
spring:
  cloud:
    gateway:
      httpclient:
        connect-timeout: 2000
        response-timeout: 10s
        pool:
          max-connections: 500       # 到下游的连接池
          acquire-timeout: 2000
```

### 1. Nacos（注册中心 + 配置中心）

**性能特征**：2.x 用 gRPC 长连接取代心跳，单节点轻松支撑数万实例；瓶颈通常在**服务端连接数、推送队列、存储**。

**客户端调优：**

```yaml
spring:
  cloud:
    nacos:
      discovery:
        server-addr: nacos-1:8848,nacos-2:8848,nacos-3:8848   # 集群地址都写上
        namespace: ${ENV}          # 环境隔离，防测试服务注册进生产
        group: DEFAULT_GROUP
      config:
        server-addr: ${spring.cloud.nacos.discovery.server-addr}
        file-extension: yaml
```

- **容灾**：Nacos 客户端会把服务列表和配置快照落地本地（`~/nacos/` 目录），注册中心全挂时已有服务仍可互相调用、应用仍能启动——不要在这套机制上做"注册中心挂了就熔断全部流量"的错误预案。
- **环境隔离**：namespace 按环境划分，group 按业务线划分，避免一个 namespace 挂几万个服务，订阅推送变慢。

**服务端（运维侧）：**

| 项目 | 建议 |
| --- | --- |
| 存储 | 内嵌 Derby 仅测试用，生产换 MySQL（或 2.2+ 的插件化存储） |
| 集群 | ≥ 3 节点 + Nginx/SLB 前置 |
| JVM | Nacos Server 也是 Java 进程，堆 4-8G + G1，出问题同样用 jcmd/JFR 诊断 |
| 配置中心 | 长轮询默认 30s（服务端 hold 29.5s），客户端配置变更秒级生效；配置发布频率本身要克制，大批量配置变更错峰 |
| 监控 | 连接数、推送失败率、慢 SQL（存储层） |

**高频事故**：客户端频繁断连重连（`server check fail`）——通常是网络设备对 gRPC 长连接空闲超时回收（如 LVS 900s），开启 TCP keepalive 或调低客户端 `keep-alive-time`。

### 2. OpenFeign / Dubbo（RPC 调用）

**OpenFeign 三个必做优化：**

```yaml
spring:
  cloud:
    openfeign:
      okhttp:
        enabled: true           # 1. 换连接池实现，默认URLConnection无池
      httpclient:
        hc5:
          enabled: true         # 或用 Apache HttpClient 5
      client:
        config:
          default:
            connect-timeout: 2000
            read-timeout: 5000
          order-service:        # 2. 分服务覆盖：慢接口单独放宽
            read-timeout: 8000
      compression:
        response:
          enabled: true         # 3. 大响应体开启 gzip
```

```yaml
# 连接池大小：与下游 Tomcat 工作线程数匹配
feign:
  okhttp:
    enabled: true
# okhttp 池参数通过 bean 定制，或用 httpclient：
# feign.httpclient.max-connections=200
# feign.httpclient.max-connections-per-route=50
```

**连接池数学关系**：本服务 Tomcat 200 工作线程，每个线程最多发起 1 个 Feign 调用，则到每个下游的 `max-connections-per-route` ≥ 200 才不会排队——否则下游不慢，自己先排队超时。

**重试纪律（防重试风暴的前提）：**

```java
@Bean
public Retryer feignRetryer() {
    // 初始间隔100ms，最大间隔1s，最多重试2次（共3次请求）
    return new Retryer.Default(100, TimeUnit.MILLISECONDS, 2);
}
```

- Spring Cloud OpenFeign **默认不重试**（NEVER_RETRY），这是刻意的——重试必须显式开启且只对**幂等接口**（GET、带幂等键的写）。
- 全链路重试总次数 ≤ 2：网关重试 + Feign 重试 + MQ 重投的总放大倍数是乘法关系（见 7.7）。

**Dubbo 场景（依赖更重时替代 Feign）：**

```yaml
dubbo:
  protocol:
    threads: 200            # 业务线程池，满了抛 RejectedExecutionException
    threadpool: fixed
  consumer:
    timeout: 3000
    retries: 1              # 默认重试2次！写接口必须改为0
    connections: 100
```

- Dubbo 默认 `retries=2` 且失败重试会换节点重发——**写操作不改成 0 必然产生重复数据**，这是 Dubbo 新手第一大坑。
- 线程池满的表现：`Thread pool is EXHAUSTED`——先用 jstack 看线程卡在哪（通常是慢下游拖死），而不是盲目调大。
- 异步化：`CompletableFuture` 返回值替代同步调用，聚合多个下游时并行拉取，RT 从"串行总和"降为"最慢一个"。

### 3. Sentinel（限流熔断降级）

**四类规则对应四类问题：**

| 规则类型 | 解决的问题 | 关键参数 |
| --- | --- | --- |
| 流控 QPS | 流量超出容量 | 阈值 = 单机压测 QPS × 0.8 |
| 流控并发线程数 | 慢调用拖垮线程池 | 阈值 ≈ 工作线程数 × 0.9，天然隔离 |
| 熔断慢调用比例 | 依赖劣化快速失败 | 最大RT、比例阈值、熔断时长 |
| 熔断异常比例 | 依赖报错雪崩 | 比例阈值、最小请求数 |
| 热点参数 | 个别参数打爆（如爆款商品ID） | 参数索引、限流阈值 |
| 系统自适应 | 整机保护 | 入口QPS / 平均RT / CPU、Load1 |

**流控效果三选一：**

- 快速失败：直接拒绝，返回 fallback——绝大多数场景。
- Warm Up（冷启动，冷加载因子默认 3）：应用刚启动缓存未预热、或大促零点流量涌入，让阈值爬坡而不是瞬间打满。
- 排队等待（匀速）：削峰填谷，请求在超时内排队通过，适合可延迟的任务型流量（如秒杀请求转队列）。

**生产部署要点：**

1. Dashboard 不常驻生产常开（规则改动走审批）；
2. **规则必须持久化到 Nacos**，否则重启全丢：

```yaml
spring:
  cloud:
    sentinel:
      datasource:
        ds-flow:
          nacos:
            server-addr: ${NACOS_ADDR}
            data-id: ${spring.application.name}-flow-rules
            rule-type: flow
        ds-degrade:
          nacos:
            server-addr: ${NACOS_ADDR}
            data-id: ${spring.application.name}-degrade-rules
            rule-type: degrade
```

3. 降级要有兜底：`blockHandler` / `fallback` 返回默认值或友好错误，而不是把 500 抛给用户：

```java
@SentinelResource(value = "queryOrder", blockHandler = "queryOrderBlock")
public Order queryOrder(Long id) { ... }

public Order queryOrderBlock(Long id, BlockException ex) {
    return Order.empty();   // 兜底：返回缓存默认值或友好提示
}
```

4. 慢调用熔断的 RT 上限是 4900ms，超过按 4900 算——超长依赖应先用监控暴露，再定阈值。

### 4. Seata（分布式事务）

**性能模型先想清楚**：AT 模式 = 一阶段本地提交 + undo_log 快照 + 全局行锁。代价有两块——undo_log 写放大、**全局锁热点竞争**（两个全局事务改同一行，第二个必须等）。

**调优要点：**

```yaml
# TC Server（事务协调器）存储模式：file 仅测试，生产 db 或 redis
seata:
  server:
    store:
      mode: redis          # redis 模式性能最好（1.5+），db 模式更稳
```

- **事务范围最小化**：`@GlobalTransactional` 只包住"必须一致"的分支，查询、RPC 聚合、发消息全部移出事务；全局事务默认 60s 超时（`default.global.transaction.timeout`），大事务必然超时回滚。
- **热点数据慎用 AT**：秒杀库存这种热点行，全局锁让吞吐掉一个数量级——改用 TCC（Try 预冻结 / Confirm / Cancel）或直接 Redis + Lua 扣减 + 异步落库。
- undo_log 清理：Seata 自动异步清理，注意该表所在库的磁盘与 binlog 增长。
- 事务模式选择：一致性要求能容忍最终一致 → 消息事务（RocketMQ 事务消息）比 Seata 轻、吞吐高，**能用消息解决的不要上全局事务**。

### 5. Spring Cloud Gateway（网关）

网关是响应式（Reactor + Netty），调优核心只有一条铁律：**事件循环线程里绝不能阻塞**。

- 阻塞一毫秒，整条事件循环上所有请求一起卡：`filter` 里写同步 Feign 调用、同步 Redis、`Thread.sleep`、`blocking IO` 都是事故。必须阻塞的逻辑放 `Schedulers.boundedElastic()` 弹性线程池。
- 内存：Netty 用堆外，必须显式设上限，否则容器环境报 `Direct buffer memory`：

```
-XX:MaxDirectMemorySize=512m
```

- 路由量大时用动态路由（配置中心驱动）避免重启加载上千条路由的启动风暴。
- 限流用 `RequestRateLimiter` + Redis 令牌桶，按 IP/用户维度 key：

```yaml
spring:
  cloud:
    gateway:
      redis-rate-limiter:
        replenish-rate: 100    # 令牌生成速率 100/s
        burst-capacity: 200    # 桶容量，允许瞬时突发
```

- 跨域、鉴权、签名校验等全局 filter 保持轻量——网关每加 1ms，全站每个请求都加 1ms。

### 6. 链路追踪 SkyWalking（微服务调优的眼睛）

微服务调优没有链路追踪等于盲调：RT 高不知道高在哪一跳。

- Java Agent 无侵入接入，加一行启动参数：

```
-javaagent:/opt/skywalking-agent/skywalking-agent.jar
-Dskywalking.agent.service_name=order-service
-Dskywalking.collector.backend_service=oop:11800
```

- **生产采样率 10%~20%**（`agent.sample_n_per_3_secs`），全量采集存储扛不住；ERROR 链路建议全采。
- 存储用 ES（7.x+），按天滚动索引，保留 7~14 天。
- 治理动作：先用拓扑图找"红色节点"，再下钻该服务 trace 看各 span（DB / Redis / 下游 RPC）耗时占比，最后回到第三节对症下药。

### 7. 微服务高频事故模式

**重试风暴（最经典）**：

```
假设：网关超时重试 2 次 × Feign 重试 2 次 × LoadBalancer 重试 1 次
一次失败请求 = 2 × 2 × 2 = 8 次打到底层服务
叠加 MQ 重投、用户端刷新，瞬间放大几十倍流量 → 雪崩
```

治理：全链路重试总放大 ≤ 2~3 倍；重试带退避（Retryer 的间隔参数）；重试必须配熔断（Sentinel），熔断打开期间连重试机会都没有；写操作零重试（靠幂等表/唯一键兜底）。

**线程池连锁耗尽**：服务 B 慢 → 服务 A 的 Tomcat 线程全卡在等 B → A 对 C 的请求也没线程处理 → C 以为 A 挂了。治理：Feign readTimeout 收紧（快速失败）+ Sentinel 并发线程数限流 + 关键依赖线程池隔离。

**注册中心抖动级联**：Nacos 网络抖动 → 客户端全量重新拉取订阅 → 大量服务同时重连（惊群）。治理：客户端连接池与重连退避、服务端集群健康探测、扩容错峰重启。

**缓存与 DB 的循环依赖**：Redis 挂 → 全量穿透到 DB → DB 慢 → 应用线程耗尽 → 连 Redis 健康检查的超时都报不出来。治理：Sentinel 对 Redis 调用加熔断降级，本地 Caffeine 兜底热点 key。

## 八、压测与容量规划

调优的成果要用压测验证，容量要用公式算，不能拍脑袋。

### 1. Little's Law（容量计算第一公式）

```
并发数 = QPS × 平均RT（秒）
```

例：目标 2000 QPS，平均 RT 0.2s → 需要同时在处理中的请求 = 400 并发。
反推单机容量：4 核机器实测 500 QPS（RT 100ms），则目标 2000 QPS 需要 2000/500 = 4 台，再留 40% 水位 → 部署 6~7 台。

### 2. 压测方法

| 工具 | 适用 |
| --- | --- |
| wrk / wrk2 | HTTP 快速压测，单机发压能力强 |
| JMeter | 场景编排、参数化、报表全 |
| Gatling | 代码化场景，报告漂亮 |
| 阿里 PTS / 全链路压测平台 | 微服务全链路，带流量染色 |

- 阶梯加压（100 → 500 → 1000 QPS）找拐点：RT 开始陡增或错误率出现的点就是单机容量。
- 压测数据必须接近真实：数据量级（千万行表 vs 空表结果完全不同）、热点分布、缓存命中率。
- 全链路压测用流量染色 + 影子表（影子库），压测请求全链路打标，写操作落影子存储。
- 观测压测全程：GC 日志、慢 SQL、连接池水位、下游中间件指标一起看，瓶颈会转移（DB 优化完瓶颈到 Redis，Redis 优化完到网络）。

### 3. 水位线管理

| 日常 | 大促/高峰 | 说明 |
| --- | --- | --- |
| CPU ≤ 40% | ≤ 60~70% | 留余量给突发与故障转移 |
| 连接池 ≤ 50% | ≤ 80% | 满了排队超时 |
| MQ 堆积 0 | 消费延迟 < 1 分钟 | |

## 九、生产调优标准流程（最重要）

1. **发现问题**：监控告警，RT 升高、CPU 高、报错、堆积；
2. **复现问题**：尽量压测环境复现，不要直接生产改；
3. **定位根因**：
   - CPU 高：是业务计算？GC？死循环？数据库？（`top -Hp` + jstack，GC 线程高转内存问题）
   - 内存高：内存泄漏？堆设置过小？大对象？（dump + MAT）
   - RT 高：慢 SQL？网络？锁等待？外部接口调用慢？（SkyWalking 分段定位）
   - 微服务雪崩：哪个依赖先慢？重试放大了吗？熔断开了吗？
4. **小改动**：一次只改一个点，不要一堆参数一起改；
5. **验证效果**：观察监控指标，看是否改善（对比同一时段基线）；
6. **回滚预案**：任何修改必须准备回滚方案（配置中心改的参数记录旧值，发布走灰度）；
7. **持续观察**：上线后观察一段时间，防止新问题引入。

诊断工具（jcmd、JFR、MAT、Arthas）的完整用法见《JDK 生产环境检测与分析工具》。

## 十、常见生产坑大全

### 单体时代的老坑

1. 凭经验瞎调参数，没有监控；
2. 大量修改参数，无法定位哪个改动生效；
3. 只调 JVM、数据库参数，不去优化慢 SQL 和业务代码；
4. 大事务、循环查询数据库，线上拖垮整个库；
5. 连接池设置过大，数据库连接打满；
6. 日志打印过多，磁盘 IO 打满。

### 微服务时代的新坑

7. **超时全用默认值**：Feign 默认 60s readTimeout，一个慢下游能把整条链路线程挂死几分钟；
8. **重试配置无全局视角**：网关、Feign、MQ 三层重试相乘，故障流量放大几十倍；
9. **Dubbo 写接口没关重试**：默认 retries=2，重复下单、重复扣款；
10. **Sentinel 规则存内存**：一重启全丢，限流形同虚设；
11. **Nacos 用内嵌 Derby 单机跑生产**：存储打满、无高可用；
12. **网关里写阻塞代码**：一行同步 IO 卡死整条事件循环；
13. **Seata 大事务**：全局事务包住 RPC + 消息，60s 超时反复回滚，吞吐崩塌；
14. **压测只压应用不压数据**：空表 1 万 QPS，千万行表上线秒变 100 QPS；
15. **没有环境隔离**：测试服务注册进生产 Nacos，测试流量打到生产库；
16. **监控只看应用不看依赖**：应用 P99 正常，Redis 慢日志爆表无人发现。

> 一条主线贯穿全文：**监控发现问题 → 链路定位瓶颈 → SQL/代码层收益最大 → 参数微调 → 压测验证 → 灰度上线**。参数调优永远是最后一环，不是第一环。
