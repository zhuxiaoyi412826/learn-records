# 主流 2D 图形 / 矢量 / 精灵 / 贴图文件格式分类

## 一、通用位图格式

### 1. PNG（Portable Network Graphics）

- **用途**：截图、图标、透明背景图、UI 切图。
- **优点**：**无损压缩**、支持 Alpha 透明、跨平台、浏览器原生支持。
- **缺点**：文件体积通常大于 JPEG/WebP；不支持动画（APNG 除外，兼容性弱）。

### 2. JPEG / JPG

- **用途**：照片、连续色调图像、网页大图。
- **优点**：**有损压缩**比极高，体积小，兼容性极好。
- **缺点**：有损、产生块状伪影；不支持透明；反复编辑会累积损伤。

### 3. GIF（Graphics Interchange Format）

- **用途**：简单动画、表情包、低色彩图形。
- **优点**：支持动画、广泛兼容、文件小。
- **缺点**：仅 256 色，画质差；不适合照片；专利历史（现已自由）。

### 4. BMP（Bitmap）

- **用途**：Windows 原生无压缩位图。
- **优点**：无压缩、解析简单、保真。
- **缺点**：体积巨大，无透明，网络与印刷几乎不用。

### 5. TIFF（Tagged Image File Format）

- **用途**：印刷、出版、扫描归档、专业摄影。
- **优点**：无损/多页/多层/高比特深，印刷级质量。
- **缺点**：文件极大，Web 不友好，软件支持不一。

### 6. WebP

- **用途**：现代网页图像（Google 推出）。
- **优点**：同时支持**有损/无损 + 透明 + 动画**，体积比 PNG/JPEG 明显更小。
- **缺点**：老浏览器/旧软件兼容性需兜底；部分专业设计软件支持仍不完整。

## 二、矢量图形格式

（无限放大不失真，UI、图标、logo）

### 1. SVG（Scalable Vector Graphics）

- **用途**：网页图标、Logo、数据可视化、UI 图形。
- **优点**：
  - 文本格式（XML），可被搜索引擎索引、脚本操控（CSS/JS 动画）。
  - 无损缩放，文件小，开源开放标准，浏览器原生支持。
  - 适合与前端直接集成。
- **缺点**：
  - 不适合表现复杂照片级影像；超复杂路径文件会变大。
  - 不同渲染引擎（浏览器/设计软件）对特效支持略有差异。

### 2. AI（Adobe Illustrator）

- **用途**：专业插画、品牌视觉、印刷前设计。
- **优点**：功能最完整的矢量编辑源文件，图层/样式/效果丰富。
- **缺点**：**专有闭源格式**，需 Illustrator 打开；非文本无法直接跨软件无损互通；不适合网络直接展示。

### 3. EPS（Encapsulated PostScript）

- **用途**：印刷出版、跨软件图形交换（传统标准）。
- **优点**：与 PostScript 印刷管线兼容好，可嵌入矢量与位图。
- **缺点**：已逐步被 PDF 取代；不支持现代透明/图层概念；预览依赖外部。

### 4. PDF（Portable Document Format）

- **用途**：跨平台文档、印刷稿、可含矢量与位图的"容器"。
- **优点**：跨平台一致、所见即所得、可嵌入字体/矢量/位图；印刷与归档首选。
- **缺点**：作为"模型源文件"编辑性弱；体积可能偏大；矢量编辑需借助专业工具提取。

### 5. CDR（CorelDRAW）

- **用途**：CorelDRAW 设计源文件，广告/刻字/印花常用。
- **优点**：矢量编辑能力强，排版与特效丰富。
- **缺点**：专有格式，跨软件兼容性差，新版本文件旧版常打不开。

## 三、游戏开发专用

精灵、图集、像素动画格式

### 图集打包文件（多张图片合并一张大图 + 坐标描述）

1. **Atlas /.atlas（TexturePacker 标准）** 搭配一张 PNG 大图，`.atlas`文本记录每个精灵矩形位置； LibGDX、Phaser、Cocos 经典格式。
2. **.plist** TexturePacker 输出的 plist（XML），Cocos2d-x 老牌图集格式。
3. **.spriteAtlas（Unity）** Unity 内置图集描述。

### 骨骼动画素材格式（2D 骨骼，重点！）

1. **.json + PNG（Spine）** Spine 标准输出：骨骼动画数据 json，配套贴图；通用引擎标准（Phaser、LibGDX、Godot、Unity） 还有二进制版本 `.skel`。
2. **.dragonbones（龙骨 DragonBones）** 国产 2D 骨骼动画，配套贴图；白鹭、Cocos 生态大量使用。
3. **.aseprite / .ase** Aseprite 原生像素动画源文件，支持帧动画、图层、调色板；像素游戏必备。可导出 GIF/PNG 序列。

### 帧动画序列载体

- **GIF (.gif)** 老旧帧动画，最多 256 色，半透明效果差；预览用，不建议游戏正式素材。
- **APNG (.apng)** 动态 PNG，支持透明，比 GIF 质量高；很多引擎支持有限。

## 四、美术软件

【源工程格式】（保存图层、时间轴，不能直接当素材）

1. **PSD (.psd)** Photoshop 分层原画、UI 源文件；几乎所有美术管线通用。 拓展：PSB（超大尺寸画布）
2. **Clip Studio Paint：.clip** 插画、漫画主流源文件。
3. **Procreate：.procreate** iPad 绘画源文件。
4. **Figma：.fig** UI 设计源文件，云端优先，可导出 SVG/PNG。
5. **Affinity Designer：.afdesign** 矢量替代 AI。

## 五、字体相关 2D 矢量轮廓

- **TTF / OTF** 字体文件（矢量字形）

## 六、贴图压缩格式

（游戏引擎 GPU 专用，外部软件打不开）

显卡原生压缩贴图，**不能用 PS 直接编辑**

- **KTX2 (.ktx2)** ⭐现代跨平台标准（Vulkan、OpenGL、WebGPU、Godot 优先）
- **DDS (.dds)** DirectX 传统压缩贴图（Windows、DX 游戏）
- **PVR (.pvr)** 苹果移动端 iOS 老格式

# 主流 3D 模型文件格式

## 一、通用交换格式（跨软件互通，最常用）

### 1. GLB / GLTF（推荐首选）

- 后缀：`.glb`（二进制单文件）、`.gltf`（文本 + 外部资源）
- 特点：Web3D 标准，轻量化，支持材质、骨骼动画、贴图、PBR；游戏、网页、Three.js、Godot、Unity、Blender 通用
- 适用：网页展示、游戏资产、AI 生图 3D 输出、跨引擎交换

### 2. FBX

- 后缀：`.fbx`
- Autodesk 出品，**动画、骨骼、绑定行业标准**
- 支持：骨骼动画、形变动画、摄像机、灯光、权重、材质
- 缺点：闭源格式，版本兼容性坑多；文件偏大
- 适用：Blender ↔ Maya ↔ 3ds Max ↔ Unity ↔ Unreal

### 3. OBJ

- 后缀：`.obj` + `.mtl`（材质文件）
- 极简老式格式，**只存顶点、UV、面**
- ❌ 不支持骨骼、动画、法线贴图高级属性
- 优点：几乎所有 3D 软件全能打开
- 适用：静态模型简单互导、雕塑、CAD 简易模型

### 4. STL/STEP

- 后缀：`.stl`
- **3D 打印专用格式**
- 仅三角面片几何信息，无颜色、材质、UV、动画
- 分 ASCII 文本 / 二进制
- 适用：切片软件（Cura）、工业 3D 打印

## 二、专业建模软件原生格式

> 这类格式包含图层、修改器、工程历史，**尽量不要拿来给别的软件导入**

1. **Blender**：`.blend`
2. **3ds Max**：`.max`
3. **Maya**：`.ma`（ascii） / `.mb`（二进制）
4. **Cinema 4D**：`.c4d`
5. **ZBrush**：`.ztl`（雕塑原生）
6. **Rhino 犀牛**：`.3dm`（工业 NURBS 曲面）
7. **SketchUp 草图大师**：`.skp`

## 三、工业 / CAD 曲面格式

**（机械、产品设计，NURBS 曲面，不是网格）**

网格模型（游戏 / 动画） vs CAD 曲面（工业建模）互不通用！

1. **STEP**：`.stp / .step` 国际通用工业交换标准
2. **IGES**：`.igs / .iges` 老牌曲面交换
3. **SolidWorks**：`.sldprt`
4. **AutoCAD**：`.dwg` / `.dxf`（2D 为主，支持简单 3D）
5. **CATIA**：`.catpart`

## 四、游戏引擎专用格式

1. Unity：`.prefab`（实例）、`.asset`；导入源文件一般用 FBX/GLB
2. Unreal Engine：`.uasset`、`.usd`
3. Godot：`.tscn`场景、`.res`资源，优先 GLB 导入
4. USD / USDZ
   - `.usd` `.usda` `.usdc`：皮克斯开源，影视、元宇宙、苹果 AR
   - `.usdz`：苹果 AR 专用单文件格式（AR 预览）



## 五、影视 / 动画 / 特效

### 14. USD / USDC / USDA / USDZ（Pixar / OpenUSD）

- **用途**：面向影视 VFX 与大型场景的**通用场景描述**，支持分层、非破坏编辑、可扩展；USDZ 为 Apple/AR 单文件封装。
- **优点**
  - 强大的可扩展场景图、分层协作；
  - 被多家巨头（Pixar、Apple、NVIDIA、Autodesk）支持；
  - 适合超大规模资产与流水线。
- **缺点**
  - 体系复杂、学习曲线陡；
  - 中小团队收益有限；
  - 实时/轻量传输不如 glTF。

## 六 、推荐选择

- **游戏 / 实时 / Web / AR**：优先 **glTF/GLB**（次选 FBX 进引擎）。
- **静态模型交换**：**OBJ**（简单）或 **glTF**（现代）。
- **带骨骼动画资产**：**FBX**（主流）或 **glTF**。
- **3D 打印**：**STL**（兼容）或 **3MF**（信息更全）。
- **机械 / 工业设计互通**：**STEP**。
- **建筑工程协作**：**IFC**。
- **影视 / 大型场景流水线**：**USD**。
- **激光雷达 / 扫描**：**LAS/LAZ、E57**。
- **长期源文件**：保留**原生格式** + 导出通用格式备份。

# 3D模型区别

全部都是 3D 网格模型  差异区别

1. 有没有骨骼与权重绑定；
2. 动画依靠骨骼还是物理 / 蓝图；
3. 是否需要挂载到其他物体上。

- 带骨骼 = 骨架网格体 (Skeletal Mesh)
- 不带骨骼 = 静态网格体 (Static Mesh) 人物、手持枪械大多属于 **骨架网格体**；花瓶、桌椅属于 **静态网格体**。

| 特性              | StaticMesh                   | SkeletalMesh                                |
| ----------------- | ---------------------------- | ------------------------------------------- |
| 顶点变换          | GPU 完成（固定）             | CPU 蒙皮 → 传到 GPU（开销高）               |
| 静态光照 Lightmap | ✅ 支持，烘焙后几乎无光照开销 | ❌ 不支持，只能用动态光照                    |
| 实例化            | ✅ GPU 实例化海量道具         | ❌ 原生不支持高效实例化（大量 NPC 代价巨大） |
| LOD               | 简单，预计算                 | 骨骼也要同步 LOD，额外开销                  |

# 2D模型

**2D 游戏里，严格来说没有 “模型 (Mesh 网格)” 这个概念**，行业口语大家习惯叫 “模型”，本质是**精灵 / 图集切片**。 先区分两大主流 2D 技术路线：**帧动画精灵**、**骨骼精灵（Spine / DragonBones）**

## 一、先统一术语

1. 帧动画：一堆连续图片序列（逐帧绘制）
2. 骨骼精灵：一张图集 + 骨骼 + 权重，靠骨骼扭曲图片切片

> Godot/Unity 2D、Cocos 通用这套体系

对应类比 3D 方便你理解：

- 2D 静态图片道具 ≈ 3D StaticMesh
- 2D 骨骼精灵 ≈ 3D SkeletalMesh

## 二、逐帧动画 VS Spine 骨骼动画

- **逐帧动画 ≈ 预渲染好一系列快照，每一帧都是独立图像**
- **Spine 骨骼动画 ≈ 2D 版 SkeletalMesh，靠骨骼驱动切片变形**

### 一、核心原理

1. **逐帧动画（帧动画）** 把角色每一个动作关键姿态全部画出来，打包成图集序列。播放时快速切换图片实现动画。
2. **Spine 骨骼动画** 把人物拆成零件（头、躯干、手臂、腿），给零件绑定骨骼；通过旋转 / 移动骨骼带动部件运动，实时生成姿态，没有预绘制的完整姿态图。

### 二、优缺点对比

#### 逐帧动画

✅ 优点

1. **美术表现力上限最高** 画师逐帧手绘，可以实现夸张形变、挤压拉伸、流畅卡通夸张动作，风格不受限制；像素画风、复古像素游戏首选。
2. **引擎运行开销极低** 没有骨骼计算，只做贴图切换；不需要 CPU 实时运算顶点变换。
3. **实现简单，不依赖第三方运行库** 不需要集成 Spine runtime，轻量化小游戏、H5 小游戏兼容性更好。
4. 不存在 “骨骼扭曲穿模” 问题，每一帧成品画面稳定。

❌ 缺点

1. **资源体积巨大** 行走、攻击、待机、转向、受伤，每个方向一套序列，贴图膨胀严重。
2. 修改成本极高 想微调走路姿态，必须重新绘制大量帧；改角色身高、服装，几乎要重画全部动画。
3. **换装极难实现** 很难单独替换头盔、武器，大多需要绘制多套完整角色图。
4. **缩放缺陷** 放大容易模糊，难以无损缩放；不适合需要多分辨率自适应的项目。

#### Spine 骨骼动画

✅ 优点

1. **资源包体极小** 一套零件切片，所有动作复用素材；待机、走路、攻击共用躯干四肢贴图。
2. **编辑灵活，迭代快** 动作随时调整关键帧；角色体型、部件位置可以直接在编辑器调整。
3. **天然支持换装、插槽挂载** 武器、头盔、披风直接挂骨骼插槽，完美适配 RPG、射击类人物换装需求。
4. **支持自由转向、角度旋转** 可以轻松实现角色 360° 转向，不用每个方向单独绘制动画。
5. 支持 IK 反向动力学（手部跟随枪械、脚部贴合地面）

❌ 缺点

1. **美术门槛更高** 需要拆分部件、绘制无缝切片，绘画思维和逐帧不一样；纯手绘卡通夸张形变很难做出逐帧的质感。
2. **运行有 CPU 开销** 游戏内每帧计算骨骼变换（类似 3D 骨架网格），大量同屏角色时压力上升。
3. **必须接入 Spine 运行时库** 增加项目打包体积，部分平台（小游戏）有适配成本。
4. 容易出现穿模、部件穿插，需要美术精细调整。

### 三、适用场景（直接照着选型）

#### 🎨 优先选【逐帧动画】

1. **像素风格游戏**（像素动作、复古 RPG、像素射击） 像素拆分骨骼极易破坏像素轮廓，几乎全部采用逐帧。
2. 需要大量夸张卡通形变：挤压、拉伸、柔滑卡通特效动画。
3. 小型小游戏、H5 广告游戏，追求最简依赖、极致兼容性。
4. 动作数量很少、角色无法换装，动作不复杂。
5. 特效动画（爆炸、火花、闪光特效绝大多数用逐帧）

#### 🦴 优先选【Spine 骨骼动画】

1. 需要**角色换装、武器切换**（ARPG、横版动作、2D 射击）
2. 角色动作繁多：行走、奔跑、跳跃、攻击、闪避、受击
3. 需要多角度转向、人物跟随武器瞄准（2D 俯视角 / 斜 45° 射击游戏）
4. 角色数量多，严格控制安装包大小
5. 需要 IK 功能：手部握持枪械、足部贴合地形
